# ページの型の割り当て（Agent の差分）

> ページの型（A〜D）と共有プリミティブの共通規約は platform の [UX 契約 page-archetypes.md](../../platform/docs/ux-contracts/page-archetypes.md)、作業状態と離脱ガードは [workspace-state.md](../../platform/docs/ux-contracts/workspace-state.md) が正本。
> 本書には Agent の各ページがどの型に属するかと、Agent 固有の補足だけを書く。システム設定（OCI 認証 / アップロード保存先 / モデル / データベース）は共有パッケージの画面なので対象外。

## 1. 割り当て

ルートの正本は `frontend/src/lib/routes.ts`（`APP_ROUTES`）と `frontend/src/App.tsx`。画面は `frontend/src/pages/<領域>/<画面>.tsx`（`agents` / `runs` / `approvals` / `audit` / `skills` / `settings` など）に置き、`App.tsx` が `React.lazy` で route ごとに読む（#818）。読み込みの間は `PageBody wide` の中に `TimedLoadingState`（「画面を読み込んでいます」、`placement="page"`）を出す。

| 型 | ページ（ルート） | 補足 |
|---|---|---|
| A. 一覧 → 全画面エディタ | 自動実行（`/automations`。#784）/ 業務 Agent（`/agents`）/ スキル（`/skills`）/ MCP 接続（`/settings/mcp-connections`） | `?id=` を唯一の情報源にする（§1.1）。 |
| B. マスタ詳細の閲覧 | フィードバック（`/feedback`。#2283）/ ツール（`/tools`。ナビには出さない） | フィードバックは狭い一覧と広い詳細を共有の `ListDetailLayout` で並べ、選択は URL（§1.2）。ツールは `FixedSplitPane` のまま（ナビに無い画面なので #2283 では移さなかった）。 |
| B の例外. 一覧 → 全幅の詳細 | 実行履歴（`/runs`。#875）/ 承認（`/approvals`。#877） | 実行は回答と過程、承認は目標・理由・引数と判断記録を全幅で確認する。実行の作成は `?id=new`、詳細は各対象 ID。承認には作成画面を設けない（§1.3 / §1.4）。 |
| C. ツール / ワークフロー | 監査ログ（`/audit`）/ 品質評価（`/evaluation`。評価セットの一覧 → 実行状況 → 評価概要（前回との比較）→ ケース別結果（行からケースの詳細を 40rem の `SideSheet`〔`size="md"`〕で開き、見出しの行の「前へ / 次へ」〔`pager`〕で評価の結果の前後のケースへ移る。#2283）→ 最近の評価 → 評価を比べる（2 つの評価を同じ質問のケースどうしで並べる。業務 Agent をまたいでよい。#1845）。評価セットは A 型の `?id=` の全画面エディタで、評価ケースを 1 件ずつ編集し Excel で取り込み・書き出しする）| 監査ログは 絞り込み → 適用 → 結果の `DataTable`。 |
| D. ダッシュボード / 状態 | 実行環境（`/runtimes`。組み込みの実行環境の状態）/ 利用状況（`/usage`）/ ツール権限（`/settings/tool-policy`。ナビには出さない。ツールの一覧は検索・ページングの表。#818） | 運用設定の単一フォームは「状態 + 最小の編集」として D 型に置く。ダッシュボード（`/`）は廃止した（#262）。チャット（`/chat`。#768）は会話の画面で、型の外（入力 → 回答を会話として積む。送信は「その場で結果を待つ操作」で、実行中は同じボタンが「停止」になる。buttons.md §3.1）。 |

### サイドナビの構成（#791）

上に一般の利用者が毎日使う画面、下に管理者が作る・運用する画面を置く（RAG・NL2SQL と同じ考え方。#658）。
正本は `frontend/src/components/layout/nav-config.ts`。権限管理の機能の一覧も同じ並び・名前になる（#567）。

| セクション | 項目 | 使う人 |
|---|---|---|
| AI 活用（NL2SQL と同じ名前） | チャット / 実行履歴（`/runs`）/ 承認 | 一般の利用者 |
| Agent 構築（RAG の「ナレッジ構築」・NL2SQL の「データ準備」に当たる） | 業務 Agent / スキル / 自動実行 | 管理者（作る人） |
| 改善・運用 | 品質評価 / フィードバック / 利用状況 / 監査ログ | 管理者・監査担当 |
| セキュリティ設定 → ユーザーとロール | 権限管理 → ユーザー管理 / ロール管理 | 管理者 |
| 運用設定 | システムテーブル / 実行環境（`/runtimes`）/ MCP 接続 | 管理者 |
| システム設定（3 製品共通） | OCI 認証 / アップロード保存先 / モデル / データベース | 管理者 |

画面・ナビの文言に「Control Plane」「Runtime」のような基盤の用語を使わない（コードの識別子・URL・権限コードはそのまま）。用語は次にそろえる（#802 / #807）。

| 概念（コード） | 画面の文言 |
|---|---|
| Run（`run`） | 実行（一覧は「実行履歴」） |
| Skill（`skill`） | スキル |
| Runtime（組み込み Runtime） | 実行環境 |
| Approval / Audit | 承認 / 監査ログ |

`/` は画面を持たない入口で、NL2SQL と同じく次のように振り分ける（`frontend/src/lib/route-permissions.ts`）。

- `/` → ナビの並び順で最初に開ける画面（`firstAllowedRoute`。どれも開けなければ権限なしの画面）。
- 未知の URL・ログイン後・権限なしの画面の「利用可能な画面へ戻る」→ 既定入口（`defaultEntryRoute`）。ナビの先頭のチャット（`/chat`）を開ければチャット（RAG と同じ。#791）、開けなければ `/` を経て最初に開ける画面。
- どちらも `Navigate replace` で移し、履歴に `/` や未知の URL を残さない。

### 1.1 A 型（一覧 → 全画面エディタ）

`frontend/src/lib/editor-route.ts` の `useEditorRoute` が URL の検索パラメータ `id` を読み書きする。

| `?id=` | 表示 |
|---|---|
| なし | 一覧（`PagedDataTable`）。上に `ListToolbar`（左に `SearchField`、右に件数の `ListCount`「全 N 件」「N 件（全 M 件）」。#808 / #1891）。下のページ送りは表示件数（10 / 25 / 50 / 100）とページ番号の入力を持つ。ページ操作（新規作成・最新情報を取得）は `PageHeader` |
| `new` | 新規作成のエディタ |
| `<対象の ID>` | その対象のエディタ。一覧に無い ID は「対象が見つかりません」と一覧へ戻る導線を出し、別の対象へ黙って置き換えない |

| 画面 | ID | エディタの節 | 対象の操作（`EntityAction`） |
|---|---|---|---|
| 業務 Agent | Agent ID | 概要（版の履歴。#770）/ 基本情報（`FormGrid`。名前 md・説明と指示は全幅・モデル lg。#1891）/ スキル（`ListPicker`）。新規は先頭に「テンプレートから始める」（#780） | 公開・有効にする・無効にする（版の履歴の行に「この版に戻す」） |
| スキル | Skill ID | 概要 / 基本情報 / 内部依存。ビルトイン・ファイル・env は読み取り専用の詳細 | 削除（実行時に追加したスキルだけ） |
| MCP 接続 | 接続 ID | 概要 / 接続 / 認証（秘密は `SecretField`）/ ツール（tools/list の取得。結果は `SettingsTestResultPanel`。#814） | 削除（RAG / NL2SQL・宣言の接続は削除不可） |

- 開く・閉じるは履歴に積む。再読込・戻る / 進むで同じ対象が開く。新規作成に成功したら作成した対象へ、エディタで削除したら一覧へ、どちらも `replace` で移る（戻るで空の新規フォームや消えた対象へ戻さない）。
- 「一覧へ戻る」は `PageHeader` の `back`（左上・タイトルの上。読み上げ名は「{一覧}の一覧へ戻る」）。2 階層のパンくずは出さない（#618）。`back` も §2 の離脱ガードの対象。
- 保存・作成・導入・追加の失敗は、欄に結び付くもの（未入力・JSON の形式）は欄の直下、それ以外は確定の行（フォームの末尾の `FormActionBar`）の直上の共有 `SaveErrorBanner` の 1 か所だけに出す（UX 契約 messaging.md §3.3.1。#585 / #1786）。Toast には重ねない。testId は `agent-save-error` / `skill-save-error` / `mcp-server-save-error`。
- 確定はフォームの末尾の `FormActionBar`（`ariaLabel`「確定の操作」）: 左に「保存 / 作成 / 導入」（primary）、その右に「変更を破棄」（secondary。変更が無いときは disabled。#808）。`PageHeader` の右端には置かない（#1786。#618 では右端だった）。複数の節を 1 つの保存で確定する画面（業務 Agent・Skill・MCP 接続・評価セット・自動実行）は保存の対象の節を包んだ最後（最後のカードの下）に置き、画面の下端に貼り付けない（#2715）。対象の操作は同じ `EntityAction[]` を一覧の行では `RowActionMenu`、エディタでは概要の `ObjectActionBar` に渡す。破壊的な操作（削除）は `useConfirm` で確認する。
- 一覧の行は、先頭セルの対象名のボタン（`RowTitleButton`）か行の操作以外の領域のクリックで開く。行の中のボタンは対象名と操作メニューの 2 つだけ。使える項目がない行のメニュー（既定の MCP サーバー）は disabled にする。
- 業務 Agent の有効 / 無効は対象の操作にし、フォームの下書きに含めない（切り替えで一覧を取り直しても、編集中の内容を上書きしない）。新規作成だけは初期状態をフォームで選ぶ。

### 1.2 B 型（一覧 + 詳細）

共通のユーザー管理・ロール管理・権限管理（`@production-ready/system-settings` の `UserManagementPage` / `RoleManagementPage` / `RolePermissionsPage`）は共有の `ListDetailLayout` の一覧 + 詳細（#2282）。選択は URL の `?user=` / `?role=`（ロール管理の詳細の「権限管理で設定」は `?role=` を付けて権限管理を開く）、先頭の行を自動で選ばない。作成・編集は今までどおり一覧に代わる 1 枚のフォーム。製品のラッパー（`frontend/src/components/security/Security*Page.tsx`）は `listDetailStoragePrefix={AGENT_LIST_DETAIL_STORAGE_PREFIX}`（`production-ready-agent.listDetail`。`EntityLayout.tsx`）を渡す。

フィードバック（`/feedback`）は共有の `ListDetailLayout`（UX 契約 page-archetypes.md §1 B。#2283）で、保存 key の前置きは `AGENT_LIST_DETAIL_STORAGE_PREFIX`（`production-ready-agent.listDetail`。`frontend/src/components/EntityLayout.tsx`）、文言は `listDetail.*`。見方の `Tabs`〔確かめるべき実行（既定。#1822）/ 利用者の評価〕→ 絞り込み（`ListToolbar` の `FilterSelect`。3 つ以上なので狭い置き場所ではシートに畳む。#1933）→ 集計のカード → 一覧 + 詳細。

| 見方 | `id` | 選択（URL） | 一覧の列（行） | 詳細の列 |
|---|---|---|---|---|
| 確かめるべき実行 | `feedback-signals` | `?signal=<run_id>` | 質問（2 行まで）+ シグナルのバッジ・実行日時。件数は列の上、ページ送りは列の下 | 業務 Agent・利用者・実行日時・状態・実行、シグナルの説明、質問・回答、評価、実行の詳細へのリンク、評価ケースに追加 |
| 利用者の評価 | `feedback-ratings` | `?feedback=<run_id>` | 質問（2 行まで）+ 本人の評価・管理者の評価・評価日時 | 業務 Agent・利用者・評価日時・理由・実行、質問・回答、本人 / 管理者の評価、管理者の評価の操作、評価ケースに追加 |

- 先頭の行を自動で選ばない（未選択の詳細は「〜を選んでください」）。詳細の上端の行の「前へ / 次へ」（`ListDetailPager`）は今のページの前後。xl 未満は 1 ペインで、左上の「一覧へ戻る」（`PageHeader` の `back`）で一覧へ戻り、選んでいた行へフォーカスを戻す。選んだ行が絞り込み・ページ送りで一覧から外れても、最後に見た内容を詳細に出したままにする（一覧の取得に 1 件の取得の API が無いので、見ていない行を URL で開くと「今の一覧にありません」）。

ツール（`/tools`。ナビには出さない）は `AgentSplitPane`（共有 `FixedSplitPane` に `storagePrefix="production-ready-agent.fixedSplitPane"` と Agent の i18n 文言）のまま。分割線の初期位置は 50%（共有部品の既定。#1572）で、xl 未満は縦積み。

| 画面 | `splitId` | 左（一覧） | 右（詳細） | 対象の操作 |
|---|---|---|---|---|
| ツール | `tools-list` | ツール一覧 | schema と監査タグ | なし |

- 行の操作以外の領域のクリックで選び、選択は行の背景と `aria-current` で示す。行の操作は `RowActionMenu`、詳細は同じ定義を `ObjectActionBar` に渡す。
- 実行の詳細の操作は `ObjectActionBar` の 1 か所だけ（#814）。操作は REST を呼び、押した操作だけを応答まで `loading` にし、ほかは `disabled`。イベントは SSE だけで購読し（方式の切り替えは持たない。#2260）、処理の経過の中の「処理の詳細」のストリームに受信の状態（`StatusBadge`）と、切れたときの停止と「再接続」（`Banner`）を出す。

### 1.3 実行履歴の全幅の導線（#875）

- `/runs` は 3 製品で共通の実行履歴の型（UX 契約 run-history.md。#1955）。`RunHistoryToolbar`（検索 → 状態 → 種類 → 期間 → 実行者の `FilterSelect`。実行者は他の人の実行が見える利用者だけ）・`RunHistoryTable`（質問 / 状態 / 種類 / 実行者 / 開始日時 / 所要時間 / token / 操作）・`OffsetPagination` の一覧。種類の既定は「品質評価以外」（`kind=not_evaluation`。品質評価の Run は「品質評価」か「すべて」で出す。件数・「条件をクリア」もこの既定が基準。#1983）。状態は共通の 7 つに写し（`lib/run-history.ts`）、承認待ち・確認待ちだけ Agent の言い方にする。見出しの「実行を作成」から `?id=new` を開く。作成フォームを一覧に重ねない。
- 一覧はサーバー側で絞り込み・ページングし（`GET /api/runs?status=&kind=&since=&executor=&q=&limit=&offset=`。`status=waiting` は承認待ち・確認待ち、`has_other_executors` で実行者の列と絞り込みを出す）、行は一覧に要る項目だけの要約（`RunSummary`）を読む。詳細は `GET /api/runs/{run_id}` で対象の実行 1 件だけを読む。全 Run を読まない（#1897）。
- 題名のリンクで `?id=<Run ID>` の全幅の詳細を開く。見出しの「一覧へ戻る」で元の検索・状態・ページを保ち、選んだ行へフォーカスを戻す。URL の再読込・戻る / 進むでも同じ対象を開く。
- 詳細はタブにせず `RunDetailLayout` の節を縦に 1 枚で並べる（#1955）: 概要（`RunSummary`。対象の操作の `ObjectActionBar`、実行中の経過時間・承認待ち・失敗の理由の Banner）→ 処理の経過（`RunTimeline`。段の名前はチャットの処理の経過と同じ。ツールの段を開くとデータの範囲・エラー・結果。回答の上。#2126。タイムラインの後ろに「処理の詳細」〔識別子・イベントの記録・ストリームの接続。既定で閉じる。#2325〕）→ 回答→ 承認 → 成果物（利用者が使う出力〔表の結果など〕の種類だけ。種類の一覧は `lib/run-artifacts.ts`、無ければ節を出さない。#2403）→ 構造化データ → 評価と改善（管理者）→ 監査ログ（権限のある利用者だけ。既定で閉じ、開いたときに取得する。ツールの記録と内部の記録〔支援タスクの状態・資料との照合など〕を共通の `RunEventLog` で 1 行ずつ並べ、行を開くと元の JSON。#2403）。
- 作成後は作った Run の詳細へ移る。URL の ID が一覧に無い場合は説明を出し、別の実行へ置換しない。

### 1.4 承認の全幅の導線（#877）

- `/approvals` は全幅のキュー。既定は「保留中」で、検索・状態・ページを作業状態に残す。題名のリンクから `?id=<Approval ID>` の全幅の詳細を開く。
- 一覧はサーバー側で絞り込み・ページングした承認の要約（`GET /api/approvals?status=&q=&limit=&offset=`）、詳細は承認の ID から承認とその実行の要約（`GET /api/approvals/{approval_id}`）を読む（#1897）。
- 詳細の対象は URL が正本で、承認の ID から解決する。判断後に保留中のキューから消えても同じ承認を表示し、判断者・日時・状態を確認できる。別の承認へ暗黙に移動しない。
- 目標・ツール・承認理由・申請日時・引数を分けて示す。判断済みには判断記録を出し、日時は JST。関連する実行への導線は実行の閲覧権限がある利用者だけに出す。
- 判断は保留中で権限を持つ利用者だけ。行メニューと詳細の `ObjectActionBar` は同じ定義を使い、確認に対象の目標・ツール・ID を含める。処理中は押した対象だけを loading にし、重複判断を抑止する。確認中に別の操作者が判断した場合は再取得済みの状態を確かめてから送る。
- 戻ると検索・状態・ページ・選択行のフォーカスを保つ。選んだ承認が保留中から消えた場合は一覧の見出しへフォーカスを戻す。対象が存在しない URL は説明し、別の対象へ置換しない。

## 2. 未保存変更の離脱ガード

共有パッケージ `@production-ready/system-settings` の `useUnsavedChangesGuard` / `useSettingsDraftGuard` を `frontend/src/lib/leave-guard.ts` で Agent の i18n 文言に包んで使う。dirty のときだけ、サイドナビ・内部リンクの移動を確認ダイアログで止め、再読込・タブを閉じる操作を `beforeunload` で止める。dirty は保存済みの基準との比較で判定し、保存に成功したら基準を更新する。

| 画面 | フック | dirty の対象 |
|---|---|---|
| 業務 Agent | `useEditorLeaveGuard` + `useDirtySources` | エディタのフォーム（スキルは集合として比較）。画面内の「一覧へ戻る」（`back`）でも破棄を確認する |
| スキル / MCP 接続 | `useEditorLeaveGuard` | 全画面エディタのフォーム（開いた時点の内容と比較）。画面内の「一覧へ戻る」でも破棄を確認する |
| 自動実行 / 評価セット | `useEditorLeaveGuard` | 全画面エディタのフォーム |
| ツール権限 | `useSettingsLeaveGuard` | 取得した設定との差分（ツール権限の「既定」は未指定として比較） |

ブラウザの戻る / 進む（`popstate`）も、data router の root（`main.tsx`）に 1 つだけ置いた共有の `UnsavedChangesBlocker` で確認する（#138 / #586）。A 型のエディタで未保存の編集があるときも、戻る / 進むで `?id=` が変わる前に破棄を確認する。

## 3. 作業状態の保持

`frontend/src/lib/workspace-state.ts` の `useWorkspaceState` が、allowlist（`WORKSPACE_FIELDS`）に登録した field だけを同じタブの `sessionStorage` に残す。namespace は `production-ready-agent.workspace.v1:`、期限は最終保存から 8 時間、1 field の JSON は 20,000 文字まで。既定値と同じ値は保存しない。読めない・型違い・期限切れの値は捨てる。

| 画面 | 保存する field | 戻ったときの検証 |
|---|---|---|

- A 型の編集対象は URL の `?id=` が唯一の情報源なので `sessionStorage` に置かない（#87 で置いた `skills.detailId` などは #137 で URL へ移した）。サイドナビから開くと一覧に戻る。
- 秘密情報（MCP の OAuth client secret / session ID 等）、確認語、サーバー応答全体、未保存の編集フォームは保存しない。編集フォームは §2 の離脱ガードで守る。
- 確認語と破壊的操作の確認は画面の state にだけ置き、ページを離れると解除される。ページに戻っただけで mutation を送り直さない。
- 実行の目標の一時保存に失敗した場合は警告を出し、離脱ガードを有効にする。
- #215 で backend は共通認証のログインに対応した（[security-rbac.md](security-rbac.md)）。画面をログインに切り替えるときは、logout とユーザーの切り替えで `clearWorkspaceState()` を呼ぶ。

## 業種テンプレート（#780）

業務 Agent の編集画面（既存の業務 Agent・変更の権限がある利用者）の見出しに「設定」と「試す」のタブを置く（#2515）。「試す」はチャットと同じ会話の部品（`AgentChat` の `tryTarget`、`ChatLayout` の `embedded`）で、保存した下書きで実行し（`POST /runs` の `draft=true`）、会話の履歴は下書きの会話だけ。未保存の変更があるあいだは送信を止め、会話の上の警告に「保存」を出す（公開と同じく、画面の入力と違う内容で試さない）。無効・移行が要る業務 Agent は理由だけを出す。タブを移ってもフォームの入力は残る。

品質評価（#2558）: 評価ケースの編集に「期待する出力」（評価する業務 Agent の出力の項目ごとの値の行。値を入れた項目だけを判定）を置く。結果は、期待する出力のあるケースがあるときだけ、概要に「出力の項目の正答率」「出力の項目がすべて正しいケース」（統計のタイルは 8 個で 2 / 4 列）、ケース別結果に「出力」の列（N / M 項目）、ケースの詳細に項目ごとの期待・記録・判定の表を出す。実行の結果から評価ケースを作るときは、記録した出力を期待する出力に入れる。出力の項目の編集では、文字の項目に「評価の比べ方」（完全に一致 / 意味が同じ。#2562）を置き、項目ごとの表の判定に「意味で判定」と判定の理由（#2568）、判定できなかった理由を出す。

業務 Agent の編集画面の「データの範囲」の下に「出力の項目」を置く（#2549）。項目ごとに表示名・key・型・必須・説明を入れ、「項目を足す」で足し、行のごみ箱で外す（並べ替えは無い）。key の形・重なり・表示名の空は保存の前に欄で知らせる。テンプレートの出力の項目はテンプレートを選ぶと入る。チャット（と「試す」）は、記録した項目を回答の下に「出力の項目」の結果の表（真偽は「はい / いいえ」、CSV のダウンロード）で出し、差し戻しても記録しなかった回答には warning の `Banner` を出す。

業務 Agent の新規作成（`/agents?id=new`）の先頭に「説明から下書きを作る」を置く（#2519）。業務の説明を `POST /api/agents/draft-suggestion` に送り、返った名前・説明・指示・スキル・データの範囲・出力の項目（#2561。決まった項目で結果を返す業務のときだけ）をフォームに入れる（入力済みなら確認してから置き換える。保存はいつもの「作成」）。評価の問いは「評価の問い（N 件）」に出し、品質評価の権限がある利用者は「作成と同時に評価セットを作る」（既定オン）で評価セットにする。提案に使えなかった候補は info の `Banner` で知らせる。

その下に「テンプレートから始める」を置く。テンプレート（`GET /api/agent-templates`。backend の `app/features/agent/templates.py`）を選ぶと、名前・説明・指示・スキルをフォームに入れる（入力済みなら確認してから置き換える）。テンプレートは業務 Agent を直接作らず、保存はいつもの「作成」で行う。使えない（登録されていない）スキルは外して知らせる。既存の業務 Agent の編集には出さない。

テンプレートを選ぶと「テンプレートの評価ケース（N 件）で評価セットを作る」（既定はオン、品質評価の権限を持つ利用者だけ）を出し、作成した後に評価セットを作る（#810）。作った業務 Agent は `template_id` を持ち、品質評価で評価セットが無ければ空の状態に「テンプレートの評価ケースで作る」を出す。

## 品質評価のフォローアップ（#810）

- **評価ケースに追加**: フィードバックの詳細（本人か管理者の評価が「役に立たなかった」。確かめるべき実行はどのシグナルでも。#1822）と実行の詳細（回答が出た実行。品質評価の実行は除く）に、`Disclosure`「評価ケースに追加」を置く（品質評価の権限を持つ利用者だけ）。開いたときに下書き（質問・管理者のコメント・呼んだツール）を取得し、読み込み中は `TimedLoadingState` + `FormSkeleton`、失敗は再試行付きの `ErrorState`。追加先の評価セットを選び（同じ質問を持たない最近の評価セットが既定。無ければ「新しい評価セットを作る」）、期待する回答の要点は必須。同じ質問を持つ評価セットを選ぶと欄の下に知らせる。成功は Toast（「評価セットを開く」）、失敗は操作の行の `FormStatus`。
- **評価する版**: 品質評価の業務 Agent の選択の横と、評価セットのエディタに「評価する版」（`SelectField`、`width="md"`）。既定は公開していない変更があれば下書き、なければ公開中の版。実行の意思なので作業状態には残さない。最近の評価の一覧に「版」の列、評価概要の説明に版、前回との比較の文に比べた版と日時を出す。
