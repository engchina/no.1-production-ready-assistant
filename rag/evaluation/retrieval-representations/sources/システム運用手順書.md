# システム運用手順書
## 1. 対象
本書は、サンプル社の受注システムと在庫システムの運用の手順を定める。
## 2. 障害対応
受注システム OrderHub で障害が起きたときは、まず監視画面で受注キューの滞留件数を確認する。滞留が500件を超えた場合は受注の受付を一時停止し、業務部へ連絡する。OrderHub の再起動は、業務部の了承があれば日中でも行える。再起動の後は、停止中に受け付けた注文の件数と、取引先へ送った確認のメールの件数が一致することを確かめる。一致しないときは、差分の注文の一覧を出力し、業務部の担当者が取引先へ個別に連絡する。OrderHub のバックアップは毎日2時に取得し、保存期間は30日とする。障害の原因が外部の決済サービスにあるときは、決済サービスの障害情報のページを確認し、復旧の見込みを業務部へ伝える。障害の記録は、発生の日時と影響を受けた注文の件数と復旧までの時間を障害記録の様式に書き、翌営業日までに情報システム部へ提出する。OrderHub の監視画面には、受注キューの滞留件数のほか、取引先ごとの受注の件数と、確認のメールの送信の失敗の件数が表示される。送信の失敗が100件を超えたときは、メールの配信サービスの状態を確認する。配信サービスが正常なときは、送信の失敗した宛先の一覧を業務部へ渡し、宛先の誤りを直してもらう。OrderHub の設定を変えるときは、変更の内容を変更管理の台帳に記録し、情報システム部の課長の確認を受ける。月末の締めの前後の3営業日は、OrderHub の設定の変更を行わない。締めの処理の途中で障害が起きたときは、締めの処理をやり直す前に、経理部へ連絡して処理の範囲を確かめる。OrderHub の利用者のアカウントは、業務部の申請にもとづいて情報システム部が発行し、異動や退職のときは1営業日の中に停止する。
続いて、在庫システム StockNavi で障害が起きたときの扱いを定める。StockNavi は倉庫の入出庫の記録を扱うため、障害の影響は出荷の遅れとして現れる。まず倉庫の現場の責任者に連絡し、手書きの出庫票で出荷を続けるかを決めてもらう。出荷を止めるときは、営業部へ出荷の遅れの見込みを伝える。
再起動は夜間の保守時間帯（22時から翌5時まで）に限る。日中に再起動が必要なときは、情報システム部長の承認を得る。再起動の後は、手書きの出庫票の内容をすべて入力し直し、入力の件数を倉庫の現場の責任者と照合する。バックアップは毎日23時に取得し、保存期間は14日とする。保存期間を過ぎたバックアップは自動で消える。障害の原因が倉庫の読み取り端末にあるときは、端末の保守業者へ連絡し、代替の端末が届くまで手書きの出庫票を使う。
