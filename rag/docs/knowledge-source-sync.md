# 知識源の同期の契約(差分・再開・削除・権限の撤回)

外部の知識源(社内の文書管理・Wiki・共有フォルダなど)を継続して取り込むときの契約と、その最小の実装
(`app.rag.source_sync`・`app.rag.source_sync_cli`)の説明。#77 の調査の判断もここに残す。

## どの対象に継続の同期が要るか

| 対象の条件 | 使う仕組み | 理由 |
|---|---|---|
| 人が選んだ文書を、必要なときに取り込む(規程の改訂を担当者が登録する) | アップロード(画面・`/api/documents/upload`)・版の登録(`superseded-by`)・有効期間 | 取込の契機が人の操作。差分は人が決める |
| まとまった数の文書を、決まった時に一括で取り込む(移行・年次の入れ替え) | 一括の取込(`/api/documents/ingestion-jobs/bulk`) | 一覧は 1 回きり。消す判断は人が確かめる |
| 知識源の側で文書が増減・更新され、**削除と閲覧権限の撤回を知識源に合わせて反映し続ける**必要がある | **知識源の同期**(この文書) | 人の操作では、消し忘れ・権限の剥奪の反映漏れ(古い根拠を返す)が起きる |

判断(#77): 外部の SaaS の connector と資格情報は今は入れない(OCI Object Storage も使わない構成で、
継続して読む知識源がまだ無い)。ただし 3 行目の条件の対象を取り込むときに守る契約は、合成の知識源
(manifest)で実装と試験まで済ませ、connector を足すときはこの契約(`SyncSource`)を実装するだけにする。

## 契約

状態を 1 つの「同期の成功」にまとめず、次を別に持つ。

| 状態 | どこに持つか | 何を表すか |
|---|---|---|
| 一覧の列挙 | 実行の状態の `run`(cursor・列挙済みの `external_id`) | どこまで一覧を読んだか。途中で止まったら続きから読む |
| item の対応 | 実行の状態の `items`(`source_id + external_id` → 文書) | 公開中の版・前の版・取込中の版・失敗した版 |
| 取込 | 製品の文書と取込 job | 取込の成否(`indexed` / `pending` / `failed`) |
| 同期の設定 | 利用者が編集する設定の JSON | 何をどの KB へ同期するか。実行の状態とは別のファイル |

1. **重複を作らない**: 取込の key は `source_id + external_id + 内容の sha256` で決まり、原本の保存先の
   path になる。同じ版の再通知・再試行・取込に出した直後に止まった同期の再開でも、同じ文書を使う。
   版(`version`)だけが変わって内容が同じなら取り込み直さない。KB ごとに文書を複製しない(1 つの文書を
   設定の KB に所属させる)。
2. **更新は前の版を残して切り替える**: 内容の更新は次の版の文書へ取り込み、取込が `indexed` になって
   から前の版を置き換え済みにする(`set_document_superseded_by`)。取込が失敗したら、前の版が公開の
   まま残り、失敗した版は消して次の同期で再試行する(`max_attempts` まで)。前の版を消してから作り直す
   方式(delete + re-create)は使わない。
3. **削除・撤回の根拠を限る**: 削除は、知識源が明示した tombstone(`deleted`)と、**最後まで列挙できた**
   一覧に無い item だけ。認証の失敗・rate limit・途中のページの失敗(`SourceListingError`)・件数の上限での
   打ち切り(`complete=false` で次のページが無い)は、削除の根拠にしない。閲覧権限の撤回
   (`visible=false`)は通常の更新の失敗と分け、公開中の版・前の版・取込中の版をすべて消す(文書の削除と
   同じ後始末)。消した文書は検索・前後の文脈・引用の本文の読み直しに出ず、古い `as_of` を指定しても
   戻らない。取込の実行中で今は消せない版は job を取り消し、次の同期で消し直す(取込が後から終わっても
   公開しない)。
4. **取りこぼさない再開**: cursor は、ページの item をすべて状態に記録してから進める。失敗した item は
   状態に残し、次の同期の最初に再試行する(cursor の先へ送って忘れない)。cursor は位置ではなく
   最後に返した `external_id`(一覧の途中で item が増減しても欠けない・重ならない)。再開の前に列挙した
   item はその同期では消さない(次に最後まで列挙した一覧の差分で消す)。
5. **同時に 1 つ**: 同じ知識源の同期は 1 つだけ(状態のファイルの lock。2 つ目は終了コード 3)。
6. **設定と実行の状態を分ける**: 設定の JSON は利用者だけが、状態の JSON は同期だけが書く。設定の
   内容が変わったら、途中の一覧は捨てて最初から列挙し直す(item の対応は残す)。
7. **公開の記録は件数だけ**: 結果は件数(追加・更新・変わらず・削除・撤回・公開・失敗・再試行・未反映)、
   検知から公開までの最大の遅れ、未反映の最古の経過、失敗の種類(例外の型名)だけ。本文・ファイルの
   中身・資格情報は状態にも結果にも書かない。

責務の分担は変えない: 取込(解析・分割・埋め込み)は文書レシピ、検索の範囲は KB の所属と検索・回答
プロファイル。取込の設定を KB や同期の設定に持たせない。

## 使い方(合成の知識源 = manifest)

```bash
cd rag/backend
cp ../examples/source-sync/manuals.sync.example.json /tmp/manuals.sync.json
# knowledge_base_ids を同期先の KB の ID に、manifest を ../examples/source-sync/manifest.json の絶対 path にする
uv run python -m app.rag.source_sync_cli --config /tmp/manuals.sync.json
```

- 文書は既定の処理レシピで取り込む。既定の文書解析が Docling(`RAG_PARSER_ADAPTER_BACKEND=docling`)だと
  `.txt` は受け付けず、結果の `errors` に `parser_unsupported` が出て item は `failed` になる(文書は残さない)。
  例の `.txt` で試すときは既定の文書解析を Unstructured にするか、PDF を置く。
- 取込 job は取込 worker が処理する(worker を動かしておく)。1 回目の同期は文書を作って取込に出し
  (`added`)、取込が済んだ後の同期で公開する(`published`)。定期に流すなら cron / systemd timer で
  同じ command を実行する。
- 終了コード: `succeeded` 0・`partial`(取込中・失敗・消し直し待ちが残る、または一覧が打ち切られた)1・
  `listing_failed` 2・同期が実行中 3・設定を読めない 4。

manifest の形:

```json
{
  "items": [
    {"external_id": "rules/kinmu", "path": "kinmu.txt", "version": "2025-04-01", "visible": true}
  ],
  "deleted": ["rules/old"]
}
```

`version` を省くと内容の sha256 を版にする。`visible: false` は閲覧権限の撤回、`deleted` は tombstone。

### 講義での見せ方(lesson03「知識ベースは育つ」の増分更新・版・失効)

1. 上の command を 2 回流す(1 回目 `added: 2`、取込の後の 2 回目 `published: 2`)。もう 1 回流すと
   `unchanged: 2` で文書が増えない(同じ内容の再通知)。
2. `kinmu.txt` の本文を変えて流す → `updated: 1`。取込が済むまで、検索は前の版を返す。済んだ後の同期で
   前の版が「置き換え済み」になる(文書の画面の版の表示)。
3. manifest の `kinmu` に `"visible": false` を足して流す → `revoked: 1`。前の版も含めて文書が消える。
4. manifest の JSON を壊して流す → `listing_failed`(終了コード 2)で、何も消さない。

## 検証

- 決定論のテスト `tests/test_source_sync.py`(合成の知識源と取込先の fake): 追加 / 同じ内容の再通知 /
  版だけの変更 / 内容の更新(取込中は前の版が公開) / 更新の失敗(前の版が残る・再試行・上限) /
  tombstone / 一覧の差分の削除 / 一覧の途中の失敗・打ち切り(消さない) / 再開(欠落・二重の取込なし) /
  取込に出した直後の停止からの再開(同じ文書) / 撤回(取込中の版も公開しない・権限が戻ったら取り込む) /
  消せない版の消し直し / 取込先が受け付けない item(理由つきの失敗) / 同時の起動 / 設定の変更 /
  遅れの計測と状態に本文を書かないこと / manifest の
  ページ・tombstone・非公開・読めない manifest と外の path。
- 実 Oracle のテスト `tests/test_source_sync_oracle.py`(`ProductSyncTarget`。取込 worker の代わりに job と
  文書の状態を進める): KB への所属・待機中の job・公開・前の版の置き換え・撤回での削除・待機中の job の
  取り消しと消し直し。
- 未確認(実サービス): 取込 worker が実際に解析・埋め込みまで進める経路を通した同期は、テストでは
  通していない(worker の代わりに状態を進めた)。外部の SaaS の connector は無い。

## 既知の制約

- 実行の状態は 1 つの JSON ファイル(同じ host で動かす CLI 用)。複数の host から同じ知識源を同期する
  ときは、同じ契約で DB に置く必要がある。
- 公開の切り替えは「新しい版が `INDEXED` になった後の同期」で行う。その間(次の同期まで)は、検索に
  前の版と新しい版の両方が出ることがある(どちらかの根拠が欠けることは無い)。同期の間隔を短くするか、
  取込 worker の完了で同期を起動すると短くなる。
- 利用者が画面で同期の文書を消したときは、同期の状態は気づかない(次の内容の更新・撤回のときに
  消し直しの対象から外れるだけ)。
