- 時間の大半はモデル（LLM）の呼び出し。1 問で 3〜5 回呼び、1 回は 8〜20 秒かかる。検索（Oracle AI Vector Search と

## #1218 の判断（2026-10-07）

計測の結果、今の待ち時間（1 問 50〜80 秒）の大半はモデルの呼び出しの回数と 1 回の時間で決まる。引き継ぎの提案のうち、
モデルの呼び出しを増やす仕組みは、精度の向上を評価で示せるまで入れない。

| 項目 | 判断 | 理由 |
|---|---|---|
| 根拠の MCP（evidence・`rag_read_source`） | 実施済み（#1219） | 呼び出しを増やさずに根拠の場所・版を渡せる |
| Excel の前処理（表頭・行とセルの場所・手順書） | 実施済み（#1221 / #1224） | 取込の質の改善で、回答の時間を増やさない |
| 評価の分類と内訳・工程ごとの計測 | 実施済み（#1226） | 以降の判断の材料 |
| 軽量の業務ガイド（適用条件・必要な証拠・引き継ぎの条件） | 今は入れない | 顧客の業務の内容（リポジトリの外）が要り、効果を示す評価のデータがまだ無い。分類付きの評価セットで「条件の確認が要る」質問の失敗が多いと分かったら再検討する |
| 覆域の行列と欠けた所だけの再検索 | 今は入れない | 再検索と判定でモデルの呼び出しが増える。修復の round（上の 2 回目）がすでにあり、その回数・効果を先に評価で見る |
| 回答の構造化と共通の最終検証（Agent の出力も） | 今は入れない | 監査（根拠確認）はすでに回答フローの中にある。Agent の出力に別の LLM の検証を足すと 1 問 20 秒前後増える |
| Agent の支援タスクの状態（Run をまたぐ確認） | 今は入れない | 「現場のデータが要る」「条件の確認が要る」分類の評価で必要性を示してから |

### D の対応の正しさは、Agent の経路の実力より低く出ている

D の対応（outcome）は、その Run の最後の `rag_search` の `outcome` から取る（README「A / C / D を比べる」）。ところが業務
Agent が `rag_search` を呼んだ Run は 22 件中 5 件だけで、ほかは `rag_retrieve_evidence`（根拠だけを集める）や
`rag_lookup_guides`（業務ガイド）の後に Agent のモデルが自分で答えた。19 問のうち 15 問は、回答の文からの推定
（`outcome_source=inferred`。最後の行が問いなら確認の質問、拒答の文なら拒答、それ以外は回答）で採点した。推定は次の
回答を取り違えた（回答の本文は Agent の API から取って確かめた）。

| ケース | D の回答 | 推定 | 取り違えの理由 |
|---|---|---|---|
| `cr-grant-permission`・`mt-grant-permission-individual`（1 回目） | 付与先（個別 / グループ）を確かめる質問 | 根拠不足 | 最終の検証が根拠の無い回答の末尾に「この回答は資料の根拠を使っておらず…」を足し、最後の行が問いでなくなる |
| `ed-error-e1023-cause`・`mt-e1023-token-expired`（1 回目） | 原因 2 つと、認証ログで見分ける方法 | 回答 | 推定は「現場のデータが要る」「条件付き」を表せない |
| `ed-current-session-timeout`・`ed-last-month-total` | 資料からは今の設定値・合計の正否は確かめられない | 回答 | 同上 |
| `km-license-fee` | 最終の検証が「記載は見つからなかった」の文を根拠で確かめられないとして外し、「根拠で確かめられた内容はありませんでした」だけになった | 回答 | 拒答の文と判定されない |

この 7 問（往復の 1 回目を含む）は、人が回答を読むと期待する対応に合っている。人の判定で数え直すと 18 / 19（0.95）

経路の対応の正しさは比べられない。D の対応を A / C と比べるには、Agent の回答が対応を持つ（`rag_search` を最後に必ず呼ぶ、
または Agent の成果物 `answer` に outcome を載せる）必要がある（#1305）。

### 読み取れること

- **C は A より対応の正しさが上がった（0.79 → 0.84）。** 確認が要る質問（`cr-grant-permission`・`cr-delete-account`・
  往復の 1 回目）は、C では回答を作らずに確認の質問を 0 秒で返した。往復の `mt-grant-permission-individual` は、返答

  で、差は dev（0.75 → 0.83）に出た。業務ガイドの効果は dev の質問で見ているので、holdout で差が出ていない点は割り引いて
  読む。
- **往復のあるケースは、返答の後の回答が弱い。** A は 3 問とも返答の後が根拠不足（正解の文書が検索に出ない
  `retrieval_miss`）。C も `mt-delete-account-approved`・`mt-e1023-token-expired` の返答の後は根拠不足だった。返答の文
  （「所属部署の部門長の承認はもらっています。」など）だけでは根拠が取れず、前の往復が検索の文にどう反映されたかは
  未確認。検索の文の確定（会話の履歴の使い方）を調べる必要がある。
- **C の holdout の条件への言及は 0.25 と低い。** `cr-delete-account` の確認の質問は承認だけを聞き、削除の取り消しの
  条件（「復元」）に触れない。`cs-closing-day` は条件の語「第2版」が回答に無かった。`ed-current-session-timeout` は
  A / C とも「既定値」に触れなかった。確認の質問を回答の生成なしで返す（#1238）と、資料の条件の文が回答に入らない。
- **C で悪くなった 1 問**: `km-license-fee`（資料に無いライセンス費用）を C は「現場のデータが要る」と返した（A は根拠
  不足で正しい）。業務ガイドの影響か、モデルの判断の揺れかは未確認（この質問に当たる業務ガイドは無い）。
- **D は手順と条件への言及が最も高く（0.72 / 0.85）、時間は半分（中央値 21 秒）。** `rag_search`（回答フロー。1 回 50〜
  110 秒）を呼ばず、`rag_retrieve_evidence` の根拠から Agent のモデルが答えたため。確認の質問は 3 秒で返した。一方、
  回答フローの監査・回答の記録（outcome）を通らないので、上の推定の問題が出る。業務ガイドの条件は確認できたが、
  `mt-delete-account-approved` の返答の後は、`rag_search` に承認の条件を渡さずに呼び、承認を聞き直す結果を受け取った
  （`known_condition_reasked`。回答の本文は手順を示した）。
- **D の最終の検証が回答を読みにくくする。** 出典の行・手順の見出し・利用者への質問の文も「確かめが終わっていない」
  として「確かめられていない点」に並ぶ（例: `da-trial-account-expiry`・`cr-delete-account`）。資料に答えが無い質問
  （`km-*`）では、「記載が見つからなかった」という正しい文まで根拠で確かめられないとして外し、「根拠で確かめられた
  内容はありませんでした」と理由の列だけが残る。拒答・見出し・出典の文を検証の対象から外す必要がある（#1306）。
- 危険な回答（勧めると危険な表現）は 3 経路とも 0 件。
- `ed-error-e1023-cause` は、A は回答の記録の対応が「回答」で不正解、C は「現場のデータが要る」で正解になった。この
  質問の業務ガイドは無いので、モデルの判断の揺れと考える（15 問のときの比較と同じ。A / C の回答の本文は未確認）。D の
  回答は原因 2 つと見分け方（認証ログ）を示した。

### 結論（handoff §14.3）

- 業務ガイド（C）は、確認が要る・現場のデータが要る質問の対応を上げ（0.60 → 0.80、0.50 → 0.75）、時間も短くした。
  条件への言及（特に holdout）と往復の返答の後の回答は課題が残る。
- Agent の経路（D）が固定の RAG（A / C）より良いことは、この評価ではまだ示せていない。手順・条件・時間は D が良いが、
  対応の正しさは採点の推定の限界で比べられず、`rag_search` を呼ばない経路が回答フローの監査と outcome を迂回する。
  D を比べ直す前に、(1) スキルの指示のツール名（#1303）、(2) Agent の回答の対応を推定に頼らずに得る仕組み（#1305）、
  (3) 最終の検証が拒答・見出し・出典の文を外す扱い（#1306）、を直す。
