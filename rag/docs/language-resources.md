# 言語資源（書き方パック）の設計

RAG が文書と質問を読むときの「言語の書き方」（数・単位・記号・助詞・参照の書き方・止め語など）を、コードから**データ**へ移す設計。

## 1. 目的と方針

- **コードには仕組み（アルゴリズム）だけを書き、言語の書き方はデータに持つ。** 漢数字の値・章や条の単位・元号・文末の記号・参照の手がかりの語・止め語などを、コードの定数や正規表現の中に書かない。
- **今までのテストで得た書き方は捨てない。** 今のコードの値を、そのまま既定の言語資源（組み込みのパック）のデータにする。既定のままなら挙動は変わらない。
- **1 つの正本にまとめる。** 同じ書き方（漢数字・単位・文末など）を各モジュールが別々に持たず、すべて言語資源から読む（今は漢数字の文字の集合だけで約 10 か所、中身もずれている）。
- **変えられる範囲を分ける。** 全体の公開版を基に、検索・回答プロファイルでは検索・回答専用の項目だけを上書きする。ナレッジベースは対象範囲であり、取込の言語資源を上書きしない。
- **変えたことの影響を確かめてから使う。** 試しの文での確認、再分割が要る文書の表示、評価の実行で確かめられるようにする。

### 業界の一般的なやり方との対応

| やり方 | 例 | この設計 |
|---|---|---|
| 言語の書き方をコードから分けたデータにする | spaCy の言語データ、Lucene / Elasticsearch の analyzer の止め語・同義語のファイル、ICU / CLDR のロケールのデータ | 言語資源のパック（JSON。スキーマで検証） |
| 既定のデータを製品に同梱し、利用者が上書きする | Elasticsearch の既定の analyzer と index ごとの設定 | 組み込みのパック → 全体 → 文書レシピ（取込）・プロファイル（検索・回答）の重ね合わせ |
| 正規表現をそのまま利用者に書かせない | analyzer の設定は語の一覧と決まった型 | 語の一覧と型（`第N条`、`YYYY年度`、`一=1`）だけを受け付ける |
| 設定の変更を評価で確かめる | 検索の関連度の調整は評価セットで比べてから反映する | 試しの文の確認・再分割の対象の表示・品質評価の実行 |
| 業務の語と言語の書き方を分ける | 同義語の辞書と言語の analyzer は別 | 業務の語は既存の「用語・同義語 / ドメインキーワード / 回答ルール / 業務ガイド」、言語の書き方は言語資源 |

## 2. 何を言語資源にし、何をしないか

| 種類 | 例 | 置き場所 |
|---|---|---|
| 言語の書き方 | 漢数字の値、章・節・条・項・号の単位、元号、文末・読点・括弧、助詞、参照の手がかりの語、止め語・一般語、英語の参照の書き方 | **言語資源** |
| 文書の種類ごとの書き方 | 見出しの階層の規則、XML ツリー JSON の引用の単位、定型文（著作権・社外秘など） | **言語資源**（後で文書の種類ごとのプリセットに分ける） |
| 業務の語 | 業務の用語・同義語、ドメインキーワード、回答ルール、業務ガイド | 既存の実行時の知識（変えない） |
| LLM への指示 | プロンプト | 既存のプロンプトの管理（変えない） |
| 保存済みのデータの形 | 条の鍵「7の2」、chunk の metadata の項目名 | コードの定数（データの契約。変えると保存済みのデータを読めなくなる） |
| 製品をまたぐ契約の語 | 回答の段落の分け方（文の区切り・見出し・導入と結びの文・出典の行・作業の経過の文）。RAG の `operation_audit` と Agent の `answer_passages` が同じ規則で、`platform/contracts/answer-passages` の事例で確かめる | RAG と Agent が読む共有の語彙 `platform/contracts/answer-passages/vocabulary.json`（#2197。規則の形は両方のコードと共有の事例。RAG の言語資源だけで変えると Agent と規則がずれるので、言語資源には入れない） |
| 製品の画面・評価のテンプレートの語 | 画面の文言、評価の Excel のテンプレートの見出し・書き方・案内の文 | 画面の i18n（言語資源にしない） |
| 安全の検査 | プロンプトの注入の検出、機微情報のマスク | コード（言語の書き方の設定で弱められないようにする） |
| システムが書いて読み戻す形 | 処理の段の名前（「（2回目）」「終了（…）」）、監査の理由（「監査: …」）、要求の単位の文 | コード（内部の形の契約） |
| 文字の種類と記号の事実 | 語の切り出しに使うひらがな・カタカナ・漢字の Unicode の範囲、ページ番号の列の区切り、ファイル名・ID・キー（F1〜F12）・ページ（p.）の英字の型 | コード（検索の質問の語の範囲は `search_terms` で変えられる） |
| 検索の文の見出し | `引用:` `数:` `参照先:` など（全文検索と埋め込みに入る） | **言語資源**（変えたら再分割・再索引が要る、と画面に出す） |

## 3. 構成

### 3.1 モジュール `rag_parser_core.language`

- 共有の契約のパッケージ `rag_parser_core` の中に置く（backend・`rag_pipeline_core`・解析と分割のサービスがすでに依存している。新しいパッケージにすると 17 の `pyproject.toml` と lock と CI を足すことになるため）。`rag_engine` は段 1b で `rag_parser_core` に依存させる。依存は Python の標準ライブラリだけ。
- 中身:
  - **項目の定義**（`FIELD_SPECS`）: 節（`numbers`・`symbols`・`references`・`titles`・`english`。段ごとに足す）と項目と種類（`FieldKind`: 語の一覧・2 文字の組・型・「字=数」・「語=値」・「語=決まった値」・文字の範囲・選択）。値は持たない。
  - **組み込みのパック**（`rag_parser_core/language/packs/ja.json`。パッケージのデータ）: 今のコードの値。
  - **重ね合わせ**（`resolve(base, *overrides)`）: 上書きは項目ごとに「継承 / 置き換え」。
  - **検証と hash**（`build_pack`）: 種類ごとに形を確かめ、内容の hash を付ける。正規表現の組み立ては使う側が hash ごとに cache する（例: `reference_grammar.current_grammar`）。
  - **今の言語資源**（`current_pack()` / `bind_pack(pack)`。`contextvars`）: 取込の job・回答の要求の間だけ束ねる。束ねていなければ組み込みのパック。
- 数の読み方（漢数字・位取り）、単位の正規表現、文末の判定などの**関数**は `rag_parser_core.language` に 1 つだけ置き、各モジュールの重複を消す（段 1b）。
  - ローマ数字（`numbers.roman_digits`。`parse_roman` / `format_roman`。標準の書き方だけを読む）も同じ場所に置き、頁番号のフッターの論理頁と柱の繰り返しの判定が漢数字と一緒に使う（#2289。[rag-engine.md](./rag-engine.md)「頁番号のフッターの論理頁」）。

### 3.2 保存と重ね合わせ

| 層 | 保存先 | 画面 |
|---|---|---|
| 組み込み | `rag_parser_core/language/packs/ja.json`（読み取り専用） | 「既定に戻す」の値 |
| 全体 | Oracle の変更できない公開版（実効値の完全な snapshot）・現在版の参照・編集用の草稿 | 取込・検索・回答設定 >「言語資源」（権限 `menu.settings_language_pack`） |
| 文書レシピ | 文書の処理レシピ（取込の節だけ。3 層モデルで取込の設定は文書レシピが持ち、KB は純スコープなので持たない） | 文書のレシピ（後の段階） |
| 検索・回答プロファイル | プロファイルの設定の `language_pack`（検索・回答の項目 = `ingest=False` だけ。取込の項目は文書の分割と食い違うので持てない） | 検索・回答プロファイルの「質問の理解」と、他用途の「言語資源の上書き」。全体の公開中の値へ重ね、会話の準備・確認・検索・回答の要求範囲で `bind_pack`（[契約](./question-understanding.md)） |

- 初回の移行時だけ既存のローカル設定を読み取り、公開版の完全な snapshot を Oracle に作る。元のファイルは変更・削除しない。以後の公開・草稿・履歴の正本は Oracle とし、ローカルファイルへ書き戻さない。
- 環境変数（`RAG_REFERENCE_*`）には持たない。#2157〜#2179 で足した `rag_reference_*` の設定は言語資源へ移し、消す（未リリースのため互換は持たない）。

### 3.3 実行のときの渡し方

- backend の中: 取込の job と回答の要求の初めに、その文書レシピ・プロファイルで重ね合わせた言語資源を `bind_pack` する。各モジュールは `current_pack()` から組み立て済みのものを読む。
- 解析・分割のサービス（別のプロセス）: 要求に言語資源（重ね合わせ済み）の JSON を付けて送り、サービスはその要求の間 `bind_pack` する。付いていなければ組み込みのパック。
- 取込の受付時に公開版 ID と完全な実効値を固定する。待機中に現在版が変わっても、その job の使用版は変えない。chunk set / artifact と job に実際の使用版・取込 hash を残す。実際の版を記録していない旧 artifact は「版未記録」とし、現在版を後付けしない。
- レシピごとの検索中の索引と、作成中の索引の対象版を分けて表示する。再処理が成功した場合だけ検索中の索引を切り替え、失敗・停止時は既存の索引を維持する。

### 3.4 草稿・公開と変更の確かめ方

- **草稿**: 編集と保存は公開中の動作を変えない。草稿の revision を照合して保存し、競合した古い草稿を新しい revision で自動再送しない。再読み込みは編集中の変更を破棄することを確認して行う。
- **試す**: `POST /api/settings/language-pack/preview` は公開中の値と編集中の値を比較する。保存・公開・モデル呼び出しは行わない。
- **公開**: 保存した草稿と現在版の差分・影響工程を確認し、草稿 revision と現在版 ID が一致する場合だけ新しい完全な公開版を作って現在版を切り替える。公開だけでは既存文書を再処理しない。
- **履歴**: `GET /api/settings/language-pack/releases` で公開版をページ単位に読む。公開版の値は読み取り専用で、既定値に戻す操作や過去版への復元も新しい公開版として残す。公開版は 5 件・50 件などの件数で間引かず、参照中の版を保持する。復元は現在版から復元対象への差分を確認し、草稿 revision・現在版 ID の一致を条件に行う。
- **文書との関係**: 実際の使用版が現在版と同じなら「現在版」、版 ID が違っても取込 hash が同じなら「取込内容は同じ」、取込 hash が違えば「差分あり」、使用版の記録がなければ「版未記録」とする。差分の件数と版未記録の件数は分け、現在版 ID に固定した一覧へ移動する。
- **影響工程**: 差分の項目が依存する実際の工程を示す。解析で使う項目は EXTRACT 以降、分割で使う問い合わせの項目は CHUNK 以降、分割済みの内容から作る実体索引の項目は INDEX が対象となる。未分類の項目は確認が必要と表示し、一律に再分割と決めない。
- **再処理**: 文書詳細で使用版から現在版への差分を読み、実在するレシピと開始工程を選ぶ。一括操作でも対象文書の実在する各レシピを確認・選択し、対象版 ID とレシピの設定 revision を固定して送る。既定レシピへの暗黙の置き換えはしない。競合・受付不可は対象ごとに残し、新しい版で自動再試行しない。
- **評価**: 検索・回答専用の言語資源はプロファイルの上書きで比較できる。取込の項目を変える比較では対象文書を適切な工程から再処理したうえで、同じ評価の質問を使う。

### 3.5 データから候補を出す（後の段階）

- 止め語・一般語の候補を、索引の語の出現の割合（文書頻度）から出し、管理者が選んで足す。言語資源は「決めた語」、統計は「候補」に分ける。

## 5. 守ること

- 言語資源の項目は語の一覧か決まった型だけ（正規表現を書かせない。ReDoS と壊れやすさを避ける）。型の記号（`N`・`YYYY` など）は項目の説明に書く。
- 解析の関数は 1 回の取込で何万回も呼ばれる。組み立ては内容の hash で cache し、`current_pack()` は束ねたものを返すだけにする（設定のファイルを毎回読まない）。
- 業務の内容（顧客・制度・文書の名前）を組み込みのパックに入れない（repo は public）。

## 6. 必要になったら足すもの

段 6 の検討で、今は作らないと決めたもの（使う場面が具体的に出てから作る）。

- **文書レシピの層（取込の項目の上書き）**: 取込の項目は全体の言語資源で足りている。文書ごとに書き方が違う資料群が出たら、3 層モデルどおり文書レシピに持たせ、取込の job の間だけ束ねる。
- **データからの候補**: 取り込んだ文書から、言語資源に無い単位・略称・見出しの語の候補を出す。誤った候補を採ると回答が崩れるので、評価の仕組みと組で作る。
- **文書の種類ごとのプリセット**: 法令・業務の手引き・Q&A などの文書の種類ごとの言語資源の組。文書レシピの層と一緒に作る。
