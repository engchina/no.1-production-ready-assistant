# rag_poc から移植した機能のガイド（回答フロー・親子階層・Docling 解析）

sibling repo `../rag_poc` の、解析から回答生成までの実装を本リポジトリへ移植した機能の使い方と設定をまとめる。

> 用語: 画面と本書では、回答フロー・親子階層（small-to-big）・回答の記録など RAG の標準の用語で呼ぶ（#598）。コードの識別子・設定・API・DB の名前も、#599 で rag_poc から移したときの名前から RAG の標準の名前にした（旧名と新しい名前の対照は [deployment.md の「既存環境の更新手順（#599）」](./deployment.md)）。

- Gradio UI は移植していない。
- 回答は #594 でこの回答フロー（`AnswerEngine`）だけにした（回答エンジンの選択は削除。標準の回答フローのコード・画面・設定は #595 で削除した）。文書分割の既定も親子階層（`small_to_big`）にした。既存環境の更新手順は [deployment.md の「既存環境の更新手順（#594）」](./deployment.md#既存環境の更新手順594-回答の方式を-1-つにする) と「既存環境の更新手順（#595）」。
- 解析・分割の rag_poc の処理は選択肢として追加している（解析の既定は Docling）。

## 実体・別名索引と文書構造索引

| 設定画面 | ページ内の構築設定 | 記録する関連 | 検索方法の全体設定 |
| --- | --- | --- | --- |
| 実体・別名索引 | 実体・別名索引の構築 | 文書中の対象（実体）の名称・ID・別名、属性と原文の断片 | 実体・別名による検索拡張 |
| 文書構造索引 | 文書構造索引の構築 | 文書と章・節・表・図の見出し、および原文の断片 | 文書構造による検索拡張 |

両者とも構築と検索利用は別に設定し、既定は OFF。構築の既定は文書レシピで上書きできるが、
検索利用は全体設定だけで決め、検索・回答プロファイルでは上書きしない。実体側は同じ対象の定義と
属性を介する 1 段の根拠を補い、構造側は同じ狭い章節・表・図と質問の見出し語から根拠を補う。
併用でき、構造側は候補・文脈・参照先・実体側ですでに追加した断片を除外する。
どちらも追加の LLM 呼び出しは行わないが、検索の読み取りと候補数は増える。

名称の変更自体にデータ移行や再構築は不要。構築する設定を変えて既存文書に反映するときは、
文書の処理レシピを再処理する（実体・別名索引は索引の工程から）。API path・設定 key・保存値は変更しない。

## 回答の監査と最終の資料との照合

引用の原文との一致、主張の裏付け、適用条件、要求の充足、監査の実行状態を別々に記録する。
近似一致で見つけた引用は参照先の候補であり、それだけで主張を確認済みにしない。監査が支持した
原文の引用を実際の出典で照合してから採用する。語の有無や重なりでは、主張の支持や要求の充足を決めない。
表の行・列の結び付け、引用 ID、原文の引用範囲などの構造の検査は継続する。
手順の説明が案内したボタン名（「実行ボタン」の「実行」）が、説明が引いたどの原文（本文と見出し）にも無いときは、
本文・出典を変えずにその段落だけに警告（`item_check`）を付ける。名前が原文にあっても、その操作を原文が支えるかは判定しない。

生成の監査では、適用性が `unknown` / `not_applicable` でも、その判定だけで一般の説明を落とさない。
元の適用性は変更せず、本文へ反映しなかった方針と理由を別に記録する。`matched` に読み替えるものではない。
主張と根拠の矛盾は別に判定し、矛盾した主張は取り除く。最終の資料との照合は、現在の権限で根拠を
読み直し、実際に表示・保存する回答全体を検査する。実行失敗・時間上限・未実行・一部未確認は、内容の誤りと区別する。

過去の監査は、検査が完了し合格した記録について、質問・回答全体・前提・実データ・ガイドの版・根拠と
その版・モデル・プロンプト・判定方針の digest が一致したときだけ再利用する。段落間の依存が分からない
変更は回答全体を再監査する。版の無い旧記録も再監査する。生成時の監査は `generation_review`、最終の
資料との照合は `answer_validation` に分け、最終検査の再利用条件は後者の `reuse_context` に保存する。
最終照合は原質問と実際の確認回答を受け取り、設定文・仮定を利用者の事実にしない。履歴の確認回答は既存の質問補完が今回に適用する ID だけを選び、署名した質問文脈と結び付ける。生成と最終照合は同じ確認回答を使う。新しい明示回答・スキップ・不明な参照では古い確認を流用しない。上限を超えた前提を黙って切り捨てて確認済みにしない。

## 構成

| 置き場所 | 内容 |
|---|---|
| `packages/rag_engine` | rag_poc の解析・分割・検索・回答の実装を、`entrypoints`（Gradio / HTTP）を除いてそのまま移したもの。package と import パスは `rag_engine`（#599）。backend と docling サービスが依存する。回帰テストは CI の `RAG / Engine` ジョブで実行する |
| `services/parsers/docling` | rag_poc から移した Docling 解析（読み順・段組補正、表セル補修、図内 OCR の集約）。`parser_artifacts.layout_records` に LayoutRecord を保持する。Vision は行わない（#497） |
| `backend/app/rag/vision.py` | 解析後の図・画像の読み取り（Vision）。Docling を含む全ての解析エンジンで、rag_engine の `describe_layout_pictures`（対象と周辺文脈の 2 枚の画像・装飾画像の skip・表内画像の検出・prompt の metadata）を既定の Vision モデルで実行する。`layout_records` の record がある文書（Docling）は、その record を入力にし、結果を record にも書き戻す（#497） |
| `backend/app/rag/chunking_small_to_big.py` | チャンク戦略 `small_to_big`（画面の表示名は「親子階層（small-to-big）」。rag_poc の Small-to-Big 親子分割） |
| `backend/app/rag/answer_engine.py` | 回答フロー（rag_poc の回答フローを backend の検索・rerank で駆動。#594 から回答はこれだけ） |
| `backend/app/rag/search_answer_profile_knowledge.py` | 検索・回答プロファイル単位の知識（Approved FAQ / 用語・同義語 / ドメインキーワード / 回答ルール） |
| `backend/app/rag/document_crop.py` | 解析に使ったファイルからの bbox の切り出し（プレビューと回答画像で共用） |

LLM と VLM は、プロジェクト全体で openai SDK（OCI OpenAI 互換の Responses API）だけを使う。接続先はモデル設定（`OCI_ENTERPRISE_AI_*`）。embedding と rerank は Cohere（OCI SDK）のままである。

KB（ナレッジベース）は検索対象の範囲を決めるだけで、上記のどれも持たない。

編集したプロンプトは `rag_answer_prompts` に保存する（#599 で旧名の表から改名した。migration `20260930_008_answer_prompts_table`）。回答では rag_engine の runtime の `prompt_overrides` で渡し、解析では backend の Vision の段（`app/rag/vision.py`）が読み取りの指示として使う（#497 以前は docling サービスへ `parser_options` で渡していた）。未編集なら rag_poc と同じコードの既定値を使う。画像の読み取りプロンプトの変更は、解析済みの文書には再解析するまで反映しない。

分類フィルタと有効期間は rag_poc の `_classification_filter_sql` と同じ意味で絞り込む。分類は指定した項目だけを比べる。保存・検索の入力の両方で表記をそろえ（NFKC・前後の空白・連続する空白。`app/schemas/classification.py` の `normalize_category_value`）、比較は先頭の番号の接頭辞（`10_` など）を除いた名前で行う（rag_engine の `_category_label` と同じ。保存値の接頭辞は残す。#547）。文書詳細の分類と RAG 検索の分類の絞り込みは、「文書の分類」の画面で作る一覧（`rag_document_categories`。大分類 → 中分類 → 小分類の 3 段・並び順。#2131）から選ぶ（中分類は選んだ大分類の下、小分類は選んだ中分類の下から選ぶ。どれも任意で、上の段を変えると下の段は「指定なし」に戻る）。一覧に無い保存済みの値（一覧を作る前に保存した値）も今の値として選べる。一覧の分類の名前は保存と同じ正規化を通し、同じ親の下で番号の接頭辞を除いた名前が同じ分類は作れない。名前を変えると、その分類を使っている文書（祖先と自分の名前が `category_label` で一致する文書）の分類の値も同じ transaction で変える。下に分類がある分類・文書が使っている分類は削除できない（件数を返す）。一覧は利用者・tenant で分けない。既存の文書の分類の表記は `uv run python -m app.rag.classification_normalization --dry-run` で件数を確かめ、Oracle のバックアップ後に `--apply` でそろえる。アップロードはファイル名だけを送り、フォルダの相対パスを持たないため、rag_poc のパスからの分類の推定は移していない。有効期間は検索の基準日（未指定なら共通の設定 `PLATFORM_TIMEZONE`〔既定 UTC〕の今日。OS の時間帯は使わない。#3249）で常に絞り、期間のない文書は除外しない。終了日は排他的（`effective_to` の当日は期間外）。基準日は 1 回の検索・回答の初めに 1 回だけ決める（#2602）。文書・chunk を ID で読む入口（MCP の `rag_read_source` / `rag_outline` / `rag_read_document` / `rag_read_section`、回答の検証）は有効期間で絞らない（過去の基準日の検索で返った根拠を、続く呼び出しで今日の日付で読めなくしない。tenant・認可の範囲・INDEXED・有効な chunk_set の条件は同じ。#3249）。分類と有効期間は文書単位で、レシピを切り替えても変わらない。

文書の版（#1248）: 文書詳細の「版」で、その文書を置き換えた新しい版の文書を選ぶと、その文書は旧版（`rag_documents.superseded_by_document_id` / `superseded_at`）になる。置き換えの記録は文書の属性で、KB の membership・レシピは変えない。旧版の chunk は、既定では回答の検索（`rag_search`・チャット・RAG 検索）の対象から外す（`_oracle_retrieval_where` の `d.superseded_by_document_id IS NULL`）。旧版・変更点を尋ねるときは `filters` の `include_superseded=true`（MCP は引数 `include_superseded: true`。#1392）で含め、その根拠の出典の文書名に「（旧版）」を付ける（MCP の根拠は `superseded: true`）。MCP の `rag_search` / `rag_retrieve_evidence` は、旧版を含めずに検索したとき、当たった今の版の文書の旧版を `older_versions`（文書名と先頭の見出しのタイトル。`OracleClient.retrieval_older_versions` が旧版を含めた検索と同じ範囲の中から引く）で返す（#1405）。`document_id` で文書を名指しする経路（文書の chunk 数・根拠の前後の補完）と MCP の `rag_read_source` は旧版も読む。自分自身・循環（A→B→A）・見えない文書は新しい版にできない（422）。新しい版の文書を削除すると、旧版は今有効な版に戻る。

回答の業務の絞り込み（#545 / #546 / #553）: 業務の範囲の正本は検索・回答プロファイル・ナレッジベース（検索範囲）で、その中で質問が大分類の名前を含むときだけ、さらにその業務の候補に絞る。大分類の語の一覧は、検索範囲（`filters` と同じ条件）の文書に保存済みの大分類の DISTINCT（`OracleClient.retrieval_large_categories`）で、1 回の回答で 1 回だけ読む。質問との比較は #547 の正規化（NFKC・空白・番号の接頭辞を外す `category_label`）と大文字・小文字の違いを無視して行い、長い名前から照合する（「業務A」の中の「業務」は拾わない）。一致した大分類は rag_engine の `AnswerDependencies.business_domains` で質問の理解（`inquiry_conditions.business_domains`）へ渡し、rag_engine の `_same_business_records`（一致する候補が無ければ絞らない）と business_match のチャネルが使う。名指しが無い、範囲外の大分類、一致する候補が無いときは絞らない。業務名はこの保存済み分類の一覧だけから照合する。

## 使い方（推奨の流れ）

1. **解析**：文書解析を Docling にする。図や画面キャプチャが多い文書では、文書のレシピで Vision（図・画像を AI で読み取る）を有効にする（Docling 以外の解析エンジンでも使える）。有効にすると、画像 1 枚ごとに Vision モデルの呼び出しと時間がかかる。
2. **分割**：文書分割は既定で親子階層（`small_to_big`。#594 で既定にした）。親は回答の文脈に渡す大きい単位、子は検索に当てる小さい単位（LangChain の ParentDocumentRetriever・LlamaIndex の階層の分割と同じ考え方）で、**どの解析の結果でも親子に分割する**（#3377。解析エンジンの名前では選ばず、抽出の形で親子の作り方を選ぶ。取込の trace の `chunk_parent_source`）。
   - 解析の結果がレイアウトの記録（`parser_artifacts.layout_records`。Docling の PDF・画像）を持つ文書は、その記録から親子を作る（`layout_records`。見出し・表・図の領域と根拠の元の要素を保つ）。
   - Excel の行の記録は行を子・表の一部を親（`sheet_records`。#1349）。
   - それ以外の抽出（標準の解析の Markdown・テキスト、Unstructured・OCI などの解析の結果、構造化レコードの JSONL の CSV・Word など）は、抽出の構造から親子を作る（`extraction_structure`）。子は構造認識と同じ要素の分割（同じ節・同じ種類の要素だけをつなぐ）を子の目標文字数で行い、表は表の子の目標文字数で行のまとまりに分けて列見出しを繰り返す。見出しだけの子は作らず、続く本文の子の先頭に入れる。構造化レコード JSONL は 1 記録 = 1 子（#2457）。親は続く子を、節（文書を 2 つ以上に分ける最初の見出しの段。題が 1 つの文書はその下の段）をまたがず、親の目標文字数・子の数・ページ数の上限の中でまとめる。見出しの無い文書は順と大きさだけでまとめる。子の metadata は Docling の親子と同じ（`chunk_strategy=small_to_big`・`parent_chunk_id` / `chunk_group_id`・`chunk_group_kind=small_to_big_parent`・`parent_text`・`section_path`・頁・`element_ids`）で、回答は同じ経路で親の本文を文脈にする。
   - 以前（#300〜#3377）は、レイアウトの記録が無い文書を「構造認識」（`structure_aware`）へ縮退し、chunk に `chunk_strategy_fallback_reason=layout_missing` を残していた。その chunk は文書詳細の Chunk タブに「親子階層で分割されていない Chunk です」と表示し、Chunk を作り直すと親子階層で分割する（再解析は要らない）。
   子・親の大きさは同じ画面の「戦略別パラメータ」で変えられる（下の設定一覧）。
3. **確認**：文書詳細の抽出タブで、次を確認できる。
   - 要素の種別と bbox
   - 表のテキスト化
   - Vision の読み取り内容（画面名・ボタン・表の行・操作手順など）と切り出し画像
4. **検索・回答プロファイル**：
   - 必要なら質問の拡張・回答の生成方式・根拠の前後から加える数・Rerank・画面目録で操作画面を探すを上書きする（既定は単純検索 / 標準 RAG / 3 / ON / OFF。回答エンジンの選択は #594 で削除した）。
   - 検索・回答プロファイルの知識に、Approved FAQ・用語・同義語・ドメインキーワード・回答ルールを登録する。タブは回答フローで使う順に並ぶ（類似問の提示 → 用語・同義語で質問を広げる → ドメインキーワードでキーワード検索の語を切り出す → 回答ルールを回答の生成に渡す。#682）。回答の処理の経過では、用語・同義語と回答ルールを別の工程「用語・同義語の確認」（別名を補助の検索文に加える）と「回答ルールの確認」（一致した回答ルールを回答時の参考情報として渡す。確認で選んだ条件もここに出す）で示し、それぞれ有効な登録の件数・一致した用語（別名つき）/ 一致した回答ルール・影響を詳細に出す（登録は 1 回だけ読む。#3451）。
5. **検索**：
   - 検索・回答プロファイルを選んで検索すると、先に類似する承認済み FAQ を照会する。候補があれば「この FAQ の回答を使う（LLM を使わない）」か「類似問を使用しない」を選ぶ。
   - 回答には「処理の経過」（#2096。回答の工程ごとの一覧〔入れ子は字下げ・所要時間・LLM の回数〕。実行中は開き、完了したら閉じる〔#2118〕。その下の「詳細」に信頼度・人手確認・使ったモデル・評価、会話を開き直した回答は保存日時と回答の記録の操作）が付く。チャットと RAG 検索は同じ部品 `components/search/AnswerProcess.tsx` 1 つで、位置・開閉・「詳細」の中身をチャットの形にそろえる（#2118。RAG 検索の「詳細」の開始・トレース ID は無くした）。工程は回答の trace の span（共通の span の表。#3226）で、チャット・RAG 検索とも記録ごとの trace の API の snapshot から作る（`lib/trace-progress.ts`。種類 `answer_step` の値に工程名、入れ子は span の親子）。根拠の構成（AI に渡した箇所を同じ節ごとにまとめた単位）は、根拠の一覧の「まとまりごと」に出す（#2097）。
   - 回答の本文の節（`rag_engine/generation/grounded.py`。#2040）: 「資料により確認できた事項」（質問の条件への該当を監査で確認した説明。印の付いた説明は入れない）・「根拠で確かめきれていない事項」（段落の印〔下の「段落の印」〕の付いた kind=rule の説明。直下に理由の案内を置く。#3394）・「操作手順（機能名）」「確認手順（機能名）」・「参考情報」（システムが補った原文〔必須根拠・確定操作・但し書き・拒答のときの関連原文・監査が必要とした根拠〕と、該当が未確認〔`applies=unverified`〕の説明の原文。直下に固定の説明「以下は資料の原文です。本質問の条件への該当は確認できていません。」を置き、結論には使わない。規則の検査・監査で確かめられなかった説明の置き場ではない〔#2738〕）・「資料から確認できなかった事項」・「回答に未反映の関連章節」（章節の拡張の上限で読めなかった章節。各行から章節の原文を開ける）・「回答時間の上限により省略した処理」（回答時間の上限で省いた生成・監査・是正）・「回答を確定するために確認すること」・「根拠と矛盾し除いた内容」（監査が根拠と矛盾と判定して本文から外した説明と理由。#2738）・「確認が必要な点」（回答全体の警告と、印の付いた段落の短い引用と理由。#2738）。最後の 2 つは本文だけを読む利用者向けで、正本は回答の構造の段落の印（下の「段落の印」）。見出しと固定の説明は主張ではないので、監査・評価・指標は `is_structural_line` で外す。回答で引用した箇所ごとの使われ方（該当確認済み `confirmed` / 参考 `reference`）は、引用の metadata の `evidence_answer_use` と MCP の `evidence[].answer_use` に載り、画面の件数とバッジ（「回答で引用」「参考」）に使う。
   - 保存された回答（回答の記録）は、チャットの各回答の「処理の経過」の中の「処理の詳細」（処理の経過を開いたときのタイムラインの後ろ。#2325）から回答の記録の詳細を開き直せる（会話の回答の trace_id で保存の有無を引き当てる。#304）。引用の一覧は回答の枠の折りたたみ「AI に渡した N 件（K のまとまり）／ 回答で引用 M 件 ／ うち該当確認済み K 件 ／ 参考 L 件」（0 件の項目は出さない。#2040・#2097）の 1 か所だけに出し、「処理の詳細」の中には重ねて出さない。折りたたみの中は「順に表示」（引用のカード）と「まとまりごと」（同じ節ごとにまとめて AI に渡した単位。各箇所の役割・位置・本文の抜粋と、押すと開く引用箇所。chunk の ID は「処理の詳細」の中）で、まとまりの件数の合計は N に一致する（backend は根拠の木 `evidence_tree` の子を引用にした箇所だけ 1 回ずつ持つ。#2097）。「処理の経過」（工程の一覧と、その後ろの「処理の詳細」）は回答の上（作成中の「N ステップ完了」の場所のまま。#2115）に置き、回答の枠の下は「AI に渡した N 件」→ 回答の評価（「この回答は役に立ちましたか？」）の順（#1202 / #1417 / #2096。`platform/docs/ux-contracts/page-archetypes.md` §6.1。RAG 検索の回答のカードもチャットと同じ部品・並び）。根拠の一覧は回答の文脈に入れた根拠の chunk の全件で、回答に使ったもの（`metadata.evidence_model_used`）が先頭に並び、カードに「回答で引用」が付く。回答を作らない検索の結果は「根拠 N 件」（RAG 検索・検索テストでは「検索結果（N）」）とだけ出す（#1208）。回答の記録は 1 件ずつ削除しない（画面の操作も API も持たない。#2325・#2348。保存期間を過ぎた記録は自動で消える）。検索画面の回答履歴の一覧は #444 で削除した（一覧の API `GET /api/search/answers` は、チャットの引き当て（`trace_id` の指定）が使うため残している）。
   - 扱えるのは自分の回答だけ（詳細・評価・削除も同じ）。SYSTEM_ADMIN と `rag.feedback.manage` を持つ利用者は、利用できる検索・回答プロファイルのすべての利用者の回答を扱える（#304）。
   - 参照するナレッジベースが 0 件の検索・回答プロファイルでは検索・チャットしない（利用者が使える全 KB を検索しない）。画面は選んだ時点で理由を示し、API は 409 と理由（「この検索・回答プロファイルには参照するナレッジベースがありません。…」）を返す（#304）。
   - RAG 検索・チャットで選ぶ検索・回答プロファイルは 1 つ（#635。同じ選択欄 `SearchAnswerProfileSelect`）。回答はその検索・回答プロファイルの参照 KB と検索・回答設定・知識で作る。
6. **評価**：回答の「処理の経過」の中の「処理の詳細」（RAG 検索・チャット）の「標準回答による評価」に期待する回答を入れて「標準回答で評価」を押すと、評価の基準（取込・検索・回答設定）の指標のうち 1 件の回答で測れるもの（Faithfulness（主張の判定）・標準回答の網羅・拒答の正しさ・引用の追跡可能性。根拠との語句の一致率は参考値）を、選んでいる基準の閾値で判定し（`rag_engine.evaluation.answer_eval` が LLM で標準回答の項目の照合と主張の監査を行い、`app/rag/answer_metrics.py` が指標と合否を付ける。#680）、結果を回答記録に保存する。rag_poc と違い、生成の後に評価する。この機能より前に保存した回答は評価の入力を持たないので評価できない。評価は LLM を複数回呼ぶため、この API だけ時間の上限を長くしている（#304）：backend は評価全体を LLM 1 回の timeout の設定の上限（600 秒）で打ち切って 504 と理由を返し、評価を保存しない。画面は 630 秒、Nginx（`platform/deploy/suite-nginx.sh` が生成する、評価と回答生成・MCP の `location`。path は `SUITE_RAG_LONG_API_PATHS`。#1597）は 660 秒待つ（backend の理由が画面に届くよう、外側ほど長くする）。
6a. **実行履歴**（#1890）：「AI 活用」の「実行履歴」（`/history`。メニュー権限 `menu.history`）で、チャットと RAG 検索の実行を 3 製品で共通の型（UX 契約 run-history.md。#1955）で一覧し（質問・検索・回答プロファイル・状態・種類・実行者・開始日時・所要時間・回答の対応・資料との照合。質問・実行 ID の検索と状態・種類・期間・実行者の絞り込み）、全幅の詳細で処理の経過（タイムラインと、その後ろの「処理の詳細」〔回答の記録の詳細と識別子。チャットと同じ部品。#2325〕）・回答・根拠・フィードバックを確かめる。実行ごとに `rag_run_history` に 1 行を残す（`app/rag/run_history.py` の `RunRecorder`。回答を作った実行の回答・引用・診断は回答の記録が正本で、ここには要約・段（`stages_json`）と回答を作らない RAG 検索の根拠（`citations_json`）だけを持つ）。安全チェックで止めた質問は保存せず、根拠の検索だけ（ナレッジベースの検索テスト・レシピの検索比較）・業務ガイドの下書き・品質評価・MCP（Agent の実行履歴に残る）は残さない。利用者が止めたチャットの回答（停止）は残らない。「資料との照合」（#2361 で「回答の検証」から改名）は回答の監査で質問の要求ごとに根拠で答えられたか（回答の構造 `envelope.requests`）で、すべて答えられていれば「照合済み」、答えられていない・確かめられなかった要求があれば「一部未確認」、監査の記録が無ければ「未照合」。見え方は #1889 の規則（system_admin は全員の実行、それ以外は自分の実行だけ。一覧・件数・詳細を Oracle の条件で絞る。判定は `pr_system_settings.auth.visibility` の `can_view_all_users_data`。他人の実行の詳細は 404）。保存期間は回答の記録の保存期間（`RAG_ANSWER_RECORD_RETENTION_DAYS`）と同じ。
7. **フィードバック**：回答を「役に立たなかった」と評価するときに、rag_poc の分類（ナレッジ不足・情報が古い・質問が曖昧を含む）と修正した回答を入力できる。管理者はフィードバック画面の詳細から、Approved FAQ への登録と品質評価のケースへの追加ができる。フィードバック画面の一覧・集計・詳細は、SYSTEM_ADMIN はすべての利用者の分、ほかのロールは自分が送った分だけで、画面の先頭に見える範囲を案内する（#408）。
8. **検証**：`uv run python -m app.rag.answer_verify_cli`（`regression` / `crag-goldset`）で、質問の回帰と CRAG goldset の評価を実行できる。標準回答を使う一括の品質評価は `app.rag.evaluation_cli` を使う（`docs/evaluation-observability-guardrails.md`）。
9. **チャット**：会話履歴を使う。直前までの会話から質問を単独で意味が通る形に書き換えてから検索・回答する（書き換え後の質問は回答パネルに表示する）。

出力の上限で未完了の応答を、上限を 2 倍にして送り直した回数（`output_retries`）と、未完了の応答の数・理由

**暴走した出力の打ち切り（#2966）**: 出力は速く続くのに、同じ並びの繰り返し・空白だけを出力の上限（32,768 tokens）まで書き続ける
生成がある（記録: 1 回目が 200 秒で上限に届いて未完了、推論の量を下げた送り直しは 2 秒で完了）。停滞の検出（event の間隔・速さ）
では見分けられないので、streaming で受ける呼び出し（下の停滞の検出が ON のとき）は出力の文（`response.output_text.delta`）の
末尾を確かめ、末尾の 2,400 文字が周期 300 文字以下の完全な繰り返し（`runaway_repetition`）か、空白が 2,000 文字続いた
（`runaway_whitespace`）ら stream を閉じ、推論の量を 1 段下げて（下げられなければそのまま）1 回だけ送り直す（`oci._RunawayMonitor`。
`RAG_LLM_RUNAWAY_DETECTION_ENABLED=false` で切れる）。行ごとに値が変わる表・一覧は打ち切らない。打ち切った呼び出しは
`incomplete_reasons` に理由、送り直しは `runaway_resends` に残る。工程の記録は呼び出しの回数（`llm_calls`）と API への送信の
回数（`llm_sends`。送り直しで多いときだけ）を分け、画面は「LLM 1 回・送信 2 回」と示す。
streaming しない呼び出し（停滞の検出が OFF・回答の期限が無い文脈）は途中で打ち切れないので、出力の上限で未完了になった応答の
出力の文に同じ基準の暴走（空白が 2,000 文字続いた箇所・末尾の繰り返し）があれば、上限を 2 倍に広げる送り直しをせず、streaming と
同じく推論の量を下げて 1 回だけ送り直す（#3835。広げても空白・繰り返しが続くだけ。`oci._runaway_response_reason`）。理由は同じく
`incomplete_reasons` に残り、送り直しても暴走した呼び出しの失敗の詳細（生成後監査では `audit_failure`）は分類 `runaway_output` と
打ち切りの理由（`cutoff_reason`）を持つ。生成後監査の固定キーの wire では、値と次の key の間（JSON の構造の空白）で空白が続く
暴走が出る。strict の JSON schema は構造の空白を制限できず、自由記述の欄の `maxLength` では防げない（#3835 の固定入力の比較）。

**停滞した LLM の呼び出しの送り直し（#1926）**: OCI Enterprise AI の呼び出しは、まれ（#1912 の記録の 206 件で約 1%）に
通常の 1/10 以下の速さ（13〜23 token/秒。中央値 224）に落ち、同じ token 数で 36 秒 → 183 秒かかった。回答の期限がある文脈では
LLM の呼び出しを streaming で受け（`rag_engine.adapters.oci._stream_parsed`）、次のとき stream を閉じて同じ要求を送り直す
（`RAG_LLM_STALL_RESENDS` 回まで。最後の送信は検出せずに期限まで待つ。期限の残りが停滞の秒より短いときの timeout は停滞ではなく
期限切れ）。

- event（最初の event を含む）が `RAG_LLM_STALL_IDLE_SECONDS`（既定 20 秒）来ない（`stall_idle`。httpx の read timeout）。
  同じ接続・モデルの直近の呼び出しの最大の間隔の中央値の 3 倍が長ければそちら（推論を stream しないモデル）。
- 最初の delta（推論・出力の event）から 10 秒が経った後、直近 10 秒の delta の数（event/秒）が、同じ接続・モデルの直近 8 回の
  完了した呼び出し（delta 256 件以上）の速さの中央値 × `RAG_LLM_STALL_MIN_RATE_RATIO`（既定 0.25）を下回った（`stall_slow`）。

判定の基準は process の中の直近の呼び出しから学び、3 回たまるまでは検出しない（基準の無いモデルを誤って打ち切らない）。
取込などの期限の無い呼び出しは従来どおり streaming しない（`responses.parse`）。`RAG_LLM_STALL_DETECTION_ENABLED=false` で従来の
受け方に戻る。打ち切った呼び出しは `llm_status=failed` と理由（`stall_idle` / `stall_slow`）で log と `llm_usage` の
`incomplete_reasons` に、送り直しの回数は `stall_resends` に残る。streaming で受けた呼び出しは、log に最初の event までの秒
（`llm_first_event_seconds`。待ち）・出力の速さ（`llm_delta_rate`。停滞）・最大の間隔（`llm_max_gap_seconds`）を、工程の
`llm_usage` にその工程の最大の待ち（`first_event_seconds_max`）と最も遅い速さ（`delta_rate_min`）を残し、遅い呼び出しが待ちか
出力の途中の停滞かを記録から見分けられる。

id を落とした形（「chunk_set:番号」）と、区切りを横線で書いた形（「78f40985‑…‑244」）も根拠に結び付ける（番号はそのまま一致し、

**最終の検証の時間の上限と段落の組（#2700）**: 監査の 1 回の呼び出しの時間は、ほぼ出力（判定と推論）の token の数で決まり、
段落の数に比例する。推論型のモデル（出力が毎秒 16〜26 token、混んだ時間は 3〜10 token）では、回答の全段落（10〜50 段落）を

Agent の MCP の待ち時間（630 秒）を超えていた（呼び出し側が待つのをやめた後も RAG は LLM を呼び続け、最長 1,937 秒かかった）。
そこで回答の段落を `RAG_ANSWER_VALIDATION_BATCH_PASSAGES` 個ずつの組に分け、同時に `RAG_ANSWER_VALIDATION_CONCURRENCY` 組までを
並行に監査する（どの組にも指示・質問・回答の全文・根拠を同じに渡し、渡す段落だけを替える。判定の基準・照合・`_enforce_support`
は変えない）。検証の全体に `RAG_ANSWER_VALIDATION_TIMEOUT_SECONDS` の期限を置き、LLM 1 回の timeout・再試行を残りの時間に縮め、
期限までに返らなかった組の段落は「照合の時間の上限までに、この段落の監査が終わりませんでした。」の `unassessed` にして、
確かめ終わった組の判定と一緒に返す（`status=partial`。組の期限は組ごとの子の期限で、1 つの組が出力の上限で期限を切っても
ほかの組は続ける）。期限の前に起きたほかの失敗（出力の契約の違反が続いた等）は、分けない監査と同じく失敗にする。検証は
回答フロー（チャット・検索・品質評価の回答）とは別の executor で動かし（`answer_threads.validation_executor`）、回答の
executor が埋まっても待たない。1 回の検証ごとに `rag_answer_validation` のログ（状態・秒・上限・根拠と判定の数・時間切れの
段落の数・LLM の呼び出しの回数と秒・出力と推論の token・停滞の送り直し）を残す。Agent は `partial` の確かめ終わらなかった
段落を外さずに本文に残して確かめきれなかった点として示し、`timed_out` は検証できなかった（`validation_timed_out`）として扱う。

**見出しの木（#1517）**: Docling の解析の結果では、chunk の見出しの列（`section_path`）と、章節ナビゲーションの抽出の章節
（方式「解析エンジンの見出し」）の元になる要素の `section_path` を、同じ規則で作る（`rag_engine/chunking/headings.py` の
`layout_section_paths`。parser の `layout_to_extraction` と分割が同じ 1 か所の更新 `_section_path_state_after` を通る）。
見出しの深さは番号の体系から決める: 「第 N 章」（漢数字・全角数字・番号の前後の空白の有無を問わない）と「N.」は 1、
「N.N」と「第 N 節」は 2、「N.N.N」と「第 N 項・条」は 3、「（N）」「（一）」は 5。「第 N 編・部」の配下の番号の見出しは
1 段深くする。番号の無い見出し（表題など）は、形（囲み記号・無印）と並びから置く。Docling の見出しの level
（`SectionHeaderItem.level`）は PDF ではすべて 1 で深さを表さない（評価の PDF の 18 件で全件 1）ため、番号を優先して
level は使わない。そのため「第 3 章 > 3.1」の 3.1 は第 3 章の子になり、「3.3」の後の「第 4 章」は第 3 章の兄弟に戻る。
評価の PDF の見出しの木は、原稿の HTML の目次と一致することを `rag_engine/tests/test_evaluation_heading_tree.py`
（解析済みの layout record の fixture）と backend の `tests/test_navigation.py` で確かめる。既存の文書の抽出の章節は、
抽出結果に保存した章節の木から作るため、取り込み直し（解析からの再処理）で新しい規則になる。分割だけをやり直す再処理
（抽出を使い回す）では chunk の `section_path` だけが変わり、抽出の章節は変わらない。人が修正した章節は上書きしない（深さが
変わった章節は id が変わるため、「新しく抽出」の印で足される）。

**章節と chunk の対応（#1438）**: 文書の詳細の「章節ナビゲーション」の章節（人の修正 `rag_document_sections` と、修正が
無いときの抽出の章節）を章節の正本とし、正しいものとして扱う。章節は何度でも直されるが、分割（chunk）・embedding・
ベクトル索引には影響させない（再分割・再 embedding をしない）。代わりに、どの chunk がどの章節に入るかの対応だけを表
`rag_chunk_set_sections`（chunk_set ごとの章節。階層・親・ページの範囲・chunk の数・文字数）と `rag_section_chunks`
（章節に入る chunk・章節の中の順・所有の章節か）に持ち、次の後に文書ごとに作り直す（`app/rag/section_map_service.py`）。

- 取込の job の成功の後（分割と embedding が終わった後）。
- 章節の保存（`PUT /api/documents/{document_id}/sections`）と取り消し（`DELETE`）の後、処理レシピの保存・削除の後（レシピの
  章節の抽出規則の方式で章節が変わる）。
- 章節の抽出規則の全体の既定の保存・取り消しの後（すべての文書をバックグラウンドで作り直す）。
- 作り直しに失敗しても取込・保存は止めない（ログ `section_map_refresh_failed`）。対応がまだ無い chunk_set（この機能の前に
  取り込んだ文書など）は、MCP で章節を読むときにその場で作る。

対応の決め方は決定論的（`app/rag/section_chunk_map.py`）。章節を並び順に見て、それぞれの始まりの chunk（読み順 =
`chunk_index`。前の章節の始まりより前にしない）を、解析の要素の ID（章節の元にした解析の結果の chunk_set のときだけ。解析

### 頁番号のフッターの論理頁（#2289）

親子階層の分割は、頁の下端の頁番号（`Page-footer` の本文が頁番号だけの形）から各頁の論理頁を決め、chunk の `layout.logical_page_labels`（物理頁 → 論理頁）と検索の文の `Pages: p.3; p.3=logical 1` に入れる（`rag_engine/chunking/page_numbers.py`）。

- **頁番号の形**: 空白を除いた本文の全体が「頁の語・範囲の記号・`/総頁数` を前後に付けた 1 つの数」（`3`・`- 3 -`・`3頁`・`P.3`・`Page 3`・`3/20`・`ii`・`三頁`）。頁の語・範囲の記号は言語資源の `markers`、数の体系（算用数字・ローマ数字 `numbers.roman_digits`・漢数字 `numbers.kanji_digits` / `kanji_multipliers`）は言語資源の `numbers` から作る。比べる前に言語資源の文字の正規化（`symbols.normalization`。既定 NFKC。全角の数字・`Ⅳ`）をする。ローマ数字は標準の書き方（`iv`。`iiii` は読まない）だけを読む。
- **並びで確かめる**: 文書全体の候補を頁の順に、同じ数の体系で値が増え、物理頁との差が一定の並びにつなぐ。並びの頁数が `page_number_min_run_pages`（文書の頁数がこれより少なければ文書の頁数）以上の並びだけを長い順に採り、採った並びの頁の範囲と重なる短い並び（並びの途中の外れた数）は使わない。1 頁だけ別の数（年・図の番号）を持つ頁、頁の多い文書の 1 頁だけの数は論理頁にならない。番号の無い頁を挟んでも差が同じなら同じ並び。
- **数の体系ごとの並び**: 前付きのローマ数字（`i`・`ii`）と本文の算用数字（`1`・`2`）は別の並び。論理頁の値は、算用数字・漢数字は数、ローマ数字は書かれた字のまま（`"ii"`。本文の頁 2 と見分ける）。
- **設定**（`rag_engine` の `ChunkingConfig`。chunk run の `config_hash` に入る。backend の取込・検索・回答設定と文書レシピには出さず、既定値で分割する）:

| 項目 | 既定 | 範囲 | 内容 |
|---|---|---|---|
| `page_number_min_run_pages` | `2` | 1〜10 | 論理頁に使う並びの最小の頁数 |
| `page_number_offset_tolerance` | `0` | 0〜5 | 隣り合う頁番号の間で許す、物理頁との差のずれ（0 = 差が一定。番号を振らない挿入頁で差が変わる文書のため） |

- **柱・フッターの繰り返しの判定**（`_boilerplate_text_key`）も同じ数の体系で数を伏せる: 頁番号だけの文は数の体系・飾りによらず同じ鍵、前後が語の字でないローマ数字の語（`Part iv`）と頁の語の前の漢数字（`三頁`）は `#`。「第三章」の章の番号は伏せない。
- **PDF の `/PageLabels` との関係**: `/PageLabels` を持つ PDF は backend の `page_labels.py`（#1244）が chunk の `page_label_start` / `page_label_end` に印刷の頁番号を入れる。これが印刷の頁番号の正本で、MCP の結果と回答の記録に残る。フッターから決める論理頁は別の項目（`layout.logical_page_labels`）で検索の文の補助に使い、`page_label_*` を上書きしない（`/PageLabels` があってもフッターの論理頁は決める）。

## 親子階層（`hierarchical_parent_child`）の削除（#271）

LlamaIndex AutoMerging 風の分割方式「親子階層」は削除し、一覧の同じ位置（再帰文字分割の次）に親子階層（small-to-big）を置いた。

- 保存済みの `hierarchical_parent_child`（`backend/.env` の `RAG_CHUNKING_STRATEGY`、文書・レシピの処理設定、KB の構築設定）は、読み込み時に `small_to_big` として扱う。子サイズ `chunk_child_size` / `RAG_CHUNK_CHILD_SIZE` は読まない。DB の移行は不要で、次に保存すると新しい値だけが残る（文書分割の設定を保存すると `.env` から `RAG_CHUNK_CHILD_SIZE` の行も消える）。
- 親子階層で作った配信中の chunk はそのまま検索対象に残り、自動では作り直さない。レシピ一覧の「再処理が必要」は設定の revision で判定するため、読み替えだけでは表示しない（文書単位の処理設定の保存 API と、その応答の差分（drift）は #488 で削除した）。親子階層（small-to-big）で作り直すには、その文書の Chunk を再作成する。
- 親子階層（small-to-big）はどの解析の結果でも親子に分割する（上の「使い方」2.。#3377。#300〜#3377 は Docling 以外の解析結果を構造認識へ縮退していた）。
- 既存環境の更新手順：`backend/.env` の `RAG_CHUNKING_STRATEGY=hierarchical_parent_child` と `RAG_CHUNK_CHILD_SIZE` は、そのままでも起動する（前者は親子階層（small-to-big）として読み、後者は無視する）。構造認識として扱いたい場合は `RAG_CHUNKING_STRATEGY` を `structure_aware` へ変えておく。

## rag_poc との差分

- 解析結果、チャンク、回答はファイル（`.runs/`）ではなく、本リポジトリの Oracle と Object Storage を使う。
- ADB の独自スキーマ（`rag_chunk_runs` / `rag_chunk_embeddings` など）は使わない。検索は backend の hybrid 検索（vector と Oracle Text の RRF）に、rag_poc の「原質問を主軸にした重み付き融合」と Sudachi 分割を組み合わせる。
- chicago / osaka の 2 系統 LLM 設定と、OCI SDK の LLM 経路は廃止した。
- 移植していないもの：
  - Gradio UI、PPT 資料、`verify/` の問題セット（データは移さない。検証 CLI `app.rag.answer_verify_cli` で rag_poc の `cases.json` / `crag_goldset.json` をそのまま使える）
  - `evaluate_crag_grader.py`（rag_poc 独自の ADB の保存先から候補を組み立てる設計のため）と、`run_answer_eval.py` の Excel 出力・LLM 呼び出し回数の集計
  - フィードバックから FAQ・評価データセットへの自動昇格（管理者がフィードバック画面の詳細から 1 件ずつ「Approved FAQ に登録」「品質評価のケースを書き出す」（評価リクエストの Excel の 1 行。#2065）する。FAQ の変換と除外の規則は rag_poc の `approved_faq_import_row_from_answer_feedback` を使う）

### 章節の最低読取範囲と回答方式（#2759・#2760）

章節展開が有効なら、主検索、業務ガイドの手順別検索、不足要求の追加検索の後に共通の補完を行う。
同じ回答内で原文キャッシュ、読了記録、入力の上限、回答開始からの期限、原文抽出の呼び出し枠を共有する。
同じ所有章節の命中をまとめ、すべての異なる所有章節を対象とする。固定2起点による打ち切りは行わない。

- 第1段は所有章節全体、第2段は親、第3段は祖父。列挙で最低範囲が文書全体なら、そちらを優先する。
- 標準 RAG は最低範囲を補い、CRAG の評価器・補正検索を呼ばずに生成する。`scope_read` は構造上の必要範囲を
  読んだことを意味し、LLM が内容の十分性を確認したという意味ではない。
- CRAG は最低範囲を補ってから再判定し、不足時にだけ上の章節へ進む。補完前の十分判定は最終判定にしない。
- 同じ ID でも本文が抜粋なら読了とせず原文へ戻す。部分取得、権限による欠落、読取失敗、抽出した抜粋は
  全量の読了にしない。評価器が十分と返しても、未確認の範囲を消さず条件つきの回答にする。
- RAG 検索の画面の回答を作らない検索（`generate_answer=False`）は、チャットと同じ流れでこの補完まで行い、回答の
  生成の手前で止める（#3506。処理の経過の工程・入れ子・LLM の呼び出しもチャットと同じ）。
- MCP の根拠取得（`rag_retrieve_evidence`。`complete_evidence=False`）は同じ流れの主の文書の検索の後で止め、
  自動補完しない。返された章節・chunk の ID から呼び出し側が `rag_read_section(up=...)` を使う。回答生成する
  RAG 内部と Agent 側で二重に読む契約にしない。

診断は `section_expansion.stop_reason`（`disabled` / `not_configured` / `no_sections` / `scope_read` / 各上限など）、
`minimum_scope_complete`、`judgement`（`llm` / `not_requested`）、`completed_sections`、`unmapped_seeds`、
`unread` を分ける。`phases` に主検索・手順別・不足要求検索後それぞれの実行を残す。
既存の近傍・親子 chunk の役割と `section_context` は別に記録する。

方式の比較と追加候補の採否は [章節補完の比較](section-completion-evaluation.md) を参照。

## 外部 DomainProfile の廃止（#3668）

外部 JSON の業務分類・別名・判定語を自動読込する機能は廃止した。文書に保存済みの分類と、その検索範囲から照合する業務名は引き続き使う。分類名を外部の一覧から補正したり、パスの語から大分類・中分類を決めたりしない。任意の手入力分類は保存した名前のまま復元する。

別名は検索・回答プロファイルの「用語・同義語」、検索で保護する語は「ドメインキーワード」、回答前の確認と回答の指示はページ管理のルール・ガイドを使用する。一般的な日本語の質問理解・条件の読取り・言語資源は維持する。旧ファイルの内容をこれらの設定へ自動コピーしない。

SDK の `DomainProfile`、`Runtime.profile`、`create_oracle_application(profile=...)` は削除した。Runtime の Prompt 上書きは `prompt_overrides`、Prompt ファイルの保存先は `ResourcePaths.prompts` / `Settings.prompt_dir` で明示する。

### 指示の保存と検査状態の区別（#3753）

検索・回答・監査・評価の指示は、各設定画面で保存・変更の破棄・既定への復帰を共通操作で扱う。`既定に戻す` は保存前の編集であり、保存時にその key の上書きを消す。保存した指示は API の要求に固定して worker thread・子 task へ引き継ぎ、構造化出力の型や認可は変更しない。

手順の根拠の関連付けと、説明・引用による手順への対応付けは別の段である。`guide.step_coverage[].assignment` は引用した item、割り当てた item、対応の方法と公開可能かを残す。`evidence_flow` は関連付けた source の数・実際の回答材料の evidence ID・引用した evidence ID を分けて残す。必須手順の直接の根拠を各手順に一つずつ先に原文予算へ配り、任意の章節だけで予算を使い切らない。予算の上限自体は増やさない。`unused` は資料の不在と断定せず、回答と手順の対応が未確定であることを示す。`round_budget.rounds[].accepted` は草稿の採否で、`acceptance_scope=draft_selection` を記録する。監査を行わなかった要約は `summary_validation=not_run` とし、`summary_supported=true` を記録しない。

既知の条件に当たる分岐の note は、資料の操作の根拠と分け、業務ガイド由来の案内として必ず本文に出す。未知・矛盾した条件の分岐の note は自動適用しない。
