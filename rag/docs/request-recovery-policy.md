# 生成前と生成後の根拠不足への補救

生成前 CRAG は材料の関連性・十分性を判定し、生成後は明示的な gap と実行した監査の要求判定を利用する。両方を自動で有効化せず、通常回答の監査なしの既定も維持する。

| 生成後の状態 | 処理 |
|---|---|
| 必要な直接根拠が入力にあり回答が省略 | 監査が示した evidence_id の存在を検証し、detailed の是正で既存の材料から補う |
| 生成が明示した gap、または監査が材料不足と判定 | 有効時だけ元の要求の文で補検索し、新規根拠が追加された場合だけ再生成 |
| 監査未実行、材料判定なし、available の根拠 ID が不正 | 材料不足と断定せず保持。新たな監査を必須化しない |
| 内容の矛盾・引用の問題 | 既存の事実検査と設定された是正モードに従う |

検索語の一致や関連する引用元の存在だけで、材料の十分性を確定しない。監査の材料判定もモデルの判定であり、人手による校正の対象である。回答の充足と材料の有無を別のフィールドにすることで、誤った対処を追跡できる。

CRAG の補正検索と生成後補查は既存の `ExtraRetrievalBudget` を同じ回答内で共有する。`CoverageUsage` は実行した検索文、追加根拠、補正検索に使った時間を後続へ引き継ぐ。CRAG の初回検索は追加検索として数えず、pool 内の局所拡張もネットワーク検索の回数には数えない。章節の原文読取は従来の章節読取予算と回答全体の期限に従う。総入力予算・各段の上限のさらなる整理は #3682 に残る。

生成後の `request_recovery` は段階、要求 ID、原因、選択した処理、実行状態、新規根拠数、停止理由を記録する。補検索自体の回数・時間・停止は `request_coverage`、回答全体の消費は `extra_retrieval_budget`、是正回数・期限は `round_budget` で確認する。取得失敗や新規根拠なしで採用済み回答を捨てない。

## 四条件の比較

既存の比較準備 CLI に `--recovery-matrix` を渡す。

```sh
python -m app.rag.retrieval_budget_plan <EvaluationRunRequest.json> --output-dir ./tmp/recovery-comparison --recovery-matrix
```

出力は CRAG 有無 × 生成後補查有無の四条件。モデル・質問・索引・検索範囲・監査モード・総予算を固定する。要求 JSON の `answer_flow` と全体環境差分を各対象環境に適用し、既存評価 CLI/API で実行する。準備ファイルは実行結果ではなく `executed=false` のままである。常駐 backend へ反映するには設定の適用と再起動が必要。保存済み設定やプロファイルが環境値を上書きしていないことを有効設定の snapshot で確認する。#2573 の段階除去 runner は未実装なので、新規 runner が利用可能とは扱わない。

決定論回帰では四条件の発火、材料不足と回答漏れ、未知、検索失敗、共通予算、無進展停止を確認する。実サービスでの品質・token・費用・p50/p95 の四条件比較は未完了であり、両方を既定 ON にする根拠はない。既定は維持し、効果の実測は #3755 で追跡する。
