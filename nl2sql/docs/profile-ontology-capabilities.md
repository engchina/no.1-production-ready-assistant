# Profile Ontology：13分類と Markdown の構築・公開

Markdown を業務定義の編集・公開元とする。画面の順序は **構築入力・進捗 → Markdown 下書き／公開版 → 接地確認グラフ**。独立した構築結果・公開能力の画面は廃止した。Function / Action Type は業務の意味を記述する定義であり、この画面から実装の設定・呼出し・更新操作を実行しない。

## 分類と同一性

| 分類 | 読む順序 |
| --- | --- |
| 主要6種類 | Object Type → Property → Link Type → Interface → Function → Action Type |
| 補助7種類 | Shared Property → Value Type → Enumeration → Metric → Business Rule → Business Event → Object Set |

旧業務エンティティは Object Type、旧属性・指標・ルール等は対応する分類に変換する。新規生成は型付き `definitions` を正本とし、旧形式への二重出力を要求しない。同一性は Profile と分類、安定 ID / API 名で確認する。ただし名前・ID が同じでも、物理の表・列（リンク型は両端と結合のキー）が食い違う定義は別の概念にする（API 名が種類の名前 `link_type`・`property` だけの定義は、所属・列・両端から API 名を作る。#1729）。同じ表・ビューを指すオブジェクト型は 1 つにまとめる（下の「同じ物の統合」）。説明・別名・証拠・マッピングは保持し、式・型・制約等の異なる値は Markdown の確認事項へ残す。Schema / 表 / ビュー / 列は物理層に保持する。

すべての分類を確認するが、根拠のないインスタンスは作らない。件数と根拠不足・不適用・失敗理由は coverage として保持する。

## オントロジーの標準

オントロジーの中身は業界の標準のモデルに沿い、専門性を保つ（#1729。規則は [agents/ontology-standard.md](./agents/ontology-standard.md)）。画面の説明・診断は平易な日本語にするが、中身の構造は崩さない。生成は best effort で、無い項目は空でよい（推測で埋めない）。

| 標準 | このオントロジーの項目 |
| --- | --- |
| Foundry の Object Type: display name・API name・description・primary key・title property・backing datasource | オブジェクト型（Object Type）: `name_ja`・`api_name`（snake_case）・`description_ja`・`primary_key`・`title_property`・`mappings`（表・ビュー） |
| Foundry の Property: base type・physical type・required・unit・description・所属 | プロパティ（Property）: `data_type`（業務の型 string / integer / number / boolean / date / datetime）・`physical_type`（精度・桁を含む DB の型。DB の列が正）・`required`（NOT NULL の列は必須）・`unit`・`description_ja`・`object_type` |
| Foundry の Shared Property | 共有プロパティ（Shared Property）: 複数のオブジェクト型で同じ意味のもの。オブジェクト型は自分の表の列のプロパティを持ち、`shared_property` で共有プロパティを指す |
| Foundry の Link Type: 両端・cardinality・foreign key・各向きの名前 | リンク型（Link Type）: `source` / `target`・`cardinality`・`join_expression_sql`（結合のキー）・`name_ja` / `inverse_name_ja` |
| SKOS: prefLabel・altLabel・definition | `name_ja`（優先ラベル）・`aliases`（別ラベル）・`description_ja`（定義） |
| semantic layer の metric: measure・aggregation・dimension・grain・time dimension・filter | 指標（Metric）: `expression_sql`（測定値）・`aggregation`（集計方法）・`grain`（ディメンション。集計の粒度を決める）・`time_property`（時間のディメンション）・`filter_sql`（絞り込みの条件） |

- 記述は日本語が主で、専門用語は「日本語（英語）」で併記する。訳は `backend/app/features/nl2sql/ontology_terms.json` の 1 つの対応表に置き、Markdown の生成（`render_concepts`・`render_llm_context`）・診断の文・画面の i18n（`ontologyResults.kind.*` / `ontologyResults.field.*`）が同じ訳を使う。物理の名前（表・列・API 名・SQL）は訳さない。
- AI 構築の生成の指示（`ontology_build.py` の system prompt）にこの標準を書き、出力は Pydantic のモデル（`ontology_definitions.py`）で形をそろえる。

## 構築

1. 範囲・資料の準備：Profile、Schema、構築資料、Q/A、業務説明を固定する。
2. 関連概念の構築：各入力バッチから主要6種類・補助7種類をまとめて抽出する。共有定義・能力契約を別工程で再生成しない。
3. 統合・検証：同一性、参照、SQL 式、物理範囲、業務上の不足を確認する。
4. Markdown 下書き生成：13分類の順に定義・証拠・確認事項を出力する。Q/A 由来 SQL ルールと物理情報を保持する。
5. 保存・最終確認：下書きと派生データを保存する。

Q/A 由来の Link Type は、JOIN 条件が参照する物理列を SQL AST で解決し、同一バッチ内の同じ Q/A SQL に存在することを統合前に検証する。表別名・CTE・引用識別子を考慮し、根拠を確認できない候補だけを除外して対象定義と理由を警告へ残す。SQL 条件式全体の意味同値を判定するものではない。資料・スキーマからの独立した抽出結果は保持する。

Q/A の補助的な `DUAL` / `SYS.DUAL` 参照は SQL の名前解決に限って扱い、そのシステム列を業務列の根拠には追加しない。Profile の同名業務表と CTE は元の名前解決を維持し、未知の表・列は引き続き拒否する。同一入力の追加抽出で空の JOIN 条件を補完できた場合、未補完版も根拠・別名・他フィールドの競合を保って統合し、補完済み空欄の拒否警告は生成しない。非空の不正な条件や未補完の関係に対する警告は保持する。

取りこぼし確認は既存設定 `nl2sql_ontology_extraction_gleaning_passes` に従い、既定で最大1回行う。入力上限内で未抽出候補・不足フィールドのみを補い、全文を再生成しない。資料分割、再試行、キャンセル、部分成功は維持する。

既存タスクの記録・警告は改変せず、旧 `objects/shared/capabilities` を「関連概念の構築」に統合表示する。新タスクのイベントには工程識別子を記録し、5段階の件数・概念一覧・処理ログを同じ工程に集約する。完了した工程は折りたたみ可能。失敗時も成功した抽出を保持し、再実行では既存 checkpoint を再利用する。

`title_property` は空文字を許す任意項目である。JSON のキー出力要件と業務上の値の必須要件を区別し、根拠がない空欄を資料不足にしない。設定時は参照先の存在・Property 型・所属オブジェクトを検証する。主識別子・物理マッピング等の実際の不足や不正参照は対象定義とフィールドを付けて報告する。修正した生成指示は新規構築・再構築から適用し、保存済み警告・公開済み定義は保持する。

## Markdown の公開

- 下書きを保存して `POST /profiles/{profile_id}/ontology-markdown/prepare` に ETag と `Idempotency-Key` を渡す。
- 準備タスクは Markdown、元 revision、Profile / Schema の fingerprint、期待する公開 head を固定する。下書きの決まった形（`#### 種類` → `##### 表示名 (`API 名`)` → `- 項目: 値`。#1729 より前の項目名も読む）は、自由な行が混じっても常に `ontology_markdown_parser.parse_markdown_rules` が決定論で読む（#1735）。読めない項目の行はその行だけを外し、定義の残りの項目は読む。
- OCI Enterprise AI には、決まった形で読めなかった行（自由な行）だけを行番号つきで渡す（下書き全体を渡さない）。LLM の結果は決定論で読めた定義を変えない（API 名の重ならない定義を、行の対応があるときだけ足す）。LLM が見つけた矛盾は警告にし、公開を止めない。LLM が未設定・失敗でも、決まった形で読めた定義があればそれだけで確認を続ける（決まった形の定義が 1 つも無い Markdown だけは、LLM の解析が要る）。
- 定義にならなかった自由な行は **業務メモ** として Markdown に残し、公開を止めない。どの行を定義として読めなかったかを「補うと精度が上がる項目」に平易な 1 件（`MARKDOWN_BUSINESS_NOTE`。行の範囲は「技術的な詳細」）で示し、準備の結果の `notes` に行と本文を返す。
- 自由な行の LLM の解析の結果は、Markdown と schema の hash ごとに成果物（`ontology_markdown_free_lines_parse`）に保存して使い回す。同じ Markdown なら公開前の確認を何度やり直しても結果（エラー・警告・未解決の件数）は同じになる。
- 節・種類の見出しと空行は定義ではないため、公開を止めない。解釈できない定義の見出し（`#####`）、概念の欠落、競合、静的検証エラーがあれば公開できない。
- `GET .../preparations/{preparation_id}` で進捗、解析した定義（`definitions`）、前の公開版との差分（`differences`）、検査事項（`findings`）、業務説明に追記する改善案（`suggestions`）、解析の経路（`parser`: `rule` / `llm`）を確認する。必要に応じて `POST .../preparations/{preparation_id}/validate-data` で標本データと受入テストを検証する。
- 確認ダイアログは Profile と実際の公開版を示す。`POST .../publish` は preparation ID、draft ETag、expected head、確認フラグ、冪等キーを必須とする。確認後に LLM を再実行しない。
- Markdown、構造化定義、graph、OWL / SHACL / 検証結果を一つの immutable snapshot に保存し、draft と head の CAS を含む同一 transaction で公開 pointer を更新する。失敗時は旧 head を維持する。
- 公開成功後は Markdown とグラフを再取得する。公開後の編集は次の下書き版を作り、以前の公開本文と成果物を書き換えない。

準備後に Markdown / Profile / Schema / 公開 head が変わった場合は再確認する。公開応答が失われた場合は `GET .../publication-outcome?key=...` で照会し、自動再送しない。準備タスクの再開時に解析済み結果を再利用し、中断して結果のない LLM 呼出しは黙示再送しない。

### 公開診断と警告の保持

- 診断は 3 段階（#1720）。**error**（公開を阻止）は graph が壊れて SQL の接地に使えないものだけ（物理の表・列が無い / 業務プロファイルの範囲外 `MAPPING_OUTSIDE_PROFILE`、参照先の概念が無い `REFERENCE_INVALID`、他オブジェクトのプロパティ `PROPERTY_OWNER_MISMATCH`、不正な SQL 式、Markdown の解析が報告した矛盾、標本検証の error）。**warning** は公開できるが SQL の意味に効くもの（指標の式・集約が無い、同じ概念の値の食い違い `DEFINITION_CONFLICT`。先の値を使う）。**info** は graph を作れるが補えば精度が上がる項目（識別子 `OBJECT_IDENTITY_REQUIRED`・粒度 `OBJECT_GRAIN_REQUIRED`・型・基数・根拠 `INFERENCE_WITHOUT_EVIDENCE`・不足情報）。view など制約の無いオブジェクトは識別子が未設定のまま公開できる。
- 診断の文は利用者が読む平易な日本語で、「何が問題か（業務の名前）」と「どうすればよいか（何もしなくてよい / Markdown のどの行をどう直す / 業務プロファイルに表を足す など）」の 2 文にする（#1729）。統合の競合も「『従業員』の『部門ID』の業務の型が 2 通り（…）作られました。… を使います。違う場合は Markdown の『部門ID』の「業務の型」の行を直してください。」の形にする。
- error / warning は最大18remの縦スクロール領域に表示し、同一 severity・メッセージを1回に集約して、件数と対象（概念の業務の名前）を出す。内部の ID・項目名・診断コードは「技術的な詳細」に畳む。info は「補うと精度が上がる項目」の 1 つの畳んだ領域にまとめ、公開の状態は「公開できます」のまま（警告の帯を出さない）。表示上の集約で元の診断を削除しない。
- 根拠（evidence）は定義ごとに 1 件だけ照合の結果を出す（evidence ごとに重ねない）。DB の schema を根拠にした evidence（`source_id=schema` / `source_kind=database`、位置は `OWNER.OBJECT[.COLUMN]` の並びや結合条件）は、資料の検証値が無くても、物理の表・列が業務プロファイルの範囲にあれば照合済みにする。
- 公開前の確認の見出しに「公開すると何が変わるかを確かめる所」と書く。並びは 公開を止める問題の帯 → **業務説明に追記する改善案** → エラー・警告 → 補うと精度が上がる項目 → 公開するオントロジーの構成 → 概念ごとの差分 → 実データの検証。
- **業務説明に追記する改善案**（#1729。`ontology_improvement_suggestion.improvement_suggestions`）: 残ったエラー・警告・補うと精度が上がる項目から、業務説明（自然言語）に追記して「AI 構築を実行」をやり直すための業務の言葉の文を、LLM を使わず決定論で作る（オブジェクト型と表の対応・主キー・粒度・関係の結合のキーと多重度・型の食い違いは DB の列の型）。公開を止めるエラーを解く文を先に並べ、分からない値は推測で書かず「（○○を確認して書いてください）」と空ける。エラー・警告が無いときは出さない。既に業務説明に書かれた文は重ねて出さない。「コピー」と「業務説明に追記」（押したときだけ業務説明の後ろに足す。自動で書き換えない。#1727）を置く。
- 公開するオントロジーの構成（オブジェクト型・リンク型・プロパティの件数と、オブジェクト型ごとのプロパティとリンク型）を示す。値型など内部の概念は数えず、同じ名前のプロパティには属するオブジェクト型の名前を 1 回だけ添える（名前に既にあれば添えない。同じ定義を重ねて数えない）。
- **概念ごとの差分**（#1729）は前の公開版から何が変わるかを示す。既定では確認が要るもの（公開を止める問題・警告のある概念と、削除）だけを件数とともに上に出し、問題の無い変更は「問題なし N 件」に畳む。初回の公開（すべて追加）は「初めての公開です。N 件の概念を追加します」の 1 行と確認が要るものだけにし、「追加」のバッジを並べない。1 行ごとに業務の名前と、平易な 1 文（何が変わるか / 何が問題か / どうすればよいか）を出し、API 名・ID・前後の値は「技術的な詳細」に畳む。
- 公開時点の `findings` と `data_report` は immutable snapshot に含める。後続の公開でも旧版の記録は変更しない。公開済みタブで確認し、版 ID を含む JSON をダウンロードできる。
- 過去版は `GET /api/nl2sql/profiles/{profile_id}/ontology-markdown/publications/{snapshot_id}/diagnostics` で取得できる。Profile の閲覧権限と snapshot の Profile 所有権を確認し、元の findings・標本検証レポートを返す。
- 旧 snapshot に診断 field がない場合は保存済み preparation を参照する。記録が残っていない場合は `available=false` として区別し、「警告なし」とは扱わない。再解析・再検証は行わない。

## SQL とグラフ

接地確認グラフは、選択 Profile の公開 Markdown revision が存在し、取得した graph の revision が一致する場合だけ表示する。未公開時は公開を案内する空状態とし、物理 Schema の fallback を公開図として扱わない。公開後・再試行時は公開状態と graph を再取得し、版不一致時は旧図を表示せず再試行を案内する。Profile 切替や graph の版変更時は以前の接地・サーバ検索結果を保持しない。

通常生成、非同期 job、引導式 session、サーバー接地検索は Profile の同じ公開 snapshot を使用する。job / session の `business_release_id` は snapshot ID を保持する。以前の独立 release を新しい生成へ重ねない。過去の release / job の読み取りは互換性のため残す。

SQL 生成・チャットの job（同じ `_run_job`）は、公開版があればその公開版だけを使い、無ければ使わない。job の中でオントロジーをその場で構築・同期しない。準備の段階の prompt の文脈も、結果の整形の段階の接地確認（`interpretation.ontology_graph`）も、job が確定した `business_release_id` の公開版（snapshot、旧方式は公開中の版）だけを読む。公開版が無い job は接地確認をせず、`interpretation.ontology_grounding_skip_reason` を `no_published_ontology` にする。SQL 生成の画面はこれを失敗ではなく「公開版なし」と情報の Banner で示す（#1168）。ジョブの要求の `include_ontology_grounding`（未指定は `use_ontology_context` に従う）が false のときは、生成の prompt の文脈には公開版を使ったまま、接地確認のグラフを読まない。チャットはこの値を false で送る（画面に接地確認を出さないため。ログの `skip_reason` は `grounding_not_requested`。#1172）。

引導式生成の正式指標には `expression_sql` と指標固有の `filter_sql` を渡す。絞り込み条件はその指標の集計対象だけに適用し、他の指標の全体 WHERE 条件へ流用しない。過去の読み取り投影に条件がない場合は、同じ snapshot の完全な型付き定義から復元する。保存済み artifact は書き換えない。

Interface の接地は下位の継承・実装を辿る。子 Interface の検索で上位だけを実装する object や兄弟 Interface の実装へ広げず、上位 Interface の検索では配下の実装を含める。Profile の node / edge 範囲は各段階で守る。

グラフには12種類の型付きノードと Link Type の選択可能な関係辺を投影する。Markdown と概念 ID を共有し、定義の説明・型固有フィールド・マッピング・証拠を詳細に表示する。「概念の種類」は主要6／補助7にまとめ、存在しない種類は該当なしとする。全体／接地パス／物理 ER を維持し、Function / Action の詳細に実行ボタンを出さない。物理マッピングを持たない概念は参照先のオブジェクト付近へ配置する。

## 型付き graph の意味と検証

新規構築・Markdown 公開では同じ `definitions` から次を投影する。保存済み snapshot は書き換えない。

| 定義・情報 | graph / RDF / SHACL への反映 |
| --- | --- |
| Object Type / Interface | OWL Class。Interface の `extends` は `rdfs:subClassOf`、実装契約は `ont:implementsInterface` として区別する。 |
| Property | 所属 object への `domain` 辺と `rdfs:domain`。基本型または Value Type を `rdfs:range` に出力する。 |
| Shared Property / Value Type | 再利用参照と基本データ型を保持する。具体 Property に許容値を適用する。構造化 `object` の値型は独自語彙に保持し、XSD の基本型とは扱わない。 |
| Enumeration | SKOS ConceptScheme と、定義 ID・コードから安定 ID を作る Concept メンバー。`skos:hasTopConcept` / `skos:inScheme` / `skos:notation`。メンバーは13分類の追加定義として数えず、「列・列挙値を表示」で展開する。 |
| Function / Metric | `ont:dependsOn`、指標の `ont:hasGrain` / `ont:timeProperty`、式・集計・単位等の宣言。 |
| Action / Event / Object Set | 所属 object、影響属性、時刻属性などを具体的な述語で参照する。実行操作は提供しない。 |
| Business Rule | `ont:appliesTo` と条件式の宣言。SQL 文字列を自動で SHACL に変換しない。 |
| Link Type | 選択可能な関係辺・OWL ObjectProperty。別定義からの必須リンク参照は、RDF では両端 object ではなくリンク自体の IRI を参照する。 |
| 根拠・物理対応 | `prov:wasDerivedFrom` で資料 ID・位置・引用・検証状態へ接続する。物理マッピングは owner / object / column / SQL 式を保持する独立リソースにする。R2RML の実行系を導入するものではない。 |

SHACL は具体 Property の基本型、必須値（主識別子を含む）、許容値と列挙範囲、Link Type の対象クラス・任意性・両方向の最大基数を検査する。共有属性の列挙制約は、それを参照する具体 Property に適用する。未知の基本型や任意 SQL の意味を推測して「検証済み」にしない。OWL の推論と、対象データに対する SHACL の適合検査は別の処理である。定義グラフだけの SHACL 成功は実 DB の全行が適合することを保証しない。

列挙コードの重複・型に合わない許容値・共有型との不一致は対象定義とフィールド付きで報告する。Enum メンバーから旧形式へ変換して定義を二重生成せず、範囲を絞った検索では親定義と所属 object の範囲を守る。物理 ER には型付き定義から派生した Enum メンバーを混在させない。

語彙の参照: [OWL 2](https://www.w3.org/TR/owl2-primer/)、[SKOS](https://www.w3.org/TR/skos-reference/)、[SHACL](https://www.w3.org/TR/shacl/)、[PROV-O](https://www.w3.org/TR/prov-o/)。`ont:*` は本システムの語彙であり、これらの標準述語とは区別する。

## 廃止 API

既存定義を Markdown 草稿へ取り込む UI と専用の `POST .../migration-preview` / `POST .../migrate` は廃止した。旧 endpoint は 404 を返す。保存済みの草稿・公開版・成果物は保持する。

独立した定義の編集・解析・適用・レビュー・検証・公開・切戻し、能力 binding / invoke / preview / execute の HTTP mutation は認証・Profile アクセス検査後に `410 Gone` を返す。歴史的な構築結果・公開履歴・実行結果の GET は読み取り専用で残す。

Markdown 草稿と保存基準、表示タブ、業務説明、準備 ID、公開結果の照会キーはユーザー・DB・Profile を分離して同じタブに一時保存する。共通の有効期限・保存容量制限・離脱ガードを適用する。旧能力の草稿を実行操作として復元しない。

### 構築 Markdown と公開時の定義

Markdown は業務名称・属性・関係・必要な表列対応を記載し、概念 ID、evidence の構造、開発診断、入力件数、未生成分類の空テンプレートは出力しない。業務上必要な補足は残す。根拠と診断は構築結果および下書き revision ごとの `ontology_markdown_generated` 成果物に保存する。抽出失敗の通知と公開版の検証記録は維持する。

生成時の定義と Markdown のハッシュを対応づけ、未編集の稿を公開する際は対応定義を再利用する。Profile / Schema / 参照 / SQL の機械検証は再実行する。編集済みの稿は再解析し、削除した定義を過去の構築結果から復元しない。旧形式の稿も再解析するが、内部診断行を業務本文として扱わない。

同じ業務オブジェクト・同じ物理列に対応する同名属性の snake_case / PascalCase を統合し、参照を合わせる。異なる意味や所属先の属性は統合しない。同一属性の integer / number は、根拠のない整数制約を加えない number に合わせる。表対応の表名を誤って SQL 式にも出力した場合は、表対応を維持して冗長な式だけを除去する。実際の列 SQL や曖昧な参照の検査は省略しない。

AI 構築の出力は best effort で graph にする（#1720）。マッピングの列 `*` は表・ビュー全体の対応（列なし）として扱う。オブジェクトの properties / 識別子が他のオブジェクトのプロパティ（同じ列名を 2 つの view で共有した `DEPARTMENT_NAME` など）や未定義の名前を指すときは、そのオブジェクトの表に同じ列があればオブジェクトごとのプロパティ（`v_emp_dept_department_name`）を作って付け替え、列が無い参照は外す（推測で列を足さない）。種類ごとの空の雛形・同じ列の重複したプロパティ・空の項目を書き写した不足情報は、AI の出力からだけ除く（利用者が Markdown に書いた定義は消さず、検証の診断に任せる）。統合では参照の一覧（properties など）を和集合にし、基数の `unknown` は未設定として分かった値を使う。生成の指示も、情報が足りない項目は推測で埋めず空のままにし、外部キーが無くても同じ名前・型の ID 列から関係を作るよう求める。

**同じ物の統合と関係（#1729）**（`ontology_unified_model.repair_definitions_report`。AI 構築と公開前の確認の両方）:

- 同じ表・ビューを指すオブジェクト型は 1 つにまとめる。表の対応が無いオブジェクト型は、所属のプロパティの列がすべて 1 つの表にあればその表を対応にし、なお無ければ名前・別名が一致する表のあるオブジェクト型に寄せる（「部署」`ADMIN.DEPARTMENT` と「部門」`department`）。残すのはプロパティ・関係の多い方で、他方の表示名は別名にする。内部の ID（`profile_concept_…`）は別名にしない。
- 同じオブジェクト型の同じ列のプロパティ、同じ両端・結合のキーのリンク型を 1 つにする。種類の違う同じ API 名は、オブジェクト型・プロパティ・リンク型を残し他方に種類の名前を付けて分ける。
- 共有プロパティ（と値型）の同一性は、名前ではなく、それを使うプロパティの物理の列の組（と自身の列。業務の型も同じもの）で決める（#1734）。同じ列の組のものは 1 つにまとめ、どのプロパティからも使われないものは表示名と業務の型が同じものに寄せる。まとめるときは前の定義（下書き・公開版）の名前を残し（同じ列のプロパティも同じ）、他方の表示名は別名（altLabel）にする。利用者の名前を AI の名付けで上書きしない。
- AI 構築では、どのプロパティからも使われない共有プロパティのうち、AI が作ったもの（`origin: ai`）だけを下書きから外し、構築の注記で知らせる（前の公開版にあれば、公開前の確認の差分に「削除」として出る）。利用者が作ったものは残す。AI の出力の `origin` は常に `ai` にし、公開前の確認では、AI 構築の生成物と同じ内容のまま（Markdown に書く項目が同じ）の定義だけ `ai` を引き継ぐ（利用者が触れた定義は `manual`）。
- AI 構築では、対応する列の無い AI のプロパティ（#1736。AI が列を共有プロパティにだけ書いたもの）は、参照する共有プロパティ・値型の列のうち所属のオブジェクト型の表の列（ちょうど 1 つ）か、所属の表の API 名と同じ名前の DB の列で補う。決まらなければ下書きから外し、構築の注記で知らせる（graph に置けず、公開を止めるため）。前の定義（下書き・公開版）と利用者のプロパティは外さない。
- AI 構築では、結合のキーの無い AI のリンク型（#1736）は、同じ両端の結合のキーのあるリンク型に寄せ（表示名は別名）、同じ両端に結合のキーの無いものしか無ければ 1 つにまとめる（残すのは前の定義の名前）。ビューと元の表・ビューの依存（data lineage）だけで結合のキーの無いもの（`v_dept_project` → `department`）は、つなぐ列が無くリンク型にならないため下書きから外し、構築の注記で知らせる。補った結合のキーが既存のリンク型と同じなら 1 つにする。前の定義と利用者のリンク型は外さない。結合のキーのあるリンク型からは、結合のキーの不足情報（「join_expression_sql が不明」など）を除く。
- リンク型の結合のキーは、外部キーの制約の列、どちらかの端の表の主キー・一意キーの制約の列（の組）、制約の無い表・ビューならオブジェクト型の主キーに対応する列か制約の無い表の「表名_ID」の列のどれかに当たるときだけ「キーでつなぐ」とみなす（#1741。`ontology_link_keys.link_join_check`）。部門名（`DEPARTMENT_NAME`）のような一意でない列でつなぐと多対多になりうり、Select AI / LLM が誤った JOIN を作るため。AI 構築では、当たらない AI のリンク型の結合のキーを外し、外部キー・同じ名前・型の ID 列の結合のキーで付け替える（同じ両端に結合のキーのあるリンク型があればそちらに寄せる）。付け替えられなければ下書きから外し、構築の注記で知らせる。前の定義と利用者のリンク型は外さず、検証（公開前の確認）の警告（`LINK_JOIN_NOT_UNIQUE`）で知らせる。同じ両端にキーでつなぐ結合のキー（外部キーの制約、または同じ名前・型の列が片方の端の主キーであるもの。`ontology_link_keys.suggest_link_join`）があれば、2 文目の「どうすればよいか」に「「結合のキー」を DEPARTMENT_ID でつなぐ形（…）に直してください。」と具体の結合のキーを書き、無ければ両端が主キー・一意キー・外部キーの列で一意につながるかを確かめ、無ければリンク型を削除するよう書く（#1760）。改善案（「コピー」「業務説明に追記」）にも「A（a）とB（b）のリンク型『名前』（api）は、<結合のキー> でつなぐ（多重度）。」の文を出す（付け替え先が無ければ結合のキーを「（…を確認して書いてください）」と空ける）。業務説明に追記されたこの文は、次の構築で、一意でない列でつなぐリンク型（前の定義・利用者のものも）だけを、文の結合のキーがキーでつなぐと確かめられるときにその結合のキー・多重度に直す（`apply_business_text_links`。修復の前に直し、同じ両端・結合のキーの AI のリンク型とは 1 つにまとめ、前の定義の名前を残す）。改善案は利用者が使ったときだけ業務説明に入るため、利用者の定義は確認なしに変わらない（#1727）。式が単純な列の等号でないときは判断しない。AI への指示にも、結合のキーを外部キー・主キー・一意制約の列に限ることを書く。
- まとめても表が決まらないオブジェクト型と、それに属する定義は公開に含めない（公開を止めず、警告で知らせる）。
- 任意の関係（Optional）は、結合のキーのあるリンク型なら起点の結合のキーの列の NULL 可（DB の列）で決める（必須と同じく DB の列が正。#1736）。この値の競合は出さない。
- 業務の型・物理の型・必須は DB の列が正。列で値が決まった競合と、同じ列のプロパティの統合で同じ定義を指すようになった参照の競合は出さない。表示名が列名のまま（`BUDGET`）のプロパティは、同じ列名の別のプロパティの業務の名前を使う。
- AI 構築では、AI が作らなかったリンク型を、外部キーの制約か、同じ名前・型の列（相手の表の主キー。制約の無い表は「表名_ID」）から作る（多対 1、両方の向きの名前つき）。片方の列の型が分からない（空）ときは、型を一致とも不一致ともせず、名前と相手の主キーとの対応で作る（#1733）。起点の列の組が起点の主キー・一意キー（制約。ビューのように制約が無ければオブジェクト型の主キー）なら 1 対 1、そうでなければ多対 1 にする（#1736。`v_dept_project.PROJECT_ID = project.PROJECT_ID` は 1 対 1）。`ID` だけの列名や、両方の主キーが同じ列は推測しない。AI の式（業務ルール・指標など）の SQL が確かめられなければ、下書きに入れない。
- 業務説明に追記された改善案の文（下の「業務説明に追記する改善案」の形）の粒度・主キーは、AI が読み落としても定義に入れる（「（…を確認して書いてください）」のままの所は使わない）。AI の出力の粒度・主キーより業務説明の文を正にし、前の定義（下書き → 公開版）の値は変えない（#1759）。
- **粒度（Grain）の統合（#1759）**: オブジェクト型の粒度は、文ではなく 1 行を特定するキーの列の組（主キーのプロパティの列）で比べる。正は 前の定義（下書き → 公開版）→ 業務説明の文 → DB の主キー・一意キーの制約の列の組に当たる方 の順。前の定義があれば AI の出力の言い換え（「1 行が 1 つの部署」と「部署」）は競合にしない。AI の出力どうしでも、キーの列の組が同じか、キーが分からなくても同じ表・ビューに対応するなら競合にしない（表も分からなければ、「1 行が 1 つの」「ごとに 1 行」「単位」を除いた文で比べる）。キーの違う粒度で、業務説明・DB の主キーでも決まらないものだけを `DEFINITION_CONFLICT` の警告（平易な 2 文。どちらか（キーの列）と、業務説明への書き方）にし、改善案にはどちらかを空けたオブジェクト型の文を出す。
- **多重度（Cardinality）の統合（#1765）**: リンク型の多重度は、結合のキーの列の組が両端の主キー・一意キー（制約。制約の無い表・ビューはオブジェクト型の主キーか「表名_ID」。`link_join_check` と同じ規則）を含むかで決める（`ontology_link_keys.link_cardinality`。両方なら 1 対 1、終点だけなら多対 1、起点だけなら 1 対多。外部キーの列の NULL 可は任意の関係（Optional）で表す）。正は 前の定義（下書き → 公開版）→ 業務説明の文（リンク型の文の「でつなぐ（多重度）」とオブジェクト型の文の「COLUMN で〈相手〉に属する（多重度）」。`business_text_cardinalities`）→ 結合のキーと両端のキー の順。前の定義があれば AI の出力の揺れは競合にせず、AI のリンク型は業務説明か結合のキーで決まる値にそろえる（`settle_link_cardinalities`）。前の定義の多重度は変えない。どれでも決まらない AI の出力どうしの食い違いだけを `DEFINITION_CONFLICT`（平易な 2 文）にし、改善案にはどちらかを空けたリンク型の文を出す。

**AI 構築の LLM に渡す前の定義と直すべき点（#1734）**（`ontology_build_prior`・`MarkdownOntologyWorkspace.prior_build_context`）: 各抽出の入力に、前の定義の要約（`previous_ontology`）と前回の公開前の確認の直すべき点（`previous_check_findings`）を足し、「既存の名前と対応を保ち、根拠があるものだけを足す・直す」と指示する。

- 前の定義の基準は、下書きがあれば下書き（公開版＋利用者の編集。Markdown を決定論で読んだ定義）、無ければ公開版、どちらも無ければ無し。渡すのはオブジェクト型・プロパティ・リンク型・共有プロパティの API 名・表示名・別名・物理の表と列（リンク型は両端と結合のキー）だけ（説明・根拠は渡さない）。
- 直すべき点は、最後の公開前の確認（`ontology_markdown_last_check`。無ければ公開版の診断）のエラー・警告・補う項目を、業務の名前の平易な文にしたもの（ID・診断コードは渡さない。最大 40 件）。
- 前回の構築で下書きから外したもの（表の決まらないオブジェクト型・確かめられない SQL の式・使われない共有プロパティ・列の決まらないプロパティ・結合のキーの無いリンク型・一意でない列でつなぐリンク型）も、直すべき点の先頭に入れる（#1742。`ontology_build_last_removals`・`plain_build_removals`。最大 20 件）。何を（業務の名前・API 名・物理の名前）、なぜ外したかと、どうなら作ってよいか（「列が分かるときだけ」など）を書き、「外した理由を解消できる根拠が無ければ同じものを作らない」と指示する。外したものが無い構築は空で上書きする（前の注記を残し続けない）。
- 入力の上限（`_ensure_llm_call_fits` と同じ上限）を超えるときは、前の定義の要約（プロパティの別名 → プロパティ・リンク型 → 共有プロパティ → 全部）から削り、直すべき点を優先して残す。
- 抽出が失敗して batch を二分割した子のタスク・入力の上限で分けた子のタスクにも、同じ要約と直すべき点を付け直す（#1736）。
- LLM の入力は手がかりにすぎず、決定論の併合と検証を今どおり正とする（LLM が前の誤りを写しても、物理の表・列の検証と併合で落とす）。

**業務プロファイルの削除（#1743）**: 業務プロファイルを削除すると、その業務プロファイルのオントロジーの成果物（`NL2SQL_ONTOLOGY_ARTIFACTS`。構築の checkpoint・下書き・公開前の確認・公開版の Markdown など、payload の `profile_id` か `session_id` の `profile-ontology:<profile_id>` が業務プロファイルのもの）と、終わったジョブの記録（`NL2SQL_ONTOLOGY_JOBS`）を、業務プロファイルの削除と同じ transaction で消す（`OracleIncrementalNl2SqlRepository.delete_profile`）。成果物の表は `PROFILE_ID` の列を持たないため FK の `ON DELETE CASCADE` では表せない。前に削除した業務プロファイルの残り（孤立の成果物）も、同じ文で消す（存在しない業務プロファイルの成果物だけ。所有者の無い成果物・全体のジョブ（`profile_id` が `-`）には触らない）。実行中のジョブの行は消さず、削除の後に取り消す（worker が読む行を消さない）。構築の worker は checkpoint を保存する前に業務プロファイルがあるかを確かめ、削除の後に孤立の checkpoint を作らない。業務プロファイルの ID は作成ごとの UUID のため、同じ名前で作り直した業務プロファイルが古い checkpoint を使うことはない。存在しない業務プロファイルの成果物と終わったジョブの記録は、業務プロファイルの削除に加えて、system schema の冪等な初期化（画面の「作成・更新」と配備の `nl2sql_system_schema --initialize`。全再作成を除く）のたびにも消す（#1758。`incremental_store.purge_orphan_profile_ontology_records`。削除が途中で失敗したもの・#1743 より前の残りを片づける。失敗しても初期化は失敗にしない）。Oracle の永続化は常に entity 単位の repository で、移行前互換の `NL2SQL_STATE_BACKEND=legacy_snapshot`（1 行の snapshot に保存し、この削除を通らない経路）は廃止した（未リリースのため互換を持たない）。旧 snapshot の表を読む store・移行の CLI（`nl2sql-migrate-state`）・`NL2SQL_ORACLE_STATE_TABLE` も、実行時の経路ではなく移行するデータも無いため削除した（#1765）。memory の永続化（テスト・CI）は `delete_profile_state` が同じものを消す。

**前の定義の説明・更新可能（#1736）**（`merge_definitions(previous=...)`）: 再構築では前の定義（下書き → 公開版）の説明を正にし、AI の出力の言い換えを連結しない（説明が表名・API 名だけのときは業務の説明に置き換える）。同じ回の抽出の説明は、同じ文（行と ` / ` の区切りの単位。空白の違いは無視）を重ねない。更新可能（Writable）は前の定義の値を正にし、AI の出力どうしで食い違うときは、アクション型（Action Type）が値を書き換えるプロパティだけを更新可能にする（推測で更新可能にしない）。どちらも競合（警告）にしない。利用者の Markdown どうしの食い違いは今どおり警告にする。

**DB の列の型（#1733）**: カタログ（`fetch_catalog`）の列の型は、精度・桁・長さを含む物理の型（`NUMBER(12,2)`・`VARCHAR2(50)`・`VARCHAR2(100 CHAR)`）にする。ビューの列も表と同じく `ALL_TAB_COLUMNS` の型を使う。サンプルデータを DB を使わずに取り込む経路（deterministic）では、ビューの列の型・NOT NULL を元の表の列から取り、元の列が分からない式の型は空（不明）にする（`VARCHAR2` と決めつけない）。この経路は Oracle の永続化先のカタログ（`NL2SQL_SCHEMA_*`）を書かない（#1736）。`NL2SQL_RUNTIME_MODE` が `oracle` でないのに永続化先が Oracle のときは、サンプルデータの取り込み・削除を `blocked` で止める（DB を使わずに組み立てた 5 件のカタログで、実 DB から再取得した全件のカタログを上書きしない）。
