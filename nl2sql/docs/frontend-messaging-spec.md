## 3.3 FormStatus（NL2SQL 固有）

### SQL 実行エラーの具体的な対応例

- `DbAdminErrorNotice` は概要・原因候補・次の対応に加え、既知のエラーにはコピー可能な構文例を同じ結果領域に表示する。分類は statement の `error_code` を優先し、従来の Oracle メッセージは `ORA-xxxxx` を補助的に使う。日本語メッセージの部分一致で分類しない。
- `DB_ADMIN_COMMENT_SQL_POLICY_VIOLATION` は `COMMENT ON TABLE`（ビューも同じ構文）/ `COLUMN` / `MATERIALIZED VIEW`、`DB_ADMIN_ANNOTATION_SQL_POLICY_VIOLATION` と `ORA-11548` は表・列の `ANNOTATIONS` 例を共通の `dbAdminErrorRecovery` で管理する。未知のエラーには修正 SQL を推測表示しない。
- 構文例と対象に適用済みの修正 SQL を区別する。例の所有者・対象・列・説明文は利用者が実際の値へ置換する必要があることを明記し、コピーで入力変更・自動実行・確認ゲートの省略を行わない。
- コピーには共通 `Button` の `secondary` / `sm` を使い、例の名前を含む `aria-label` を付ける。SQL はモバイル幅で折り返して表示し、コピー成功・失敗は既存 Toast で通知する。

### 3.3.1 業務プロファイルのエディタの保存の失敗（#585）

共通規約は [UX 契約 messaging.md §3.3.1](../../platform/docs/ux-contracts/messaging.md#331-全画面のエディタの保存の失敗585)。業務プロファイルのエディタ（`/profiles?profile=`）は、保存ボタンがヘッダーではなくフォームの中（実行確認語の欄と並ぶ）にあるため、欄に結び付かない保存（PATCH / POST）の失敗は保存ボタンの直下の `FormStatus`（`profile-save-error`）の 1 か所だけに出す。`toast.error` は出さない。名前の重複（409）は名前の欄の直下に出してフォーカスし、Oracle 同期の投入の失敗は今までどおりその下の保存結果の領域（`ProfileSaveResultRegion`）に出す。

## 11. 回答前の確認（SQL 生成の画面とチャットで共通。NL2SQL 固有。#1439 / #1442 / #1715 / #1727 / #1761 / #1772 / #1776）

共通の送信の規則は [UX 契約 messaging.md §11](../../platform/docs/ux-contracts/messaging.md#11-チャットの送信楽観的な表示907)。回答前の確認は **SQL 生成の画面の回答前の確認を基準**にし、チャットも同じ API・同じ hook（`useRequirementSession`・`useRequirementCheck`・`useRequirementProceed`）・同じ部品（`components/RequirementClarificationView.tsx`）・**同じ文言**で行う（#1715 / #1761）。確認事項と確かめて生成するカードは、3 製品共通の回答前の確認のカード（`ClarificationCard`。[UX 契約 confirm-before-answer.md](../../platform/docs/ux-contracts/confirm-before-answer.md)。#1839）で出し、NL2SQL は名詞（「SQL の生成」「SQL を生成」）・物理名と根拠（選択肢の `detail`）・要件の一覧とまとめを渡す。機能の名前は 3 製品の総称「回答前の確認」（旧名「AI要件確認」。#1839）で、i18n の `CONFIRM_FEATURE` の 1 か所から組む。画面ごとに違うのは入口（下の表）と、置く場所に合わせた操作部品の高さ（SQL 生成の画面は lg、チャットは sm）だけで、操作の文言を画面ごとに props で変えない。

| | SQL 生成の画面 | チャット |
|---|---|---|
| 入口 | 「回答前の確認」のボタンで開く。業務プロファイルの推薦と確定の後に session を作る（「ALL」は推薦から選ぶ） | 送信のときに自動で始める（`POST /query-sessions` の `chat: true`・`previous_job_id`。会話の前の質問と SQL を検査に渡す）。送信のボタンは同じ位置で「停止」になり、押すと確認を中止する（質問を入力欄に戻す） |
| 確認を終える（#2303 / #2311） | 「確認をやめる」は出さない。確認を終えるのは「確認せずに SQL を生成」だけで、パネルを閉じて質問の欄の質問のまま SQL を生成して実行する。開始の処理（業務プロファイルの推薦・確定・下書き）の最中も経過の行から進める | 「確認をやめる」は出さない。確認を終えるのは「確認せずに SQL を生成」だけで、質問を取り消さずに SQL の生成へ進む |

両方の画面で、AI の処理中（要件の下書き・回答の後の再検査）も経過の行の「確認せずに SQL を生成」で、応答を待たずに捨てて（回答の要求は中断）進み、届いた session はサーバーで中止する。確かめて生成するカード・検査の失敗・終わった確認・業務プロファイルの選択（SQL 生成の画面の「ALL」）でも「確認せずに SQL を生成」を出す（3 製品の契約。[confirm-before-answer.md](../../platform/docs/ux-contracts/confirm-before-answer.md) §4）。

両方の画面で同じ操作（#1761）:

| 操作 | 文言 | 振る舞い |
|---|---|---|
| 要件を確定して進む | 「この内容で SQL を生成して実行」（SQL の実行の権限が無いチャットは「この内容で SQL を生成」） | 要件を反映（`/apply`）し、その要件（`requirement_session_id`）で SQL を生成して実行する。SQL 生成の画面もパネルを閉じてそのまま生成と実行を始め（「SQL を生成して実行」を押し直させない）、質問の欄はそのままで、欄の下に「回答前の確認の要件を SQL の生成に渡します」と「SQL の生成前に確認した内容」（中は書き直した質問）を残す（同じ質問で押し直すと同じ要件で生成する）。業務プロファイルが変わるとき（「ALL」）は、確定した業務プロファイルに切り替えてから生成する |
| 確認事項に答える | 「この内容で回答」 | 1 件の確認事項への回答を送る（AI が要件を検査し直す）。送っている間は、カードがフォームと送った確認事項の警告（最低の基準の「SELECT と FROM が…」など）を消し、答えた内容と経過の行 1 つ（「回答を反映しています。…」・送った時からの経過時間・「確認せずに SQL を生成」）に置き換える（#2311）。応答の状態で次の確認事項・警告・確かめて生成するカードを出し直し、失敗したらフォームと入力を戻す |
| 確認せずに進む（#1839） | 「確認せずに SQL を生成」＋補足「前提を示して SQL を生成します。」 | 要件が生成に進める（SELECT / FROM が明確）なら、答えていない確認事項を AI の推測のまま反映して生成する（旧「残りを AI に任せて SQL を生成」）。進めないなら確認を使わずに作る（開いている session は中止し、チャットの会話には「確認せずに SQL を生成しました」を残す） |
| 自由入力 | 「その他（自由入力）」（対象の表の選び直しが無いカードは「直す内容」。#3366）と「直しを伝える」 | 確かめて生成するカードの直しとして送る（下の「確認のカード」） |

- **最低限だけを確かめる（#1715）**: 確認する（不足 / あいまいにする）のは、それが無いと SQL を 1 つに決められないものだけ（対象の表が特定できない・主な指標や列が複数の候補で決まらない・期間の基準の日付の列が複数ありうる・年度の開始月が分からない「今年度」・質問に書かれた条件の列や値が決まらない・同じ表の間の承認済みの関係が複数ある・結合の条件の無い表）。質問に書かれていない絞り込み・期間・集計・並び順・件数の上限・結合・サブクエリは「指定なし（使わない）」として確認しない（件数の上限は画面の既定の上限）。実行日から 1 つに決まる期間（「先月」など）と、承認済みの関係で 1 つに決まる結合の経路も聞かない。
- **利用者の質問を書き換えない（#1727）**: 利用者が入力した質問（入力欄の値・チャットの吹き出し）を、利用者の明示の操作なしに書き換えない（両方の画面で同じ）。回答前の確認が作った書き直した質問・要件は要件の表示（まとめ・「SQL の生成前に確認した内容」）に出し、SQL の生成にだけ使う。ジョブの `question` は利用者の質問のまま送り、backend は session の `original_question` と同じときだけ要件を渡す（`applied_requirement_spec`）。生成の質問は `JobCreateRequest.generation_question`（確かめた質問の文）。質問の欄を書き換えたら要件は渡さない（「質問の文を変えたため、…」）。
- **選択肢の無い欄の名前（#3366）**: 候補の無い確認事項は共通の「答え」（placeholder「答えを入力してください。表・列は TABLE.COLUMN の名前で書くと確実です」）。確認済みの一覧から候補の無い要件を「直す」ときは「直す内容」、「条件を追加」は「追加する条件」（押せない理由も「直す内容を書くと押せます。」「追加する条件を書くと押せます。」）。候補があれば「その他（自由入力）」のまま。
- **確認のカード（#1761。自動では反映しない）**: 確認の質問が 0 件（最低限が決まり、聞くことが無い）でも、全部に答えた後でも、要件のまとめ（書き直した質問・SQL の骨組み）の下に確認のカードを必ず出し、利用者が「この内容で SQL を生成して実行」を押すまで要件を SQL の生成に渡さない（#1715 の「聞かずに反映」はやめた）。カードには次を出す。
  - **対象の表の選び直し**: AI が決めた表（確定・推測で、まだ答えていない FROM）に、backend が業務プロファイルのほかの表を候補として添えたとき（業務プロファイルの表が 2 つ以上・質問が表の物理名を書いていない・FROM の表が 1 つ）だけ、「使用テーブルはこの表でよいですか？」のラジオで出す（今の表を選んだ状態）。別の表を選ぶと、その FROM の項目への回答になる。
  - **「その他（自由入力）」**（対象の表の選び直しが無く選択肢の無いカードは「直す内容」。選択肢が無いのに「その他」と言わない。#3366）: AI の解釈を直す指示。`item_id` `add:other` の自由入力として送り、backend は「そのほか」の回答の項目にして（書かれた表・列を FROM などに足さない）、AI の再検査（カードの上の「確認 n 回目（上限 m 回）」。最初の確認が 1 回目で、再検査のたびに 1 回増え、上限の回は「これが最後の確認です。…」を添える。上限の前なら）に直しの指示として渡す。
  - 直し（別の表の選択・自由入力）は「直しを伝える」で送る。直しを入力している間は「この内容で SQL を生成して実行」を押せない（入力した直しを捨てて、直す前の要件で進まない）。送った後は新しい要件で同じカードを出す（再検査が確認の質問を出せば 1 問ずつ聞く）。
  - **押せない理由（#1772 / #1776）**: 直しが未送信の間だけ、カードの操作の行の下（共通のカードの押せない理由。`blockedReason`）に次の 1 文を出し、無効の「この内容で SQL を生成して実行」の `aria-describedby` でこの文につなぐ（ボタンの文言は変えない）。文は直しの種類で選ぶ（候補を選ぶと自由入力は空になり、自由入力を書くと表の選択は外れるので、2 つが同時に未送信にならない）。
    - 自由入力（「その他（自由入力）」/「直す内容」）に文字がある（空白だけは除く。#1772）: 「入力した内容は「直しを伝える」で AI に伝えてから、SQL を生成してください。」
    - 対象の表で別の表を選んだ（#1776）: 「選んだ内容は「直しを伝える」で AI に伝えてから、SQL を生成してください。」
    - 入力を空にする・元の表に戻すと消え、ボタンは押せる。
- **MCP の「確認せずに SQL を生成」（#1839）**: `nl2sql_query` の `skip_clarification: true`（`requirement_session_id` と一緒に）で、利用者が確認せずに進めると選んだことを渡す。業務プロファイルの方針 `assume` と同じに、要件を反映できれば反映し、できなければ確認を使わずに作り、`requirement.status = skipped`（message に前提を示すよう書く）を返す。`answer` と一緒には指定できない。Agent の確認のカードの「確認せずに回答」が使う。
- **MCP（`nl2sql_query`）との整合（#1761）**: MCP は機械（Agent）の呼び出しで確認のカードを持たず、今までどおり確認の質問があれば 1 問を返し、無ければ要件を反映してジョブを作る（呼び出し元の Agent が利用者の確認を担う）。対象の表が決まらないときに質問にする判断（規則 11）は画面と同じ LLM の指示で行うので、MCP も同じ場面で対象を選ぶ質問を返す。
- **対象を推測で決めない（#1761）**: LLM の指示の規則 11。業務プロファイルに表が複数あり、質問の語（例: 「employee」の 1 語）が複数の表に当てはまりうる・1 つに決まらないときは、FROM を「要確認」にし、当てはまりうる表を候補にした 1 つの質問にする（最低限の要件の方針は保ち、ほかの細部は聞かない。prompt の版 `sql_requirement_v4_target`）。
- **つながらないビューを FROM から外す（#1991）**: 回答（例: 「… と結合する（ビューでもよい）」）や AI の推測が、同じ内容のビューと元の表を両方 FROM に入れ、承認済みの関係・外部キーでつなげないときは、FROM 以外の項目（SELECT・WHERE など）が列・SQL の断片で使う表が 1 つのまとまり（承認済みの関係でつながる表）に収まるなら、列を使わない別のまとまりの表・ビューを FROM から外して答える（外したことは FROM の項目の理由に出す）。どの項目も列を書かなければ AI が書き直した質問の文の表で決める。承認されていない結合は作らない（#1741）。FROM にビューが無い・使う列が 2 つ以上のまとまりにまたがるときは今までどおり「この業務プロファイルでは答えられません」を返す。
- **確認事項は 1 回 3 件まで（#1917）**: 実モデルは同じ質問でも確認事項の数が揺れる（2〜8 件）。LLM の指示（規則 12）に上限と優先度を書き、プログラムでも強制する（`MAX_OPEN_QUESTIONS`）。答えが大きく変わるもの（FROM → SELECT → 結合 → 期間 → WHERE → GROUP BY → ORDER BY → 件数 → サブクエリ → そのほか）から 3 件を残し、超えた分は聞かずに「AI の推測」にする（候補があれば先頭の候補、無ければ SQL の生成で AI が判断）。推測は確認済みの一覧に出て直せる。FROM・SELECT は最低の基準なので推測にしない。答えた後にプログラムの規則が推測の項目を開き直しても、そのときの上限の中で聞く（prompt の版 `sql_requirement_v5_cap`）。
- **選択肢の名前に内部の値を出さない（#1917）**: 選択肢・項目の名前・値・質問の文に、LLM が相対的な期間の種類の値（`this_month` など）を書いたら既定の名前（「今月」）に置き換える（構造化出力の Pydantic の検証）。ほかの英小文字の識別子は Schema の表・列の表示名に直し、直せなければ説明を名前にし、それも無い選択肢は出さない（「その他（自由入力）」で答えられる）。期間の表現が値のままなら、質問の文の期間の語で補う。
- **日付で書いた期間・質問に無い欄は聞かない（#1948）**: 日付・年月で書いた期間（「2025-04-01〜2025-06-30」「2025 年 4 月から 6 月まで」「2025 年 5 月」）は、その範囲（両端を含む）で確定し、「いつからいつまでですか？」と聞き返さない（年度は開始月が要るので今までどおり確かめる。`absolute_period_range`）。集計の単位・並び順の不足（候補も値も無い）は、質問に集計・並び順を求める語（「別」「ごと」「順」「多い」など）が無ければ「指定なし」にする（件数の上限の #1718 と同じ考え方）。
- **入力が SQL の文でも同じに確かめる（#1727）**: SQL の文かどうかは判断に使わない（画面・チャット・MCP の `nl2sql_query` とも、SQL の文で確認を飛ばさない）。判断は SQL を 1 つに決める最低限の情報があるかだけで、完全な SQL の文（例: `select * from employee`）は LLM が最低限を満たすと判断して質問 0 件になる（LLM の指示の規則 10。確認のカードは出す）。SQL 生成の画面の「回答前の確認」のボタンは、入力が空のとき以外は常に押せる。
- **確認が要る**: 1 問ずつ（選択肢・複数選択・自由入力）聞く。SQL の要件（物理名の欄）・まとめ（書き直した質問・SQL の骨組み）は両方の画面で同じ表示。答えるまでチャットは次の質問を送らない。
- **SQL の要件（AI の理解）**（#1718）: 両方の画面で同じ部品（`RequirementItemsList`）・同じ振る舞い（画面ごとの分岐を持たない）。値のある部分だけを 1 行ずつ（項目名・値・状態・「直す」）並べ、値の無い部分は控えめな「指定なし: 結合・期間・…」の 1 行と「条件を追加」（部分を選び、その部分の自由入力を回答欄に出す。`item_id` は `add:<section>`）にまとめる。状態は「確定」（質問から明らか・答えた）/「AI の推測」（値があり、違えば直す）/「要確認」（AI が SQL を 1 つに決められない）の 3 つで、値の無い部分に「AI の推測」「未確認」を出さない。要確認の行は質問と候補を出し、候補を押して答えられる（今の質問は回答欄で答え、同じ候補を 2 か所に出さない）。要確認が無ければ畳んで要約の 1 行（「使用テーブル … ／ 表示列 …（確認の必要なし）」）にし、開けば一覧を見られる。
- **質問の取り消し**: 両方の画面とも「確認をやめる」は無い（#2303 / #2311）。チャットで質問を取り消して入力欄に戻すのは、要件の下書きの最中の入力欄の「停止」だけ（入力欄に書き始めた文字があれば上書きしない）。確認済みの一覧から開いた直し・追加の入力の「直すのをやめる」「追加をやめる」は、前の確認事項に戻るだけ（カードの `dismissAction`）。
- **AI の処理中の経過時間**: 要件の下書き（検査）と回答の後の再検査は、それぞれの処理を始めた時から数える（処理ごとに経過の表示を出し直す。利用者が答えていた時間・前の処理の時間を含めない）。「通常より時間がかかっています。」も同じ経過時間で出す。SQL 生成の画面の開始（業務プロファイルの推薦 → 確定 → 下書き）は 1 つの開始の処理として通しで数える。
- **検査の失敗**: 両方の画面で同じ `RequirementCheckFailure`（`ApiErrorBanner`）に、backend の 1 行の理由（タイムアウト・呼び出しの上限 429・サービスの 5xx・要求の誤り 400・応答が出力の上限で途中で終わった・応答の形式の誤り・接続の失敗・設定の誤り）と、開いた「詳細」（失敗の種類・OCI Enterprise AI の HTTP ステータス・モデル・所要時間・試行回数・待ち時間の上限・出力の上限・応答の理由・OCI のリクエスト ID・エラーコード・リクエストID）を出し、「もう一度確認」「確認せずに SQL を生成」を並べる。secret・prompt の全文は出さない。OCI Enterprise AI が設定されていない（`REQUIREMENT_AI_NOT_CONFIGURED`）ときだけは、確認せずにそのまま SQL を作る（チャット）。
- **業務プロファイルの「回答前の確認」（#1839）**: 業務プロファイルの編集に節「回答前の確認」を置き、「曖昧な質問の扱い」（確認してから SQL を生成する（既定）/ 前提を示して SQL を生成する）と「確認の上限（往復）」（システムの既定 / 2〜6 回。最初の確認を 1 回目に数え、AI の再検査の上限はこの値 - 1。0 はシステムの既定で `NL2SQL_REQUIREMENT_MAX_REVIEW_ROUNDS` + 1。既定の設定では 3 回）を保存する（`Nl2SqlProfile.clarification_policy` / `clarification_max_rounds`。JSON の payload なので migration は無い）。「前提を示して…」のときは、チャットは要件の検査をせずに SQL を作り、MCP の `nl2sql_query` は聞かずに、要件を反映できれば反映し、できなければ確認を使わずに作る（`requirement.status = skipped`）。SQL 生成の画面の「回答前の確認」のボタンは利用者の明示の操作なので変えない。
- チャットの送った質問と session の ID は作業状態（`requirementCheck`）に残し、再読込・画面の移動の後も同じ確認を続ける（session を作り直さない・中止しない）。SQL 生成の画面は、パネルを閉じずに画面を離れたら session を中止する（作業状態に残すのはチャットの送信だけ）。
- チャットで作ったターンの吹き出しは利用者の質問のまま、生成は確かめた質問の文で行い、回答に「SQL の生成前に確認した内容」（畳んだ詳細。中は書き直した質問）を SQL の前に出す。利用者が答えた・直した確認事項（`JobData.requirement_answers`）と確認を飛ばしたこと（`requirement_skipped`）は、質問の下に利用者の発言として「SQL の生成前に確認した内容」（共通の `ClarificationRecord`）で残す（#1839）。

### Markdown オントロジーの公開（Issue #491）

- 初回取得は `LoadingState`、空結果は `EmptyState`、再取得失敗は再試行を伴う `ErrorState`。以前の内容を残す場合は前回取得の情報であることを明記する。
- バージョンは読み取り DTO の `display_version` に由来する `vN` を表示する。解決できない場合は「版番号を取得できません」と取得可能な日時を示す。ID や一覧順から推測しない。
- 一般状態・操作は日本語のみ。Ontology の概念・契約には専門用語の英日併記を維持する。
- 定義検証と実データ検証はそれぞれの実施状況・日時・範囲・阻害事項を表示する。原始 JSON は初期状態で閉じた技術詳細へ置く。
- 受入テストの JSON エラーは入力に関連付ける。Markdown 解析の未対応行・競合・阻害事項を公開前に示す。移行と公開の確認は共通ダイアログで行い、公開の対象 Profile と実際の版を明記する。
- 公開成功はトースト、公開前チェックと取得失敗は対応する操作の近くに表示する。Markdown の編集で準備済み確認を失効させ、草稿は保持する。
- 公開成功後の再取得は本文が同じでも新しい草稿 ETag を受理する。公開 snapshot と草稿 revision の ID が異なる場合も、次の編集を保存可能にし、未保存入力は保持する。
- 応答喪失時は保存した冪等キーで公開結果を照会し、自動再実行しない。構築結果・公開能力の独立パネルは使用しない。
