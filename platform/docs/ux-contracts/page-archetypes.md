# ページの型と共有プリミティブ（Page archetypes）

> 3製品共通の正本。システム設定以外のページのレイアウトの型と、共有プリミティブの使い方を決める。
> 画面の骨格（`AppShell` / `PageHeader` / `PageBody` / `Section`）とトークンは [デザインシステム](../design-system/README.md)、ボタンは [buttons.md](./buttons.md)、通知は [messaging.md](./messaging.md) を併せて正本とする。
> 各ページがどの型に属するかは、製品の `docs/frontend-page-archetypes-spec.md` に書く。

---

## 0. 設計原則

1. 各ページは **4 つの型のどれか** に属する（§1）。例外はチャット（会話の画面。§6）だけ。独自のレイアウトを勝手に増やさない。
2. 共通の骨格 = `PageHeader`（+ 必要なら状態バー）+ 共有プリミティブ。新しい CSS / UI を作らない。
3. 色は**意味のトークン**だけ（[デザインシステム README §5 / §6](../design-system/README.md)）。生のパレットの class（`slate-` / `sky-` / `red-` …）を足さない。
4. 一覧・結果の表は共有 `DataTable` + `Pagination`、一覧と詳細の併置は `ListDetailLayout`（B 型。§3）、入力と結果の併置は `FixedSplitPane`（C 型・比較だけ。§3）、確認は `useConfirm`、通知は [messaging.md](./messaging.md) の 6 チャネル。詳細の出し方の選び方は §1「詳細の出し方」。
5. 文言はすべて i18n 経由。共有パッケージのプリミティブは i18n に依存しない（翻訳済みの文字列・ラベルを props で受ける）。
6. 一覧の行と詳細パネルの対象オブジェクトの操作は `EntityAction` を 1 つの定義にし、行は `RowActionMenu`、詳細は `ObjectActionBar` で出す（[buttons.md §5.1](./buttons.md#51-オブジェクト操作一覧行--詳細)）。
7. 一覧 / 詳細の単一選択は、行の操作以外の領域のクリックで選び、選択の状態は行全体の背景と `aria-current` で示す。キーボード向けに先頭セルの対象名のボタン（共有の `RowTitleButton`。選択中は `current` で `aria-current`）を残し、行のメニューには削除・アーカイブなどの実際の操作だけを入れる。A 型（一覧 → 全画面エディタ）のように URL で開く対象は、`RowTitleButton` に `href` を渡してリンクにし、新しいタブでも開けるようにする（#583）。
8. ページの操作は `PageHeader` の右側に置く（[buttons.md §5](./buttons.md#5-ページヘッダー操作)）。
9. コードブロック・プレビュー・結果などのコンテンツ内の操作は `ContentActionBar` で右上に寄せる。ページ・オブジェクト・行・コンテンツの操作を混ぜない。

## 1. ページの型（4 種）

### A. 一覧 → 全画面エディタ（エンティティの CRUD）

- URL の検索パラメータ（`?id=` など）を**唯一の情報源**とし、`null` = 一覧 / `"new"` = 新規 / `<id>` = 編集。
- 一覧：共有 `DataTable`（検索 / ソート / `Pagination`）+「新規」ボタン + 必要なら状態バー。
- エディタ：全幅で `Section` を**縦に積む**。`PageHeader` の左上（タイトルの上）に「一覧へ戻る」（`back`）。確定（作成・保存。primary）と「変更を破棄」（secondary）は**フォームの末尾の `FormActionBar`**（primary が左、左端を入力欄の左端にそろえる。画面の下端に貼り付けない。#2715）。`PageHeader` の右端には置かない。対象への操作（アーカイブ・削除など）は最初のカードの見出しの右の `ObjectActionBar` 1 か所（[design-system README §4「詳細・作成・編集の画面の操作」](../design-system/README.md)、#618 / #1786）。一覧と同じページで切り替える編集（NL2SQL・system-settings）も同じ置き方にする。
- **保存の失敗**：欄に結び付く失敗は欄の直下、それ以外は確定の行の直上の `SaveErrorBanner` の 1 か所だけ（Toast・フォームの下の `FormStatus` に重ねない。[messaging.md §3.3.1](./messaging.md#331-全画面のエディタの保存の失敗585)）。
- **離脱ガード**：未保存のまま離れるときは破棄を確認する（[workspace-state.md](./workspace-state.md#未保存変更の離脱ガード)）。
- **戻る**：2 階層（一覧 › 対象）のパンくずは出さず、`PageHeader` の `back`「一覧へ戻る」にする（読み上げ名は「{list}の一覧へ戻る」）。3 階層以上の深い導線だけパンくずを使う（#618）。
- 古いタブ（list / create / import など）は、**一覧上の操作** か **エディタ内の節** に平らにする。破壊的な操作は `useConfirm` に集める。

### B. マスタ詳細の閲覧（読み取り / 点検）

一覧と詳細を共有の `ListDetailLayout` で並べる（§3。#2281）。一覧は狭い列、詳細は広い列にする（一覧は名前と補足 1 行を見分けられればよく、詳細は表・フォーム・長い文を読む）。

```text
xl 以上（2 ペイン）                                          xl 未満（1 ペイン）
┌ 一覧（20rem・16〜32rem）┐┃┌ 詳細 ───────────────────────────┐   ┌ 一覧 ──────────┐  選ぶ   ┌ ← 一覧へ戻る ─────┐
│ 見出し・検索・絞り込み・件数 │┃│ [≡ 開閉]            [‹ 前へ][次へ ›] │   │ 検索・件数       │ ──────▶ │ 詳細               │
│ 行（名前 + 補足 1 行）     │┃│ 対象の見出し・ObjectActionBar        │   │ 行               │ ◀────── │ （PageHeader の back）│
│ …（列の中でスクロール）    │┃│ タブ・表・フォーム（ページと一緒に     │   └─────────────────┘  戻る   └──────────────────┘
│ ページ送り / さらに読み込む │┃│ スクロール）                          │
└───────────────────────┘┃└───────────────────────────────────┘
```

- **2 ペインは xl（1280px）以上だけ。** xl 未満は 1 ペインにし、一覧 → 選ぶと詳細だけ → `PageHeader` の `back`「一覧へ戻る」で一覧へ戻る（Material 3 の list-detail の canonical layout）。戻ると一覧の検索・絞り込み・ページ・一覧の中のスクロールと本文のスクロールの位置を保ち、フォーカスを選んでいた行へ戻す（一覧は描いたまま隠す）。1 ペインで詳細へ入ると、本文の先頭へ移り詳細の領域へフォーカスする。
- **一覧の列**: 既定 20rem（チャットの会話の履歴の列と同じ）。分割線（`role="separator"`。ドラッグ・← →（Shift で 4rem）・ダブルクリック / Home で既定）で 16〜32rem に変えられ、詳細に 30rem を残す。幅は画面ごと（`id`）に localStorage に残す。詳細の上端の行の左の開閉ボタン（チャットの会話の履歴と同じ `PanelLeftClose` / `PanelLeftOpen`、名前は一覧の列の名前。`aria-expanded` / `aria-controls`）で畳むと詳細が全幅になり、開閉も残す。一覧の列は sticky で画面の高さの中に収め（2 ペインの高さは本文の見える高さ − 列の上端 − 下の余白。詳細が短ければ本文に縦のスクロールを作らず、詳細が長ければ高さを変えずに `PageHeader` の下に貼り付く。#2330）、行は列の中でスクロールする（`DataTable` の `visibleRows` の 8 行の固定の高さにしない。表頭は固定）。検索・絞り込み・件数は列の上（スクロールしない）、ページ送り・「さらに読み込む」は列の下に置く。列は 28rem 未満なので `ListToolbar` は縦に積む（絞り込みが 3 つ以上なら `filtersLayout="sheet"`）。
- **一覧の行**: 名前と補足 1 行（コメント・日時など）と、要るなら右の短い値（行数・状態）だけ。列の多い表にしない（狭い列で横スクロールさせない）。並べ替えは列見出しか `FilterSelect` で。
- **詳細の列**: ページと一緒にスクロールし、詳細の中に縦のスクロールを入れ子にしない（列情報などの表も全行を出す）。枠（カード）は `ListDetailLayout` の詳細の列が持ち、製品の詳細は枠を重ねない（一覧の外側にも枠を付けない）。
- **選択**: URL の検索パラメータ（`useUrlSelection`。例 `?table=` / `?user=` / `?role=` / `?feedback=`）を唯一の情報源にし、再読込・戻る / 進む・リンクの共有で同じ対象が開く。**先頭の行を自動で選ばない**（利用者の操作なしに詳細の取得を走らせない）。未選択の 2 ペインは詳細に空の状態（「一覧から〜を選んでください」）。1 ペインで一覧から詳細へ入るときは履歴に積み（ブラウザの「戻る」でも一覧へ）、2 ペインで選び直す・前へ / 次へは置き換える（見比べるたびに履歴を積まない）。絞り込みで選んだ行が一覧から消えても、選択を別の行へ置き換えない。選んだ対象を削除したら選択を外す。
- **キーボード**: 一覧の行の名前のボタン（`RowTitleButton`）の間を ↑ / ↓ / Home / End で移り、Enter で選ぶ。詳細の上端の行の「前へ / 次へ」（`ListDetailPager`。任意）で、一覧の今の並びの前後へ移る。
- 製品が keep-alive（離れても描いたまま隠す。NL2SQL）なら、隠れている間はほかの画面の URL を読まず、サイドナビから戻ったときは最後の選択を URL に戻す（作業状態の「対象の選択は残して検証し直す」。NL2SQL の `useWorkspaceUrlSelection`）。

例外（#875）：Agent の実行履歴（と、同じ型にそろえた RAG の実行履歴。#1890）は長い回答・成果物・過程を読むため、一覧 → 全幅の詳細とする。RAG は詳細をパスの `/history/<run_id>` に置き、作成の画面は持たない（実行はチャット・RAG 検索で行う）。作成も `?id=new` の独立画面に置き、詳細は `?id=<Run ID>` を唯一の情報源にする。戻る操作・行メニュー・対象の操作は A 型と同じ共有部品を使い、一覧の検索・状態・ページを保持する。詳細はタブにせず、`RunDetailLayout` の節（概要 → 処理の経過〔処理の詳細を含む。#2325〕→ 回答 → 根拠・成果物 → フィードバック）を縦に 1 枚で読む（Agent の監査ログは既定で閉じた節。#1955・run-history.md §3）。この例外で他のマスタ詳細の分割ペインを変更しない。

例外（#877）：Agent の承認も、キュー → 全幅の確認画面とする。対象は `?id=<Approval ID>` から全承認で解決し、判断済みになってキューから消えても同じ対象に留まる。目標・理由・引数・判断記録を示し、判断の確認は維持する。戻ると検索・状態・ページを保つ。

- 行の操作以外の領域のクリックで選び、詳細をすぐ更新する。`詳細` ボタンを行の中に重ねて置かない。
- 一覧の行の操作は `RowActionMenu` 1 個にまとめ、詳細側は同じ action の定義を `ObjectActionBar` に渡す。
- 詳細側に常に出す操作は、非破壊・高頻度の最大 2 個に限る。危険な操作と低頻度の操作は overflow メニューに入れる。
- 行のメニューは表や一覧の列の scroll container に切られないこと。件数が少なく一覧の container が実際にはスクロールしていない場合も、viewport の中に浮かせて出す。

### C. ツール / ワークフロー（入力 → 操作 → 結果）

上に入力、実行ボタン（`loading`）、下に結果（`DataTable` + `Pagination`）。段階の表示は必要なときだけ。入力と結果を左右に並べる場合は `FixedSplitPane`（§3）に従う。

### D. ダッシュボード / 状態

メトリクスのカード + `StatusBadge` + セクション。編集は最小にする。

> システム設定（アップロード保存先 / モデル / データベース / 外観と証明書）は共有パッケージ `@production-ready/system-settings` の画面を使い、本規約の対象外。

### 詳細の出し方（#2281）

一覧の 1 件の詳細を出す形は、内容の量と「一覧と見比べるか」で選ぶ。同じ機能（例: 3 製品のフィードバック）は同じ形にする。

| 形 | 使うとき | 部品 | 例 |
|---|---|---|---|
| **全幅の詳細**（一覧 → 詳細の画面、`PageHeader` の `back`） | 詳細が長い・編集する・節が多い。一覧と同時に見る必要が無い | A 型のエディタ・`RunDetailLayout` | 業務プロファイル・ナレッジベース・実行履歴・承認・RAG の文書の詳細 |
| **一覧 + 詳細**（狭い一覧 + 広い詳細、xl 未満は 1 ペイン） | 一覧の行を次々に開いて点検する。詳細は表・フォーム・文章で、読む幅が要る | `ListDetailLayout` + `useUrlSelection` | テーブル・ビューの管理、ユーザー・ロール・権限管理、フィードバック、NL2SQL のデータの表示（詳細はデータの結果。#2315） |
| **シート**（右から重ねる `SideSheet`） | 一覧の文脈を保ったまま 1 件をのぞく補助の内容。閉じれば元の一覧のまま | `SideSheet`（`md` 40rem・前へ / 次へは `pager`。表は `wide` 64rem。短い一覧・絞り込みは既定の 22rem） | 品質評価のケースの詳細（`md`）、データの結果の「すべての行を見る」（`wide`）、会話の履歴・絞り込み（既定） |
| **左右の分割**（1:1 から利用者が動かす） | 入力と結果、2 つの対象の比較。両方を同じ重さで見る | `FixedSplitPane` | SQL から質問を生成・サンプルデータ（C 型） |

- モーダル（`SideSheet`・ダイアログ）は背後の一覧を操作できない（NN/g: modal と nonmodal）。一覧と詳細を行き来して点検する作業は `ListDetailLayout`（nonmodal）にし、シートにしない。
- シートの幅は Fluent 2 の Drawer の段（small / medium / large）にそろえ、文章を読む詳細に既定（22rem）を使わない。

## 2. 共有プリミティブ（`@production-ready/ui`）

### Pagination

```ts
usePagination<T>(items: T[], pageSize?: number, options?)
  => { page, setPage, totalPages, pageItems, range: { start, end, total } }
<Pagination page totalPages onPageChange range labels={paginationLabels()}
  pageSize? pageSizeOptions? onPageSizeChange? mode? disabled? ariaLabel? testId? />
```

```text
[1–25 / 123 件] [表示件数 25 件▾]            [«] [‹ 前へ] [ 1 ] / 5 ページ [次へ ›] [»]
```

- 文言は `labels`（製品の `paginationLabels()`。i18n の `pager.*`）と `range` から部品が作る。数値は `formatPaginationNumber`（桁区切り）、範囲の区切りは en dash、等幅数字（`tnum`）。翻訳済みの文字列を props で個別に渡さない（#1891 で削除）。
- 既定の `pageSize` は `DEFAULT_PAGE_SIZE`（25。#1952）。画面ごとの `PAGE_SIZE` を作らない。表示件数を選べる一覧は `onPageSizeChange`（10 / 25 / 50 / 100）を渡し、件数を変えたら 1 ページ目へ戻す。ページ番号と件数は作業状態（URL / sessionStorage）に残す（[workspace-state.md](./workspace-state.md)）。
- ページ番号の入力: 数値で、Enter か欄を離れたときに移る。範囲の外・数でない値は直前のページに戻し、理由を入力欄の下に出す（入力を黙って捨てない）。Escape は入力を戻す。IME の変換を確定する Enter では移らない。
- 375px・狭いパネル（置き場所が 28rem 未満）では「範囲」と「前へ・入力・次へ」を 2 行に折り返し、最初へ・最後へを畳む。置き場所が 20rem 未満（一覧 + 詳細の一覧の列の下端）では、前へ・次へもアイコンだけにする（名前は「前へ」「次へ」のまま。#2282）。タッチ端末では操作部品が 44px（トークン）。
- `nav` のランドマークと `aria-label`（一覧ごとに `ariaLabel` で名前を付ける。例「文書一覧のページ」）。今のページ（「2 / 13 ページ」）と範囲の外の理由は 1 つの `role="status"` で読む。最初へ・最後へはアイコンだけのボタンで、名前と Tooltip は「最初のページ」「最後のページ」。
- 1 ページ以下はページ送りを出さない（件数は `ListToolbar` の `ListCount` が出す）。表示件数の選択があるときは、件数が最も少ない段より多ければ範囲と選択だけを出す。
- カーソル型（`CursorPagination`）は隣のページにしか移れないので「前へ・N / M ページ（総数が無ければ N ページ目）・次へ」。任意のページへ移る必要がある一覧は、サーバーを offset 型（`OffsetPagination`）にする。
- e2e は共通の helper（`platform/packages/ui/e2e/layout-checks.ts` の `jumpToPage`）で「入力して移る」を確かめる。

### 一覧の件数（`ListCount`。#1891）

- 一覧の件数は `ListToolbar` の `count`（`ListCount`）で、ツールバーの右（一覧への操作の左）に 1 か所だけ出す。絞り込みなし「全 N 件」、絞り込み中「N 件（全 M 件）」（M は絞り込む前の全件、N は一致した全件。今のページの件数ではない）。1 ページに収まっても出す。
- カードの見出しのバッジ・`Section` の副題に同じ件数を出さない（二重にしない）。今のページの範囲「1–25 / 123 件」はページ送りの左が出す。
- 件数が変わったら `role="status"` で読む。`SearchField` の `resultCountLabel` と同じ件数を二重に読ませない（どちらかにする。`ListCount` の `live={false}`）。

### 一覧の型と、基準から外す例外（#265 / #403）

一覧は次の基準にそろえる（ルートの `docs/agents/ui.md`「読み込み中・一覧・ページング」）。

- 表は `DataTable` の `stickyHeader` + `visibleRows`（md 未満 5 行・md 以上 8 行）、表ではない行リストは `INFORMATION_LIST_SCROLL_CLASS`。それを超える行は一覧の中で縦スクロールにし、ページ全体を伸ばさない。手書きの `max-h-[…]` で高さを決めない。
- ページングは一覧の直下の共通 `Pagination`（既定 25 件/ページ。advanced の形。上の「Pagination」）。1 ページしかないときはページ送りを出さない（件数は `ListCount`）。
  - クライアント側で全件を持つ一覧: `usePagination` / `PagedDataTable`。
  - offset / limit / total の API: `OffsetPagination`（`offsetPagination` / `offsetForPage` を包み、今のページが空で返ったら最後のページへ寄せる。RAG の文書・ナレッジベース・検索・回答プロファイル・チャットの会話一覧、Agent のフィードバック・評価のジョブ・監査ログ・実行履歴・承認、NL2SQL の実行履歴・アプリのフィードバック・質問の学習の候補・SQL生成評価の結果明細と最近の job・チャットの会話一覧。#1266・#1897・#1891）。並べ替えのある一覧は、並べ替えもサーバーが全件で行う（ページの中だけで並べ替えない。NL2SQL の実行履歴の `sort` / `direction`）。日本語の文字列（質問など）は日本語の辞書順で並べる（Oracle は `NLSSORT(..., 'NLS_SORT=JAPANESE_M')`。同じ値は ID で順を決め、ページをまたいで抜け・重なりを作らない。#1777）。絞り込みのある一覧の API は、絞り込む前の全件（NL2SQL は `unfiltered_total`）も返し、`ListCount` の「N 件（全 M 件）」に使う（#1891）。
  - カーソル（`next_cursor`）だけを返す API（件数を数えるのが重い）で「前へ / 次へ」だけを送る一覧: `useCursorPages`（前へ戻るカーソルの履歴）+ `CursorPagination`（総数が無ければ「N ページ目」）。総数を返せる一覧は offset 型にして、ページ番号を入れて移れるようにする（#1891。NL2SQL の実行履歴などはカーソル型（#1266 / #1764）から移した）。
  - 1 ページの件数を選べる一覧は `Pagination` / `OffsetPagination` / `PagedDataTable` の `onPageSizeChange`（中身は `PageSizeSelect`、10 / 25 / 50 / 100、既定 25。`ResultTable` の「すべての行を見る」も同じ部品）。文言は共通の `Pagination` の既定（「a–b / n 件」「p / n ページ」「表示件数」）に製品の i18n を重ねる。

### データの結果の型（`ResultTable`。#1178）

**データの結果（読み取りだけの行と列）は、要約＋先頭の行のプレビュー＋「すべての行を見る」の `SideSheet`＋CSV で出す。行の操作・選択・編集のある一覧は、上の一覧の型（`DataTable` / `PagedDataTable` + `Pagination`）のまま。** 部品は共通の `ResultTable`（design-system README §4。旧名 `ChatResultTable`）で、製品で結果の表・ページング・CSV を組み立てない。

- **データの結果**: SQL・ツールの実行の結果、テーブル・ビューのデータの表示、取り込みのプレビュー・サンプル行、表の形のツールの結果・回答の Markdown の表。列は実行のたびに変わり（DB の列名）、行は「見る・出力する」だけで、行ごとの操作・選択・遷移が無い。
- **一覧**: 業務の対象（プロファイル・文書・履歴・評価のケース・監査の記録・ロールなど）の行で、列は画面が決め、行を選ぶ・開く・操作する。絞り込み・サーバーのページング・並べ替えを持つ。
- 1 つの画面の中では、データの結果は起点の操作（実行・表示のボタンの行）の直下に、カード・パネルの全幅で出す（[messaging.md §10](./messaging.md#10-操作の結果状態の出し方位置幅形出す情報705)）。
- 要約は部品が出す（「100 行・5 列」、打ち切りは「先頭の 100 行を取得しました（さらに行があります）」と info の案内、0 行は「該当する行はありません」で表・シート・CSV を出さない）。画面で指定した条件（取得上限・実行した接続）は `meta` に `StatusBadge` で並べ、行数を重ねて出さない。
- CSV は取得した行だけ（ブラウザで作る）。サーバーの出力（全件・XLSX）がある画面は、それを対象の操作（`ObjectActionBar` など）に残す。
- プレビューは先頭 50 行、表頭固定・表の中で縦横スクロール（md 未満 5 行・md 以上 8 行の高さ）。すべての行のシートは 10 / 50 / 100 行/ページ。

### 一覧のツールバー（検索欄の位置。#600）

一覧の上の「検索・絞り込み・件数・一覧への操作」は、共通の `ListToolbar` で次の位置にそろえる。

```text
┌ ListToolbar ────────────────────────────────────────────────────────────┐
│ [🔍 検索欄（先頭・lg）] [絞り込み: FilterSelect / FilterChipGroup] │ [件数] [一覧への操作（主操作は右端）] │
└──────────────────────────────── 左（2） ────────────────────────────────┴──────────── 右（1） ────────────┘
```

1. **検索欄は左端（先頭）。** 一覧の「見る範囲を決める」操作（検索・絞り込み）は、読む順（左上）と Tab の順の先頭に置く。絞り込みは検索欄のすぐ右に並べる。
2. **件数と一覧への操作（追加・一括操作・出力）は右。** 右端に寄せ、主操作は右端（`PageHeader` と同じ考え方）。選択に対する一括操作は、選択しているときだけ一覧の直上に出す行（RAG の文書一覧の一括操作のバー、`ListPicker` の選択の行）に置く。
3. **幅（#1891）**: 検索欄は `lg`（28rem）で固定し、行を埋めない（複数の語が見え、隣の部品とつり合う幅。以前は左の列の残りを埋め、1920px で約 1,000px に伸びた）。その右に絞り込み（それぞれの `width`）、右端に件数と操作。ツールバー自身の幅が 42rem 以上なら 1 行に並べ（入らない絞り込みは折り返す）、28rem 未満は縦に積んで検索欄を先頭に全幅で置く。画面幅ではなく container query で決めるので、横に並べたパネルの中でも同じ規則で崩れない。
4. 検索欄の隣に「検索」「絞り込み」のボタンを置かない（下の「一覧の絞り込みの検索」）。
5. **件数はツールバーの右の `ListCount` 1 か所**（#1891。上の「一覧の件数」）。見出しのバッジに件数を出している画面（NL2SQL のパネルの見出し・platform のユーザー・ロールの一覧・Agent の監査）は、段 2〜4 でツールバーの `ListCount` に移す。見出しとツールバーの両方に同じ件数を並べない。
6. 検索欄・絞り込み・一覧への操作は同じ高さ（既定 `md`）。絞り込みの選択欄は値の長さの幅（`width`）にする（下の「入力欄・選択欄・ボタンの高さと幅」、#613）。
7. **絞り込みの部品と 1 行の揃え（#1933）**: ツールバーの中の部品はすべて同じ高さ（md 36px・タッチ端末 44px）で縦の中心をそろえ、欄の上にラベルを置かない。選択は `FilterSelect`、少数の排他の状態は `FilterChipGroup`、条件があるときだけ「条件をクリア」。部品・狭い画面・期間・作業状態の規則は下の「一覧の絞り込みの部品」。

業界の設計との比較（2026-09 に確認。検索欄の置き場所と、その理由）:

| 設計 | 検索欄 | 右側 | 読み取れる考え方 |
|---|---|---|---|
| Atlassian（Jira の一覧・`PageHeader` の `bottomBar`） | 左に検索、その右に絞り込みの select | 一覧への操作 | 見る範囲を決めてから行を読む |
| GitHub Primer（Issues / Pull requests の一覧、`SubNav`） | 左に絞り込みの検索（行の大半を占める） | 「New issue」などの主操作 | 検索が主な絞り込みで、主操作は右端 |
| Shopify Polaris（`IndexFilters`） | 検索を開くと左に検索欄、その下に絞り込み | 並べ替え | 絞り込みは表の左上から |

### 一覧の絞り込みの部品（#1933）

一覧の上の絞り込み（選択・状態・期間）と、条件のクリア・件数・狭い画面での畳み方を 3 製品でそろえる。以前は製品ごとに `SelectField` の上にラベルを出したり（RAG の実行履歴・文書、NL2SQL の履歴・フィードバック・学習候補、Agent のフィードバック・利用状況）、約 26px の `ToggleChip` を並べたりしていて、1 行の中で上端・下端・中心がそろわなかった（RAG の実行履歴では検索欄 36px・上にラベルの「種類」・低いチップが下端でそろい、チップが下にずれて見えた）。棚卸しは #1933 の段 1 の PR にある。

```text
┌ ListToolbar ───────────────────────────────────────────────────────────────────────────────┐
│ [🔍 検索欄 lg] [種類: すべて ▾] [すべて 128|完了 112|失敗 12] [× 条件をクリア]  …  [12 件（全 128 件）] [操作] │
└────────────────────── すべて 36px（タッチ端末 44px）、縦の中心をそろえる ───────────────────────┘
375px（絞り込み 3 つ以上）:  [🔍 検索欄（全幅）]
                             [≡ 絞り込み（2）] [× 条件をクリア]
                             [210 件（全 3,402 件）] [操作]       → 押すと右からシート（絞り込みを縦に並べ、末尾に「210 件を表示」）
```

規則（推奨で確定。根拠は下の表）:

1. **1 行の揃え**: ツールバーの中の部品（検索欄・選択・チップ・条件のクリア・操作）はすべて同じ `size`（既定 md 36px、タッチ端末 44px）で、縦の中心をそろえる（`ListToolbar` が `items-center`）。件数と操作の群れは 1 行目（検索欄の行）にそろえ、絞り込みが折り返しても上に残す。**ツールバーの中では欄の上にラベルを置かない。** 移行前の上のラベルの欄（`data-field-label="top"`）が入っているあいだだけ、`ListToolbar` は入力欄の下端でそろえる（段 2〜4 で無くす）。
2. **選択の絞り込みは `FilterSelect`**: ラベルをボタンの中の先頭に入れる（「種類: すべて」）。読み上げ名はラベル（「種類」）、値はボタンの中の値で読む。既定の値（「すべて」。既定は選択肢の先頭）以外を選ぶと、値を太字・アクセントの文字、枠をアクセントの線にする（値の文字が変わるので色だけで伝えない）。幅は「ラベル: 値」の長さで `sm`（既定。状態・種類・期間）/ `md`（名前・長い選択肢）/ `lg`（対象の選択）。数百件から選ぶ対象（ナレッジベースなど）は `SearchableSelectField` に `labelPlacement="inline"` と `active` を渡す（「ナレッジベース: すべて」。選んだ名前は 1 行で切り、全文は `title`。#1933 段 2 で足した）。
3. **少数の排他の状態は `FilterChipGroup`**: 「すべて」を含めて 5 つまで（`FILTER_CHIP_MAX_OPTIONS`）。チップの高さは欄と同じ。選んだチップは塗り（`aria-pressed="true"`）。件数を添えられる（「完了 112」。等幅数字・桁区切り、読み上げは説明）。6 つ以上か、文言が長く 1 行に入らない状態は `FilterSelect`。複数を同時に選ぶ絞り込み（チェックの付くチップ）は今は作らない（要る画面が出たら決める）。`ToggleChip` は一覧のツールバーの外の切り替え（表示のオン / オフ・回答のモデルなど）に使う。
4. **条件のクリア**: 検索語か既定と違う絞り込みがあるときだけ、絞り込みの後ろに「条件をクリア」（ghost・`X`）を 1 か所出す（`ListToolbar` の `onClearFilters` + `activeFilterCount` / `searchActive`）。検索語と絞り込みをすべて既定に戻し、ページを 1 ページ目へ戻す。0 件の空の状態の「検索語をクリア」（`ClearActionButton`）は残す（一覧の場所から戻せる）。
5. **件数**: 絞り込み中は `ListCount` の「N 件（全 M 件）」（上の「一覧の件数」）。状態のチップの件数は「その状態の全件」（検索語で絞る前でも後でもよいが、1 つの画面の中でそろえ、`ListCount` と矛盾させない）。
6. **すぐ適用する**: 選択・チップを変えたらすぐ一覧に反映する（「適用」のボタンを置かない。検索欄は 300ms の debounce）。シートの中でもすぐ反映し、末尾のボタン（「N 件を表示」）は閉じるだけ。例外は条件を組み合わせてから 1 度だけ問い合わせる条件のフォーム（Agent の監査ログ。上の「一覧の絞り込みの検索」の例外）。
7. **狭い置き場所（ツールバーが 28rem 未満。375px・横に並べたパネル）**: 検索欄を先頭に全幅で置く。**ツールバーの中の欄（検索欄・`FilterSelect`・所有者などの入力）の幅の段は、画面（viewport の `sm`）ではなくツールバーの幅（container の 28rem）で切り替える**（`ListToolbar` が `FieldWidthScopeProvider scope="container"` で包む）。狭い分割のペインでは、画面が広くても検索欄と絞り込みの欄がそろって全幅になる（以前は検索欄だけ全幅で、隣の所有者の欄は `sm:` の段の幅のままだった。#1891 の段 3 で見つかった）。絞り込みが **2 つまで**なら検索欄の下に縦に積む（チップは折り返す。隠さない）。**3 つ以上**なら `filtersLayout="sheet"` を渡し、「絞り込み（N）」（N は既定と違う絞り込みの数）のボタンと「条件をクリア」だけを出し、押すと右からのシート（`SideSheet`）に絞り込みを縦に並べる。シートの末尾に「N 件を表示」（閉じる）と「条件をクリア」。広い置き場所に戻ったらシートを閉じて行に戻す。
8. **期間**: 一覧の期間の絞り込みは、プリセットの `FilterSelect`（「期間: 過去 7 日」。すべて / 今日 / 過去 7 日 / 過去 30 日 / 過去 90 日 など。「過去 7 日」は今日を含む。期間を限らない選択肢はほかの絞り込みと同じ「すべて」にし、`sm` の幅に収める（「期間: すべての期間」は `sm` で切れる。#1933 段 2））。日付の範囲の入力（開始日・終了日）は分析の条件のフォーム（Agent の監査）だけで使い、ツールバーには置かない（要る一覧が出たら「期間を指定」の選択肢から範囲の欄を開く形で `packages/ui` に足す）。
9. **作業状態**: 検索語・絞り込み・ページ・表示件数は作業状態に残す（[workspace-state.md](./workspace-state.md)）。共有して同じ範囲を見る意味がある一覧（分析・履歴）は URL の query、それ以外は workspace の sessionStorage。読み込んだ値が選択肢に無ければ既定に戻す。絞り込みを変えたら 1 ページ目へ戻し、選択を解除する。秘密・個人情報を URL に入れない。

### 大量の候補から選ぶ（`ListPicker`。#600）

候補の数で部品を分ける。

| 候補の数 | 部品 | 例 |
|---|---|---|
| 選択欄に収まる数（数十〜数百件。選んだ値は欄の中・chip で見せる）。**1 つを選ぶ**なら件数が多くても（`remote` でサーバー側の検索） | 検索できる選択欄（combobox。`SearchableSelectField`（単一）/ `SearchableMultiSelect`（複数）。#578） | 検索・回答プロファイルの参照先のナレッジベース、アップロード先、文書の一覧のナレッジベースの絞り込み（#608） |
| 大量（数千〜数万件。一覧を見比べて、まとめて選ぶ。グループ単位の一括選択・「選択中だけ表示」が要る） | **`ListPicker`**（一覧型。ページの中に置く） | ナレッジベースの「文書を追加」（RAG）、業務プロファイルの許可する表・ビュー・メタデータ SQL の対象・合成データの対象の表（NL2SQL）、権限管理の「利用できる対象」（platform） |

`ListPicker` の型（NL2SQL の業務プロファイルの「許可する表・ビュー」を共通にした）:

1. **ツールバー**: 左に候補の検索欄（`SearchField`。入力に合わせてサーバーの `q` で絞る）と絞り込み。
2. **選択の行**: 左に「表示中をすべて選択」「選択をすべて解除」、右に「選択中だけ表示（K）」。選んだ候補は検索語を変えても残り、「選択中だけ表示」で確かめられる。
3. **候補の一覧**: 選択肢の listbox（`aria-multiselectable`、選択の状態は `aria-checked`、位置は `aria-posinset` / `aria-setsize`）。グループ（例: スキーマ）ごとに見出し（件数・グループの一括選択）と listbox を分ける（listbox の中にボタンを置かない）。Tab で listbox に入り、↑↓ / Home / End / PageUp / PageDown で移り、Space（Enter）で選択を切り替える。グループの端の ↑↓ で隣のグループへ移る。選べない候補（例: 追加済み）は `aria-disabled` と理由の文言で示す。
4. **高さ**: 5 / 8 行（md 未満 / 以上）で中をスクロールする。100 行を超えたら見えている行だけを描く（仮想スクロール）。100 行までは全部描き、ページ内検索・読み上げで届くようにする。
5. **フッター**: 「N / M 件を表示、選択 K 件」と「さらに読み込む」（`LoadMoreFooter`。失敗は再試行付きの `Banner`）。数千件を一度に読まない（RAG は 100 件ずつ、NL2SQL は 50 件ずつ）。
6. **確定**: 選んだ後の「選択した N 件を追加」などは、一覧の下の操作行（`FormActionBar`。区切り線の下に左寄せ、primary → secondary）。追加したら閉じて、開いたボタンへフォーカスを戻す。
7. **保存中**: `disabled`（または囲む `<fieldset disabled>`）の間は、選択を切り替えない。

画面ごとの判断（#608。「似た機能は同じ UI / UX にする」の見直し）:

| 画面 | 候補の数・選び方 | 部品 | 理由 |
|---|---|---|---|
| NL2SQL のメタデータ SQL の対象 | 数千件の表・ビューから複数（上限 100 件） | `ListPicker` | 業務プロファイルの許可する表・ビューと同じ「大量から複数」。並べ替えの列より、検索・「選択中だけ表示」・キーボード操作が要る |
| NL2SQL の合成データの対象の表 | 業務プロファイルの許可する表（数百件）から複数 | `ListPicker` | 同上。一括選択と「選択中だけ表示」で選んだ表を確かめる |
| NL2SQL の学習候補の追加 | 1 ページ 25 件（既定。表示件数 10 / 25 / 50 / 100。#1891・#1952）の候補ごとに、状態・確定する業務プロファイル・元のフィードバックへのリンク | 今のまま（行の中の `SelectField` と行のチェックボックス、`Pagination`） | 候補を選ぶ一覧ではなく、行ごとに業務プロファイルを確定してから追加する作業の一覧（行の中に入力と操作がある）。`ListPicker` の行は選択肢（option）で、中に入力を置けない |
| platform の権限管理の「利用できる対象」 | 数千件になりうる対象から複数 | `ListPicker`（サーバー側の検索とページング） | 候補を全件読まない。検索は `q`、続きは `limit` / `offset`、選択済みの名前は `ids` |

### 一覧の絞り込みの検索（#535）

検索には 2 種類あり、操作を分ける（NN/g・Material 3・GOV.UK Design System・WCAG 2.2 に合わせる）。

| 種類 | 例 | 操作 | 部品 |
|---|---|---|---|
| **一覧の絞り込み**（画面上の一覧・表を名前などで絞る。結果は同じ一覧の行） | ナレッジベース・検索・回答プロファイル・文書・フィードバック（RAG）、DB オブジェクト・プロファイル・履歴・学習候補・フィードバック履歴・スキーマ参照（NL2SQL）、業務 Agent・実行履歴・承認・スキルなどの一覧（Agent。#808）、ユーザー・ロール・権限の対象（system-settings）、`ListPicker` の候補（RAG の文書を追加・所属文書、NL2SQL の許可する表・ビュー） | **入力に合わせて絞り込む。検索ボタンを置かない。** 入力が止まって 300ms で反映し、Enter は debounce を待たずにすぐ反映する。値があるときは末尾に消去（×。Escape でも消す） | `SearchField` |
| **重い検索・問い合わせ**（LLM・ベクトル検索・SQL の生成と実行を呼ぶもの。結果は回答・生成物） | RAG 検索・チャット・検索テスト・文書の検索比較（RAG）、SQL 生成・オントロジーの問い合わせ・分類器の予測（NL2SQL）、Run の目標（Agent） | **明示的に実行する。** ボタンと Enter（複数行は Ctrl/⌘+Enter）。入力中には実行しない | `TextField`（`type="search"` にしない）+ `Button`、Enter の判定は `isSubmitEnter` |

一覧の絞り込みの規則:

1. **入力に合わせて絞り込む**（debounce 300ms、Enter はすぐ）。検索ボタン・「絞り込み」ボタンを隣に置かない。同じ一覧のほかの条件（`FilterSelect`・`FilterChipGroup` の状態・種類。#1933）も、選んだらすぐ適用する。
2. **日本語入力**: IME の変換中（`compositionstart`〜`compositionend`、`isComposing`、Safari の確定の Enter の `keyCode 229`）は、入力でも Enter でも絞り込まない。変換を確定した値で絞り込む。`SearchField` と `isImeComposing` / `isSubmitEnter` が判定する。製品で `event.key === "Enter"` だけで判定しない。
3. **件数を伝える**: 結果の件数を `aria-live`（`SearchField` の `resultCountLabel`）で読み上げる。画面の件数の表示（`StatusBadge` 等）はそのままでよい。
4. **0 件**: 空の状態に「検索に一致する〜がありません」と、「検索語をクリア」（`ClearActionButton`）を出す。データがそもそも無いときの空の状態と文言を分ける。
5. **作業状態**: 検索語は作業状態として残す（[workspace-state.md](./workspace-state.md)）。`SearchField` の `value` には保存している**適用中**の検索語を渡し、入力中の文字は部品が持つ。検索語が変わったらページングを 1 ページ目へ戻し、選択を解除する（変わらない Enter・blur ではページと選択を失わない）。
6. **サーバー側で絞り込む一覧**: 古い応答で新しい結果を上書きしない。TanStack Query は検索語を query key に入れ、`placeholderData: keepPreviousData` で前の一覧を出したまま取り直す。手で取得する一覧は、要求の連番か `AbortController` で最後の要求の応答だけを使う。読込中は一覧の領域で示す（操作したボタンが無いので、`ProcessingIndicator` / `TimedLoadingState` のスピナーを出す）。
7. **親で遅延させない**: debounce は `SearchField` の 1 か所だけにする。親で `useDebouncedValue` などを重ねない（反映が遅れる）。

レビューのチェックリスト（lint が見るのは 1 だけ）:

- [ ] 一覧の絞り込みの検索欄が `SearchField`（adherence の lint が `type="search"` の `TextField` / `<input>` を検出する）
- [ ] 検索欄の隣に「検索」「絞り込み」「適用」のボタンが無い
- [ ] IME の変換中に問い合わせ・絞り込みをしない（e2e で `compositionstart` → `isComposing` の `input` → `compositionend` を確かめる）
- [ ] 0 件の空の状態に「検索語をクリア」がある
- [ ] 検索語が作業状態に残り、変えるとページが 1 ページ目に戻る
- [ ] 重い検索は `type="search"` にせず、明示的に実行し、Enter の判定が `isSubmitEnter`

### 入力欄・選択欄・ボタンの高さと幅（#613）

寸法の値と部品の API は [design-system README §4「操作部品の高さと幅」](../design-system/README.md) が正本。画面では次のように選ぶ。

1. **1 つの行の中では、入力欄・選択欄・ボタンを同じ高さの段にする。** 部品に同じ `size` を渡す（既定 `md` 36px）。`lg`（40px）は工程・フォームの末尾で次へ進む主操作の行、主な問い合わせの入力の行（チャット・検索テスト・オントロジーの質問）、確認語欄、ログインなど 1 つの作業だけの画面。`sm`（32px）は表の行・密なツールバーの中。
2. **タッチ端末では 3 段とも 44px** になる（入力方式で決まる）。製品で `touchTarget`・`h-*`・`min-h-*` を書かない。
3. **入力欄・選択欄の幅は、入る値の種類で選ぶ**（`width`。#613 / #1891）。ラベルと必須の印は段の幅で折り返さず 1 行に出る（部品が外枠をラベルの幅まで広げる。#1746）。375px ではどの段も全幅。

   | 種類 | 幅 |
   |---|---|
   | 数値・短いコード（〜6 文字）・表示件数 | `xs` 8rem |
   | 日付・期間・短い選択（状態・種類）・有効期限・リージョン | `sm` 12rem |
   | 名前・ID・メール・一般の選択 | `md` 20rem |
   | 長い名前・対象の選択（プロファイル・ナレッジベース・業務 Agent）・一覧の検索欄 | `lg` 28rem |
   | URL・OCID・パス・文章・SQL・プロンプト・`TextareaField` | `full`（フォームでは `FormGrid` の最大幅 60rem まで） |

   - **フォームの grid のセルでも種類の `width` を渡す**（段の幅が上限。以前の「セルには渡さない」は廃止）。長い値は `col-span-full`。フォームの本文は `FormGrid`（最大 60rem・置き場所 57.5rem 以上で 2 列。それより狭いと 1 列で、`lg` の欄もセルで切られない。#1891 段 5）に置く。
   - 欄の補足・エラーの文は欄の幅ではなく、置き場所（grid のセル・`FormGrid` の段・カード）の幅で折り返す（`xs` / `sm` の欄でも、部品が外枠をその幅まで広げる。1 行は 60rem まで。横に並べる行の中では `min(20rem, 置き場所の幅)` 以上。#1891 段 5・#2063）。
   - grid の外に単独で置く欄（カードの先頭の対象の選択・ツールバーの絞り込み・表示件数・操作の横の選択）も必ず指定し、カードや行の幅いっぱいに伸ばさない。
   - 例外: RAG の検索・3 製品のチャットの対象の選択（検索・回答プロファイル / 業務プロファイル / 業務 Agent）は、すぐ下の問い合わせの入力欄と端をそろえる `full`（#635）。
   - **placeholder は欄の幅に収める。** 収まらないときは短い例にし、説明は欄の下の補足（`helper`）に移す（placeholder は入力を始めると消え、ラベル・説明の代わりにならない）。e2e は共通の `findClippedPlaceholders` で切れを検出する。
4. **入力欄と、その値への操作（送信・実行・取得）の行は `FieldActionRow`。** 操作は入力欄の下端にそろえ、375px では入力欄の下に全幅で置く。補足・エラーは行の下（`footer`）に出す。
5. 一覧のツールバー（`ListToolbar`）の絞り込みの選択欄も `width` を渡す。検索欄は部品が `lg` で固定する（上の「一覧のツールバー」）。
6. 画面の検証（Playwright）は共通の helper（`platform/packages/ui/e2e/layout-checks.ts`）を使う: 横あふれ（`measureHorizontalOverflow`）・placeholder の切れ（`findClippedPlaceholders`）・ページ番号の入力で移る（`jumpToPage`）・欄の幅が段のどれかで `FormGrid` のセルからはみ出さない（`findFieldsOffWidthScale`、sm 以上で任意）・補足が狭く折り返さない（`findNarrowFieldTexts`）。`FormGrid` の置き場所の幅は `setFormGridMaxWidth` で狭めて確かめる。

## 3. 一覧 + 詳細と分割ペイン

### `ListDetailLayout`（B 型の一覧 + 詳細。#2281）

RAG のフィードバックと Agent の「確かめるべき実行」は、長い質問・回答・根拠やシグナルを読むため、すべての幅で一覧から全幅の詳細へ切り替える B 型の例外とする（#3635・#3743）。Agent の主一覧は `listVariant="table"` を指定し、`Section` の見出し、`ListToolbar` の件数、標準の高さの `DataTable` と直下のページ送りを使う（#3749）。共通 `ListDetailLayout` の `layout="single"` と `useUrlSelection(singlePane: true)` を組み合わせ、一覧の検索・条件・ページと、戻る時の行へのフォーカスを保つ。

規則は §1 B。部品の props は design-system README §4「`ListDetailLayout`」と components-reference.md。

- `id` は `<feature>-<view>`（例: `table-management`）。一覧の幅と開閉の localStorage の key（製品の `storagePrefix` + `id`）と `data-testid`（`list-detail-<id>` / `-list` / `-detail` / `-resizer` / `-toggle`）に使う。
- 製品は `listHeader`（見出し・`ListToolbar`）・`list`（行）・`listFooter`（ページ送り）・`detail`・`emptyDetail`・`detailToolbar`（`ListDetailPager`）を渡し、1 ペインの「一覧へ戻る」は `PageHeader` の `back`（`useListDetailSplit()` が false で選んでいるとき。`onClick` は `useUrlSelection` の `clear`）に置く。
- 読み込み中・失敗・空は、一覧の列・詳細の列のそれぞれの中で出す（`TimedLoadingState` + 内容の形の `Skeleton`）。

### `FixedSplitPane`（C 型の入力 | 結果と比較だけ）

`@production-ready/ui` の `FixedSplitPane` は、入力と結果・2 つの対象の比較のように、左右を同じ重さで見る画面だけに使う（一覧 + 詳細には使わない。#2281）。構造 CSS は共有の `tokens.css` が配布する。

- `splitId` は `<feature>-<view>`（例：`sql-to-question-input`）。localStorage の key は部品に任せる。
- 分割線の初期位置は、すべての画面で 50%（左右 1:1）。画面ごとに片側を広くする指定は持たない（#1572）。利用者が動かした位置は `splitId` ごとに localStorage に残り、次からはそれを使う。ダブルクリック / Enter / Space は 1:1 → 左を広く → 右を広く（黄金比）の順に切り替え、Home で 1:1 に戻す。
- 左右の枠の class は共通の panel shell にまとめ、ページごとに重ねて書かない。
- 狭い幅（`xl` 未満）は縦積みに切り替える。divider は `role="separator"`、矢印 / Home キー、grip を備える。

## 6. チャット（会話の画面。#1161）

3 製品のチャット（RAG `/chat`・NL2SQL `/chat`・Agent `/chat`）は §1 の 4 つの型の外の、会話の画面の型にする。入力 → 回答を会話として積み、送信は「その場で結果を待つ操作」（[buttons.md §3.1](./buttons.md)）。送信の振る舞い（楽観的な表示・失敗と再送信・停止・読み上げ・処理の段階）は [messaging.md §11](./messaging.md#11-チャットの送信楽観的な表示907) が正本で、この節は画面の骨格と、共通の部品と製品の分担を決める。

### 6.1 骨格

```text
PageHeader wide（タイトル・説明。操作は置かない）
PageBody wide
└─ grid（lg 以上で履歴を開くと「履歴 20rem | 会話」の 2 列）
   ├─ 会話の履歴（lg 以上: 本文の横の <aside>。lg 未満: SideSheet。既定で閉じる。#664）
   └─ 会話の領域（<section>。lg 未満は高さ 70dvh・最小 28rem、lg 以上は残りの高さ・最小 28rem。拡大や低いウィンドウで不足する分はページでスクロールし、会話の内容領域を入力欄で潰さない）
      ├─ 上端のツールバー: 履歴の開閉（左端）・今の会話の名前・対象の選択（compact）・「新しい会話」（右端。#3918）
      ├─ 会話の欄（role="log"「会話」。中だけスクロールする）
      │   └─ 1 往復 = 利用者の吹き出し（ChatUserMessage）+ 回答の入れ物（処理の段階 ChatProgress → 回答の本文 → 回答の操作）
      └─ 入力欄の領域: 設定の行（任意。ラベル + InfoTip + 選択）→ 入力欄と送信 / 停止（FieldActionRow + RunStopButton、lg）→ 通知（停止の失敗など）
```

- **回答の詳細は根拠を先、実行記録を後に並べる**（#1417）: 回答の本文の下の折りたたみは、回答を裏付けるもの（引用・出典・根拠の構成・SQL やオントロジーの根拠）を上、技術的な記録（工程・ツールの呼び出し・SQL の実行・プロンプト・経過時間と trace）を下にする（利用者がまず確かめるのは何に基づく回答かで、実行記録は監査・調査用の詳細。messaging.md §10 の「詳細に畳む」と同じ段階的な開示）。チャット以外の回答の詳細（RAG 検索・保存した回答・Agent の実行の詳細）も同じで、回答の前に出す処理の段階（`ChatProgress`）は対象外。**評価（「この回答は役に立ちましたか？」などの回答の評価）は根拠と実行記録の後**に置き、回答の枠の最後にする（根拠を確かめてから評価できるように。#1202 / #1420）。RAG のチャットと RAG 検索は「処理の経過（回答の上。工程の一覧と、技術的な記録の「詳細」。#2096 / #2115）→ 回答 → 回答の注意書き → AI に渡した箇所（折りたたみ。まとまりごとの見方を含む。#2097）→ 評価」、Agent のチャットは「処理の経過（回答の上。完了したら閉じる。使ったツールはツールの段を開いて見る。#2324）→ 回答 → 資料との照合 → 回答の注意書き → 出典 → 評価」（注意書きから評価までの並びは共通の `AnswerFooter`。#2707）。引用ごとの評価は各引用の中に置く。
- **回答の本文の前に見出し「回答」を出す**（#3433）: 回答の枠の中で、処理の経過（と保存の失敗などの注意）の後、回答の本文の直前に、本文の中の節の見出し（「資料により確認できた事項」など）と同じ書式・同じ部品の見出し「回答」を置く（共通の `ChatAnswerBody`。段は会話の名前 h2 の下の h3、本文の中の節の見出しは h4、Markdown の回答の見出しは h4 から）。回答の本文を描くときだけ出し、処理の経過だけの間（本文が届く前）・失敗・停止だけの枠には出さない。回答の本文が利用者への問い返しの文（Agent が資料を絞るために尋ねる文など）でも回答の本文なので同じ「回答」にする（回答前の確認のカード `ClarificationCard` は自分の見出しを持つので付けない）。実行の詳細は節の見出し「回答」（`RunDetailLayout` の `Section`）があるので重ねない。RAG のチャットと Agent のチャットに出し、NL2SQL のチャットの回答（SQL・説明・結果）は本文の節を持たないので出さない。
- 対象（検索・回答プロファイル / 業務プロファイル / 業務 Agent）を選ぶまで、会話の領域は出さない（または空の状態だけを出す）。対象を変えたら、開いている会話と確定していない仮のメッセージを外す（messaging.md §11.3）。
- 会話の履歴は「会話の履歴」（`complementary` / `dialog` の名前）。開閉ボタンは会話の領域の上端の行の左端に 1 つだけ置き、`aria-expanded`・`aria-controls` を付ける。lg 以上のインラインの開閉は作業状態に残し、lg 未満のシートの開閉は残さない（[design-system README §4「SideSheet」](../design-system/README.md)、[workspace-state.md](./workspace-state.md)）。画面の幅が lg を越えたらシートを閉じる。
- 会話の履歴は、最後の更新が直近 N 日（共通の設定 `PLATFORM_CHAT_HISTORY_DAYS`。既定 90 日）の会話だけを出す。期間は見出しの行の右端（lg 未満はシートの本文の先頭）に「最近 N 日」と小さく出し（`ChatLayout` の `historyCaption`。パネルの `aria-describedby`）、0 件は「最近 N 日の会話はありません」にする（文言は `chatHistoryWindowLabels`。4 つのチャットで同じ）。期間の外の会話は消さず、実行の詳細の「会話を開く」・直接のリンクから開ける（backend-standard.md「チャットの「会話の履歴」の期間」。#2340）。
- 「新しい会話」は上端の行の 1 か所だけに置く（履歴の一覧の中に重ねて置かない。#889）。会話を選んでいる間は、履歴を閉じていても上端の行に会話の名前を出す。
- 会話の欄は会話の領域の中だけでスクロールし、自動の移動は会話の欄の `scrollTo` で行う（祖先を動かす `scrollIntoView` を使わない。design-system README §4「AppShell」）。
- 入力欄は回答の作成中も書ける。Enter で送信、Shift+Enter で改行、IME の変換中の Enter では送らない（`isSubmitEnter`。#459）。実行中の Enter では停止しない（buttons.md §3.1）。
- **閲覧だけの会話**（system_admin が開いた他の利用者の会話。#3244）は、入力欄の領域に `ChatComposer` の代わりに `ChatReadOnlyNotice`（info の Banner「他の利用者の会話です（閲覧のみ）」と、できないこと・できることの文。文は backend の 403 の `OTHERS_CONTENT_FORBIDDEN_MESSAGE` と同じ）を置く。回答の作成中・処理中・承認待ちなら案内の中に「停止」を出す。続きの操作（再送信・確認への回答・評価・SQL の実行）は会話の欄にも出さず、会話の履歴の行は「名前の変更」を出さない（`useChatHistoryActions` の `canRename`）で「削除」だけを出す。3 製品で同じ部品・同じ文にする。
- 読み込み中・失敗・空は、履歴の一覧・会話の欄・対象の選択のそれぞれの領域の中で出す（messaging.md §3.6。前提の読み込み中に空の状態を出さず、送信を止める。入力欄を無効にするのは対象の一覧の読み込み中だけで、会話の内容の読み込み中は書ける。#1153 / #1188）。

### 6.2 共通の部品と製品の分担

|---|---|
| 骨格（履歴のパネルとシート・会話の領域・上端の行・会話の欄・入力欄の領域）、履歴の開閉の判定、履歴の行の名前の変更・削除（`useChatHistoryActions`。その場の欄・空の名前の検証・確認のダイアログ・Toast と文言・行ごとの `canRename`。#1817・#3244）、閲覧だけの会話の入力欄の代わりの案内（`ChatReadOnlyNotice`。#3244）、1 往復の入れ物と回答の入れ物、仮の質問と失敗・再送信の表示、入力欄の行と Enter / IME の判定、自動スクロール、処理の段階（`ChatProgress`）、評価（`FeedbackControls`）、回答前の確認のカードと会話に残す表示（`ClarificationCard` / `ClarificationRecord`。[confirm-before-answer.md](./confirm-before-answer.md)。#1839） | データの取得（会話の一覧・会話・ポーリング / SSE）、送信・置き換え・停止・会話の名前の変更・削除の API、作業状態の保存（下書き・対象・会話・履歴の開閉）、対象の選択の中身、回答の本文と回答に付く操作（RAG の引用・複数モデル・類似問・確認、NL2SQL の SQL と実行、Agent のツール・承認・出典）、処理の段階の組み立て、文言 |

- 共通の部品は業務の語彙を知らない。文言は翻訳済みを props で受け、会話・メッセージのデータは製品が自分の API の型から写して渡す。回答の本文は子要素（スロット）で渡す。
- 回答の中のデータの表（SQL の実行の結果・表の形のツールの結果・回答の Markdown の表）は、3 製品とも `ResultTable`（#1154 / #1178。旧名 `ChatResultTable`）で回答の入れ物の中に出す。画面のデータの結果も同じ部品にする（上の「データの結果の型」）。JSON・Markdown から列と行を作る判定は共通の `toTabularData` / `splitMarkdownTables`（#1158）で、製品で表を組み立てない。表でない結果は製品の今の表示のまま。RAG の回答は根拠付きの文章で、列と行の結果を返さないので出さない（RAG `docs/frontend-page-archetypes-spec.md` §5。#1159）。
- 製品でチャットの骨格を書き写さない。足りない振る舞いは `packages/ui` の部品に足し、3 製品で同時に受け取る（[design-system ARCHITECTURE.md §7](../design-system/ARCHITECTURE.md)）。

### 6.3 製品ごとの違いとして残すもの

- 対象の種類と選択の欄（RAG は検索・回答プロファイルの専用の欄、NL2SQL・Agent は `SearchableSelectField`）。
- 入力欄の上の設定の行の中身（RAG「回答するモデル」、NL2SQL「生成方法」、Agent はなし）。
- 履歴の一覧のページングは 3 製品で同じにする（#1265）。`ChatHistoryList` の `pagination` に渡し、一覧の下に共通の `Pagination`（既定 25 件 / ページ、件数「a–b / n 件」と「前へ / N / M ページ / 次へ」。1 ページなら出さない）を常に見せる。3 製品とも offset の API（NL2SQL は #1891 でカーソル型から移した）で、`type: "offset"`（`OffsetPagination`）を渡す。ページは作業状態に残し、対象を変えたら 1 ページ目へ戻す。会話が減って今のページが空になったら、最後のページへ戻す（空の案内を出さない）。「さらに読み込む」は使わない。
- 停止の方法（RAG は request の中断、NL2SQL・Agent はジョブ・Run の中止の API）。
