# プロンプト（LLM への指示・skill・ツールの説明）の書き方

> root の [AGENTS.md](../../AGENTS.md) から移した詳細（#2276）。root の規則と同じ強さで守る。規則を変えるときはこのファイルを直し、root には規則の要約と案内だけを書く。

LLM に渡す文（製品の LLM への指示、組み込みのスキル `skills/`、MCP の server instructions・ツールと引数の説明、Agent の組み込み Runtime の指示とツールの結果の案内）は、pi（[badlogic/pi-mono](https://github.com/badlogic/pi-mono) の coding agent。[作者の解説](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)）と DeepSeek Harness（[deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) の `.agents/skills/` の `agent-experience`・`dsh-prose-standard`・`dsh-trim-cot-leakage`）の書き方に従う。

- **Agent・RAG・NL2SQL と共通基盤のすべての Prompt は、実際にモデルへ渡す指示を `## Step 1: …`、`## Step 2: …` の形式で処理順に書く。** System Prompt・入力テンプレート・ツールやスキルのモデル向けの手順にも適用する。役割と目的、入力の読み方、判断と制約、出力を必要な Step に整理し、内容に応じた連番にする。画面の表示だけを整形して済ませず、表示と実行の指示を一致させる。既存の意味・安全上の境界・否定・例外・出力契約を保ち、形式を変えた場合も関連テストと初回に渡す字数の前後を確認する。
- **1 つの規則は 1 つの層にだけ書く**（MCP の instructions / ツールの説明 / 引数の説明 / validator / スキル / Runtime の指示）。引数の既定・範囲・組み合わせ・いつ渡すかは引数の説明、ツールをいつ使うかはツールの説明、複数のツールをつなぐ手順はスキルに置き、ほかの層で繰り返さない。
- **コードで保証できることはコードに置く**（validator・正規化・既定値・上限）。プロンプトに重ねない。誤りのメッセージは、何が違反でどう直せばよいかを書く（モデルが読んで呼び直せる形）。
- **状態で変わる案内はツールの結果に置く**（`next_step` などの次にすること）。静的な指示に「〜のときは〜」を並べない。呼べば結果で分かること（無いファイルは読めない等）は書かない。
- **目的と判断の基準を書き、経緯を書かない。** 事故・評価の経緯・Issue 番号・「以前は」はプロンプトに入れず、コードのコメント・docs・PR に置く。今の振る舞いとして書く。
- **システムの内部を説明しない。** 何をして何を返すかを書き、内部の仕組み（キャッシュ・モデルの呼び出しの回数・強制の方法・結果に付く印の作り方）は書かない。
- **数値・名前は正本から差し込む**（定数・設定・ツールの定義。文に手で写さない）。
- **決まった形は型とテンプレートで渡す**（構造化出力・JSON schema・出力の雛形）。誤りやすい判断にだけ短い例を 1 つ付ける。
- **読み手を分ける。** 外部の Agent に配るスキル（`skills/`）は MCP が実際に返すフィールドだけを使い、組み込み Runtime だけが結果に足すもの（`next_step` など）は「組み込みの Agent では」と分かる 1 か所にまとめる（契約は `agent/backend/tests/test_skill_md_spec.py`）。
- **節の価値は、外した版と比べて確かめる**（ablation・記録の replay。実モデルの評価は 1 回 5 問）。短くすることを目的にせず、条件・様相（必ず / してよい / しない）・否定・例外を落とさない。変えたら、最初のターンに渡す字数（token）の前後を PR に書く。
- **モデルの力を前提にする。** 既定のモデルは frontier のモデルより弱い。意味の判断の規則・例・出力の雛形・中核の制約は残し、構造化出力・ツールの結果の次の手・差し戻しと再試行・Runtime が決定的に行う手順を優先する。
- **プロンプトの文は振る舞い。** 変えたら同じ PR で関係するテストを直す。文字列をそのまま固定するテストより、契約（スキルが参照するフィールドが MCP の出力にある、ツールの結果に次の手がある等）を確かめるテストにする。

## 指示の構成と呼び出しの編成

- **Step 形式は1回の呼び出しの指示の構成、prompt chaining は複数回の呼び出しの編成。** Step は本 repo の共通表記であり、業界の認証や品質の保証ではない。段階に分けた各呼び出しでも、実際に渡す指示を Step 形式にする。
- **全体で統一するのは責務と入出力の境界であり、呼び出しの回数ではない。** 単純な分類・抽出・短い回答は1回を保つ。固定した小課題に分けられ、個別に成否を確認できる複雑な処理だけを分ける。独立した課題は予算内で並行にし、依存する課題は構造化した出力でつなぐ。Agent の動的なツールループを固定の連鎖へ置き換えない。
- **RAG は根拠の計画と回答、NL2SQL は要件確認・SQL 生成・実行前の検査、評価は比較範囲・網羅・主張の支持の責務を区別する。** 既存の段階を再利用し、同じ判定や文書の読み直しを複数の段へ追加しない。生成後の LLM 監査を分割のためだけに必須にしない。
- **段階間は検証した型で渡す。** 原質問、明示条件・否定・例外、未解決の要求、安定した要求 ID・根拠 ID・原文位置を保持する。計画や要約を事実の出典にせず、判断に必要な原文を次の段でも参照可能にする。計画の欠落・不正・時間切れを空の成功へ変えない。
- **安全上の規則は、編成の方法にかかわらずコードで強制する。** 認証・認可・対象範囲・承認、型と引用範囲・入力予算の検査はモデルの自己確認に任せない。段の追加によって権限を広げたり、別のモデル・接続へ暗黙に切り替えたりしない。

## 文脈の渡し方と改善の判定

- **必要な操作と判断に情報を近づける。** 最初は目的・使える能力・重要な制約を渡し、詳しい資料は内容の説明と取得方法を示して必要時に読む。短い結果には安定した ID と追加取得の手段を付け、関連する近傍の原文は予算内で添える。省略・切り詰めは明示する。権限・破壊的作用・必須検査の条件は操作の前に見えるまま保つ。
- **不変の指示と変化する状態を分ける。** ツールの宣言は実際に使える能力から組み立て、同じ説明を重複させない。進捗・読取済み範囲・不足情報・次の操作は要求の状態やツール結果に置く。provider 固有の差分更新・キャッシュ機能を全モデルの前提にしない。
- **短さだけで改善としない。** 変更前、指示だけを整理した版、呼び出しを分けた版を同じ質問・根拠・条件・モデルと予算で比較する。必要根拠の到達、回答と引用の正しさ、完了率に加え、全体の所要時間・呼出数・再試行・取得可能な token 使用量を測る。繰り返し検索や読み直しを含む総作業が増えていないか確認する。
- **根拠のない効果を規則にしない。** 決定論の回帰は段の順序・構造化した引き継ぎ・コードの境界を証明し、実モデルの品質と速度は固定入力の比較で確かめる。未実施・失敗・差を判定できない結果を成功と書かない。実行時の指示と schema を含む初回入力の前後を残す。
