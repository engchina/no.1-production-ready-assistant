# 共通の仕組みと製品固有の仕組みの分け方

> root の [AGENTS.md](../../AGENTS.md) から移した詳細（#2276）。root の規則と同じ強さで守る。規則を変えるときはこのファイルを直し、root には規則の要約と案内だけを書く。

- **3 製品で同じ機能は platform に 1 セットだけ置く。** システム設定（アップロード保存先・モデル・データベース）・回答の注意書きとユーザー / ロール管理は、画面を `packages/system-settings`、API を `packages/system_settings_backend` に置き、製品は `api` や権限判定を渡す薄いラッパーだけを持つ。製品固有の機能は製品固有のセクションに置く（例: NL2SQL の権限管理・Deep Data Security は「セキュリティ設定」）。
- **サイドナビの下部は 3 製品で同じ並びと名前**: 業務のセクション →「改善・運用」（あれば）→「セキュリティ設定」→「ユーザーとロール」→「運用設定」（システムテーブルが先頭、その下に軌跡の記録・チャットの添付・回答の注意書き）→「システム設定」。backend の権限カタログの `group` と並びもそろえる。
- **外部の MCP クライアント向けの API キーは 3 製品で共通**（使える製品は RAG / NL2SQL / Agent。発行の既定は 3 つとも。#1805・#1874）。Agent のキーは使える業務 Agent を絞れ（共通の表の `RESOURCE_SCOPES`）、キーごとに呼び出しの回数（`PLATFORM_API_KEY_CALLS_PER_MINUTE`）と Agent の Run の数（`PLATFORM_API_KEY_RUNS_PER_DAY`）の上限がある。仕組みは platform の共通（表 `PLATFORM_API_KEYS`・`authorize_request` の `api_key_paths`・`build_auth_router(api_keys=True)`・画面 `MyApiKeysPanel` / `ApiKeysAdminPage`）。キーは各利用者がアカウントの画面（下の「アカウントの画面」）の「API キー」のタブから自分で発行し（メニュー権限を要しない）、全員のキーの一覧と削除は「ユーザーとロール」の末尾の「API キー」（`menu.security_api_keys`）。キーは MCP の入口（`POST /api/mcp`）だけで使え、画面用の Cookie / CSRF の API には使わせない。
- **アカウントの画面は 3 製品で同じ**（`/account`。共通の `AccountPage`。#1873）: サイドナビの下部のアカウントの欄（名前・ロール）の行全体がこの画面へのリンクで、タブ「API キー」「パスワード変更」（`?tab=api-keys` / `?tab=password`）を持つ。個人の操作（API キー・パスワード変更）はサイドナビの行に置かない。初回・リセット後のパスワードの強制の変更は単独の画面（`/password/change`）のまま。ログインの画面の「パスワードを忘れた場合」は管理者に一時パスワードの発行を依頼する案内（メールの送信は無い）。
- **ナビのアイコンは、同じ機能なら 3 製品で同じ、違う機能なら違うもの**（1 製品の中で重ねない）。共通の項目は `packages/system-settings` のアイコン、製品間で同じ機能は 権限管理 `LockKeyhole`・システムテーブル `TableProperties`・品質評価 `FlaskConical`・フィードバック `ThumbsUp`・検索・回答プロファイル / 業務プロファイル `BriefcaseBusiness`・実行履歴 `History`（RAG の文書の分類は `FolderTree`）。各製品のテスト（RAG `src/lib/route-permissions.test.ts`、NL2SQL `tests/nav-config-icons.test.ts`、Agent `e2e/sidebar-nav-order.spec.ts`）が検出する。
- **「AI 活用」の下の機能は、system_admin は全員のデータ、それ以外は自分のデータだけ**を一覧・詳細・操作で扱う（3 製品共通。backend で絞り、他人のデータは 404。判定は `pr_system_settings.auth.visibility`。規則は [backend-standard.md](../../platform/docs/backend-standard.md)「「AI 活用」の下の機能のデータの見え方」。#1889）。system_admin が他の利用者のデータにできるのは、閲覧と運用の操作（停止・取り消し・削除、Agent の承認待ちの判断と再開）だけで、actor を記録し持ち主は変えない。新しい実行・内容を足す操作（続きの質問・SQL の実行・再実行・確認や明確化への回答・評価・名前の変更）は持ち主だけで、system_admin でも 403（`can_add_user_content`。#3244。#1928 を置き換え）。実行履歴の行・Run は実行した人と会話の持ち主の両方に見え、利用量・上限・監査は実行した人に数える（#1954）。
- **チャットの「会話の履歴」は、4 つのチャット（RAG・NL2SQL・NL2SQL の DB 管理・Agent）で最後の更新が直近 N 日の会話だけを出す**（共通の設定 `PLATFORM_CHAT_HISTORY_DAYS`、既定 90 日、0 は絞らない。#2340）。一覧の API が件数とページを同じ条件でサーバー側で絞り、応答の `history_days` から画面が「最近 N 日」を出す。表示の絞り込みで会話は消さず、ID では開ける。仕組みは `pr_backend_core.chat_history_window` と `@production-ready/ui` の `chatHistoryWindowLabels`（[backend-standard.md](../../platform/docs/backend-standard.md)「チャットの「会話の履歴」の期間」）。
- **回答の注意書きは製品ごとの設定**（出す / 出さない・本文・窓口。各製品の「運用設定 › システムテーブル」の下の「回答の注意書き」で、画面は platform の共有パッケージ。表 `PLATFORM_ANSWER_NOTICE` の製品の行（`answer_notice:<製品>`）、未設定は既定（有効・既定の文）。#2405・#2449）。窓口の案内の 1 行（本文の後）は、RAG の検索・回答プロファイルだけが窓口の上書きと「仕様を示し、当てはまらなければ窓口へ」の形で変えられ、業務ガイドの引き継ぎの窓口があれば注意書きに重ねない（#2400。`app/rag/answer_notice.py`）。プロファイルとガイドの画面は、空の欄に継承する窓口（ガイドは属するプロファイルの上書き、無ければシステム設定）を placeholder で示し、有効な窓口と出どころ・上の層と同じ値の案内を欄の下に出す（値は欄にコピーしない。システム設定の窓口はプロファイルの画面の権限で `GET /api/search-answer-profiles/inherited-contact` から読む。#2683）。4 つのチャットと RAG 検索の回答（根拠が足りない回答・拒答を含む）の本文の後に、共通の部品 `AnswerNotice` で出す。回答のカードの末尾の並びは共通の `AnswerFooter` が決め、回答の注意書き →「AI に渡した N 件 ／ 回答で引用 M 件」（回答の根拠）→ 回答の評価 の順にする（RAG のチャット・RAG 検索・Agent のチャット。NL2SQL のチャットは根拠の一覧と評価が無く、注意書きを SQL と結果の後に出す。#2707）。実行の詳細は「回答」の Section に本文と注意書き、別の Section「回答の根拠」に根拠の一覧を置く（RAG・Agent）。モデルに書かせず、backend が回答の確定の後に回答とは別の項目（`notice`）として付けて回答の記録に保存する（文は `pr_system_settings.answer_notice` の `AnswerNoticeProvider.current_text()`）。モデルへの指示・会話の履歴・回答の検証の対象に入れない。確認の質問・エラー・停止には出さない。 MCP（`rag_search`・`nl2sql_query` / `nl2sql_get_job`・`agent_chat` など）は API キーで呼んだ外部のクライアントにだけ `notice` を返し、Agent がサービストークンで呼んだ結果には返さない（Agent の回答には Agent が付ける 1 つだけ）。
- **チャットの添付は 3 製品で共通の仕組み**（#2517）: 保存（`PLATFORM_CHAT_ATTACHMENTS`）・解析・期限・見え方・読むツール・入力欄の部品は platform に 1 セット。使うかは製品ごとの「運用設定 › チャットの添付」（回答の注意書きの上。既定は無効）、上限は共通の `.env`。詳細は [backend-standard.md](../../platform/docs/backend-standard.md)「チャットの添付」。
- ロールの基本情報は共通のロール管理が、ロールの権限は製品の権限管理が扱う（共通のロール API は権限を変えない）。
- **権限管理のメニューの一覧は左のナビを正本にする**: 製品の `nav-config.ts` から `permissionNavSections` / `arrangePermissionsByNav`（製品の `PERMISSIONS_API.permissions` を通す）で作り、backend の `group` / `label` を画面に使わない（名前はサイドナビの表示名。`sidebarLabelKey` があればそれ）。ナビに無い capability はナビの後ろに置く。画面のあるメニュー権限は必ずナビの項目にし、ずれは各製品のテスト（RAG `src/lib/permission-nav.test.ts`、NL2SQL `tests/permission-nav.test.ts`、Agent `e2e/permission-catalog.spec.ts`）が検出する。権限の code・保存値は変えない。

- **軌跡の本文記録は3製品で1つの設定**（運用設定 › 軌跡の記録。システムテーブルの直下。#3901）。既定は無効で、共有 API と `PLATFORM_TRACE_RECORDING_SETTINGS` の単一行で管理する。新しい呼び出しの開始時に判断し、入力・出力・返却された思考・Schema・本文の診断詳細を対象とする。本文を止めても時刻・状態・階層・モデル・usage は残し、既存の trace と通常の業務記録は削除しない。
